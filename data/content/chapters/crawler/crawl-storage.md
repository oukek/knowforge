## 从具体问题认识去重、唯一约束、幂等写与检查点

采集存储需要面对重复页面、重复任务和重启恢复。去重不是在内存里放一个 Set 就结束，而是定义哪两个结果代表同一个业务对象，并让并发写入也遵守这个定义。

例如同一文章从列表与搜索入口都被发现，URL 可能不同，但来源文章 ID 相同；如果只按完整 URL 去重，就可能保存两份。反过来，同一个 URL 的新版本又不能被永久忽略。

## 业务键、幂等写与检查点顺序

先选择稳定业务键，如来源站点加文章 ID，并建立相应唯一索引。写入时按版本或更新时间决定新增、更新或忽略，避免较旧响应覆盖较新记录。内存字典能演示覆盖语义，但跨进程竞争必须由持久存储与事务条件处理。

检查点记录已可靠处理到哪里。应先保存数据，再推进分页或任务进度；若两者在同一数据库中，可以用事务协调。若跨不同系统，允许重复处理并幂等写入通常比提前确认更安全，因为重复可去除，跳过未保存数据却难恢复。

原始样本、标准化记录与派生索引最好分层保存，并记录关联版本。解析器升级后可以从允许保留的样本回放，不必重新访问所有页面。保留期、容量与删除传播也要明确，避免旧数据在搜索或向量库中长期残留。

## 把机制放到一条完整路径中

```flow
可靠采集存储
确定身份｜定义来源与业务唯一键
条件写入｜拒绝旧版本并处理重复
推进检查点｜只确认已可靠保存的数据
恢复回放｜允许重读并保持幂等结果
```

## 配套代码：去重、唯一约束、幂等写与检查点：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

store={}
for item in [{'id':'1','title':'A'},{'id':'1','title':'B'},{'id':'2','title':'C'}]:
    store[item['id']]=item
show(list(store.values()))
```

字典仅模拟按稳定键覆盖的逻辑，不提供数据库并发、持久化和事务保证。真实实现见本地配套采集项目的 SQLite 唯一主键和事务；测试需要重复运行与中断恢复，而不是只在一个进程内看到长度正确。

## 从示例走向实际使用

模拟在写入前、写入后和检查点提交后崩溃，检查恢复结果是否无遗漏且无重复业务行。并发处理同一记录时，验证唯一性与版本条件。

本项目偏好普通 ID 与索引、业务层关联校验，不需要数据库外键；但相关写入的一致性仍应使用事务或明确的恢复协议。
