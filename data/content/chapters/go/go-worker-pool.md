## 限制的是同时工作，而不是仅限制 goroutine 名字
为每个输入直接启动goroutine，简单却可能让内存、连接和下游请求瞬间膨胀。工作池用固定数量消费者从队列取任务，把活动工作数量与资源容量联系起来。队列也必须有上限，否则只是把过载从执行阶段移到等待阶段。

任务结果需要保留输入身份。完成顺序通常不同于输入顺序，如果业务要求原顺序，可以把结果写回对应索引；互不重叠元素的写入与完成后的读取，要通过明确同步保证。
## 工作池由任务、工作者和结果通道组成

生产者按顺序提供任务，固定数量worker从任务channel取出并执行，再把结果交给消费者。工作者数量限制同时执行的业务操作，任务channel容量限制等待队列，结果channel容量限制尚未消费的结果。三个数都影响内存和延迟，不能只设置worker数量而让输入和输出无限积累。

如果任务耗时不同，完成顺序通常不同于提交顺序。需要按输入顺序返回时，可以为任务携带索引，将结果写到对应独占位置，或在汇总阶段排序；不要依赖channel自然保序来推断整个并行处理结果也按序。channel保存发送顺序，但多个worker何时发送由实际执行决定。

## 失败与取消需要覆盖每个等待点

生产者可能堵在发送任务，worker可能堵在接任务、调用下游或发送结果，消费者也可能提前返回。每个可能无限等待的位置都要能观察取消，或由明确关闭协议保证退出。通常由生产者关闭任务channel，由等待所有worker退出的协调者关闭结果channel，避免多个worker抢着close。

错误策略先决定业务要求：全部成功才返回、允许部分成功、还是首个失败立即取消。即使选择首错取消，也要等待已启动工作完成清理，并明确哪些外部副作用可能已经执行。不能返回一个error后把仍在写入的goroutine留在后台。

容量选择应结合下游连接池和限流。20个worker访问只有5个连接的数据库，额外工作可能只是在等连接；加到200个通常增加排队与超时。记录队列等待、执行耗时、取消数量和完成数量，才能判断瓶颈在池前、池内还是外部服务。

## 可直接运行的两人工作池
```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	inputs := []int{2, 3, 4, 5}
	results := make([]int, len(inputs))
	jobs := make(chan int, 2)
	var workers sync.WaitGroup
	for n := 0; n < 2; n++ {
		workers.Add(1)
		go func() {
			defer workers.Done()
			for index := range jobs {
				results[index] = inputs[index] * inputs[index]
			}
		}()
	}
	for index := range inputs {
		jobs <- index
	}
	close(jobs)
	workers.Wait()
	fmt.Println(results)
}
```
发送方在全部任务发送后关闭jobs，工作者排空队列并结束，Wait之后主程序再读取结果。这个例子没有外部失败，真实任务还要传递error、context和任务截止时间，不能直接照搬成生产爬虫或支付调度器。
## 取消与错误传播如何设计
```flow
生产者与工作池
输入验证｜限制总任务量与每项成本
有界队列｜满时等待或拒绝，形成背压
固定工作者｜执行、超时、捕获可处理错误
结果归集｜保留任务ID，区分成功失败
收束退出｜关闭由自己拥有的通道，等待工作者结束
```
任务失败后是继续其它任务还是取消整个批次，必须由业务决定。取消时发送和接收两侧都应有退出路径，不能只停止消费者让生产者永远阻塞在发送。结果通道若无人消费，同样可能阻塞工作者。
## 容量和公平性
工作者数量受下游配额、连接池、CPU和内存限制。一个大用户批次不能无限占队列让其它用户饿死，可以按用户分配配额或公平调度。重试仍占总预算，并需幂等；不能把无限重试塞回同一队列制造放大。

测试队列满、用户取消、单项超时、所有消费者失败和停止服务。记录排队时长与执行时长，才能区分是工作慢还是等待资源慢。
