## 从具体问题认识miniprogram-ci 与小程序发布链路

持续集成把重复的构建与检查放到可追溯的自动化环境中。miniprogram-ci 可以参与小程序的预览和上传，但上传成功只是交付链路中的一个状态，审核与正式发布仍有各自的流程。

目标不是省掉所有人工判断，而是保证“准备发布的内容来自哪次提交、用什么工具构建、通过哪些检查”有证据。否则本地能运行的目录与真正上传的产物可能并不是同一份代码。

## 从源码到上线建立可追溯链路

构建输入包括源码版本、依赖锁文件、工具版本和环境配置。相同源码若安装了不同依赖，可能产生不同结果，因此 CI 应使用锁定安装并记录环境。测试通过后生成待上传产物，再对这份产物做包体与环境检查，避免检查源码后又用另一套配置重新构建。

上传凭据由 CI 密钥管理注入，只授予需要的能力，不写入仓库、构建日志或客户端包。前端环境变量最终可能被编译进客户端，不能用来保存 AppSecret。预览二维码和版本说明也要与构建标识关联，便于测试人员确认自己检查的是哪一版。

发布后仍需观察启动、登录、接口失败和关键业务成功率。客户端更新并非所有用户同时完成，服务端接口要兼容合理范围内的旧版本。恢复策略不仅是重新上传旧代码，还包括停止灰度、恢复配置和处理已经写入的新数据格式。

## 把机制放到一条完整路径中

```flow
可追溯发布
固定输入｜提交依赖锁与工具版本
构建验证｜测试包体与环境配置
受控上传｜使用密钥并记录产物身份
上线观察｜监控关键路径并保留恢复方案
```

## 配套代码：质量门槛与上传资格

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

把类型、用例、包体结果合成发布前决策；不连接真实 CI 或微信上传。

```javascript
function canUpload(report) {
  return report.types && report.tests && report.bundleWithinBudget;
}
console.log(canUpload({types:true, tests:true, bundleWithinBudget:true}));
console.log(canUpload({types:true, tests:false, bundleWithinBudget:true}));
console.log(canUpload({types:true, tests:true, bundleWithinBudget:false}));
```

任一必要质量门槛失败就阻止上传。上传成功也不等于审核通过或上线，真实链路还需凭证管理、产物追踪、体验验证和回退。

## 从示例走向实际使用

把流水线划分为安装、检查、构建、产物验证、上传和发布记录，每步失败都给出可定位的阶段信息。正式发布授权与普通分支构建可以使用不同权限。

本课实验验证的是发布门槛的布尔组合，不代表已经调用真实上传服务。接入时使用官方工具的当前版本与参数，并用测试应用验证密钥、路径和目标身份。
