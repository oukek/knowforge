## 为什么 count++ 不是并发安全操作
自增包含读取、计算和写回，多 goroutine 同时执行可能覆盖结果。即使某次运行结果正确，也不能据此证明安全。数据竞争讨论的是没有必要同步的并发冲突访问，不只是最后数字偶尔少了；编译器与CPU可见性也要服从语言内存模型的约束。

互斥锁将临界区串行化，并提供规定的同步关系。atomic 适合明确的单变量操作，不能自动维护涉及多个字段的不变量。余额和流水必须一致时，分别原子加两个数字仍可能让观察者看到中间状态。
## 数据竞争与业务竞争分别是什么

多个goroutine并发访问同一内存，其中至少一个写入且缺乏必要同步，会形成数据竞争。`count++`包含读、计算、写回，两个任务可能都读到旧值后覆盖结果。即使某个单独操作是原子的，“检查余额足够→扣减余额”这个复合业务过程也可能竞争，所以需要保护整个不变量。

Mutex让同一时刻只有一个持锁者进入相关临界区；所有访问同一受保护数据的路径都要遵守协议，只锁写路径而让读路径裸读仍可能错误。defer Unlock便于确保返回时释放，但临界区应尽量小，不在持锁期间执行慢网络请求或调用未知回调。

## 同步不仅排顺序，也建立可见性关系

Go内存模型通过同步操作定义跨goroutine可观察的顺序。不能因为“我先启动A，后来启动B”就推断B一定看见A的所有写入；启动顺序不是完成顺序。channel交接、锁释放与后续获取等建立规定的同步关系，代码应通过这些关系表达依赖。

RWMutex允许多个读者同时持读锁，但写入需要独占，不代表它总比Mutex快。读写比例、临界区长度和竞争模式决定收益。原子操作适合简单共享值或经过严谨设计的无锁结构，但多个原子字段不能自动组成一个一致快照；结构复杂时普通锁往往更清楚。

`go test -race`能在执行到的路径中发现很多竞争，代价是额外资源和时间。没报告不代表所有调度都安全，因此测试需要主动并发覆盖关键访问，设计上仍应明确数据拥有者与同步协议。含锁对象在使用后不要复制，这也是方法和容器设计需要考虑的语义。

## 用锁保护共享不变量
```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	var wg sync.WaitGroup
	total := 0
	for i := 0; i < 4; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := 0; j < 100; j++ {
				mu.Lock()
				total++
				mu.Unlock()
			}
		}()
	}
	wg.Wait()
	fmt.Println(total)
}
```
锁保护的范围应覆盖完整不变量，而不是随意把某一行围起来。持锁期间做慢网络请求会延长等待；多个锁还需一致顺序避免死锁。使用后的 Mutex 不应被随意复制，含锁结构体的方法与传参也要小心。
## 先有同步，再讨论可见性
```flow

识别共享可变数据｜哪些 goroutine 能读写

选择同步边界｜锁、channel 所有权或特定原子操作
所有访问遵守同一规则｜读也不能绕过保护
运行竞态检测与压力测试｜补充检查，但不替代设计
```
go test -race 能发现被执行路径上的数据竞争，未报错不证明未覆盖路径也安全。竞态检测有额外开销，测试环境应使用代表性的并发场景。普通 map 并发写读尤其不能靠“读多写少”直接忽略同步。
## 什么时候使用 RWMutex 或原子值
读写锁适合特定读写比例与临界区特征，不一定比 Mutex 快；需要测量竞争和持锁时长。原子发布不可变快照可降低读锁开销，但更新后的对象若继续被普通写入，就破坏了不可变约定。

先选择易于证明正确的方案，再分析瓶颈。为了减少锁而复制大量数据，或为追求并发而增加复杂状态机，都可能把问题转移到内存和维护成本。
