## 从具体问题认识Node 内存、GC 与线上泄漏排查

Node 进程的内存不只有 JavaScript 对象堆。Buffer、原生库、线程栈和运行时也会占用内存；操作系统看到的进程驻留内存，与 V8 堆统计不是同一个指标。只盯着 heapUsed，可能漏掉真正增长的部分。

垃圾回收释放的是不可达对象，而不是业务上“已经没用”的对象。一个全局 Map 若一直保存历史请求，里面的对象仍可达，回收器没有理由替你删除它们。

## 从增长曲线定位保留关系

先区分正常峰值、缓存增长与泄漏。处理大请求时内存上升、结束后回落，可能是正常工作集；缓存达到容量后趋稳，也可能符合设计；重复执行相同操作后基线持续上升，才需要寻找未释放的引用或外部资源。

常见保留链包括全局缓存、事件监听、未清理的定时器、长寿命闭包和未完成任务。堆快照用来查看对象由谁保留，比较不同时间点的数量与保留大小。采集快照本身可能暂停进程并消耗内存，线上应选择合适实例和时机，不能在已接近内存上限时盲目连续采集。

GC 时间也会影响延迟。对象分配过快，即使最终都能回收，也会制造回收压力。优化应减少不必要的大对象复制、限制请求体与队列，并给缓存设置容量、TTL 或明确淘汰策略。单纯增加堆上限可能推迟崩溃，却不会修复无限增长。

## 把机制放到一条完整路径中

```flow
内存排查
观察曲线｜区分峰值与持续基线增长
分解指标｜查看堆外内存与运行负载
寻找引用｜比较快照和资源生命周期
验证修复｜重复负载确认上界与延迟
```

## 配套代码：有界缓存比无限保留更可控

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

用 Map 模拟保留对象数量，只说明引用存量，不模拟 GC 或真实 RSS。

```javascript
const cache=new Map();
function put(key,value) {
  cache.set(key,value);
  if(cache.size>2) cache.delete(cache.keys().next().value);
}
for(let i=0;i<5;i++) put(i,{payload:i});
console.log(cache.size);
console.log([...cache.keys()]);
```

容量限制使旧引用不再被缓存保留；是否回收仍取决于其他引用和 GC。真实排查要分 heap/external/RSS，不可由缓存条数直接推断进程内存。

## 从示例走向实际使用

观察 RSS、堆使用、外部内存、请求量与 GC 延迟的同一时间线，再决定检查哪类资源。做可重复负载，等待系统回到空闲，比较基线而非只看瞬时峰值。

课内缓存只限制条目数；真实缓存还应考虑每条数据大小。一千个小对象和一千张大图片的成本完全不同，必要时按字节预算淘汰。
