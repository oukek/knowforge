## 从具体问题认识错误、请求、性能与白屏监控

监控把线上发生的事件变成可检索证据。错误监控回答哪里失败，请求监控回答哪段依赖慢或不可用，性能监控回答用户等待多久，白屏监控则尝试识别主要界面未正常出现。它们需要共同的版本与请求标识才能关联。

只收集 JavaScript 异常会漏掉接口一直等待、资源加载失败或渲染出空内容等问题；反过来，页面空白也可能是正常加载或用户权限限制，不能只凭一个空节点就报警。

## 事件采集、归并与可行动告警

事件应包含时间、应用版本、页面路径、错误类别和必要关联 ID。原始堆栈可以结合 source map 恢复源码位置，但 source map 的访问与发布要受控。聚合指纹应减少相同问题的重复噪音，同时避免把不同根因都合并成“加载失败”。

采样需要区分总量估计与单次诊断。若只采成功请求的一部分、失败请求全部上报，计算失败率时必须使用相应权重或完整计数，否则比例会失真。用户内容、令牌和敏感参数应在采集前裁剪，而不是先全部上传再期待后台隐藏。

告警应说明影响和可执行下一步，例如某版本课程详情加载失败率上升，并关联发布与依赖状态。单个错误出现一次不一定值得打断值班，持续异常却也不能因平均值正常而被掩盖。阈值、窗口和去重规则要与业务目标匹配。

## 把机制放到一条完整路径中

```flow
可定位的监控事件
采集｜获取错误请求与页面状态
裁剪关联｜脱敏并附加版本追踪标识
聚合分析｜归并问题并计算真实影响
行动告警｜连接发布证据与排障路径
```

## 配套代码：错误聚合与敏感字段白名单

下面代码在课内JavaScript运行区执行；需要DOM、Node或平台SDK的真实集成，应按正文的运行边界另行验证。

只从原始事件提取必要字段，并按稳定指纹统计次数。

```javascript
const raw={message:'加载失败',release:'v1',path:'/home',token:'secret-demo'};
const safe={message:raw.message,release:raw.release,path:raw.path};
const issues=new Map();
for(const event of [safe,safe]) {
  const key=event.release+':'+event.message;
  issues.set(key,(issues.get(key)??0)+1);
}
console.log(Object.hasOwn(safe,'token'));
console.log([...issues.values()]);
```

白名单避免顺手上传 token；指纹聚合相同错误以便观察频率。真实 SDK 需更细的脱敏、采样与上下文策略，消息本身也可能含敏感信息。

## 从示例走向实际使用

先用一个受控错误验证从浏览器到后台的完整链路：能否找到版本、源码位置、关联请求和影响人数。再模拟网络超时与资源 404，确认不同问题不会全部落入同一个模糊类别。

白屏检测可结合主要内容标记、路由状态和错误信号，并记录误报情况。它是需要校准的检测器，不能替代真实业务成功指标。
