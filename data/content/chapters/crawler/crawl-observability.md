## 从具体问题认识采集可观测性、错误预算与回放

采集可观测性让你解释任务为什么慢、为什么失败、数据在哪个阶段丢失。一个总耗时数字只能说明结果，不能区分排队、网络、解析和存储。各阶段需要共同任务 ID 才能连接成完整时间线。

例如请求只花 120 毫秒，存储却花 240 毫秒，增加下载并发可能让存储积压更严重。先定位阶段，再调整参数。

## 任务、尝试与数据质量一起观察

任务指标关注最终完成率、积压年龄和更新时间；尝试指标关注请求状态、重试与超时；数据质量指标关注字段与记录。一次任务重试三次后成功，应计一个成功任务和三次尝试，而不是混在一个比例里。

日志包含任务 ID、来源、阶段、解析器版本和错误分类，敏感凭据与完整用户数据应裁剪。延迟分布按域名与阶段分组，避免一个慢站点被全局平均掩盖。队列最老任务年龄往往比当前长度更能暴露长期饥饿。

回放能力把失败样本交给相同或新解析器重现，帮助区分网络变化与代码变化。错误预算用于讨论可接受失败范围与何时停止扩大采集，不应变成允许忽略数据损坏的借口。告警需要对应具体行动，例如暂停某站解析或降低速率。

## 把机制放到一条完整路径中

```flow
采集观测
关联身份｜区分任务尝试与记录版本
阶段计时｜拆分排队网络解析和存储
质量汇总｜结合结果完整性与错误分类
行动回放｜定位原因并验证修复
```

## 配套代码：采集可观测性、错误预算与回放：最小可验证示例

下面代码在课内Python运行区执行；浏览器环境与本机CPython的网络、文件和原生扩展能力不同。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

timings={'queue':30,'network':120,'parse':10,'store':240}
show(max(timings,key=timings.get))
show(sum(timings.values()))
```

固定阶段时长说明总体等待可能由存储占据，即使 CPU 不高也能成为瓶颈。真实并发链路可能有重叠阶段，不能简单求和所有并行 span；应区分关键路径、累计工作量和端到端耗时。

## 从示例走向实际使用

从一个故意失败的任务检查是否能找到来源响应、解析版本、尝试链与最终状态。再让存储变慢，确认监控指出存储与排队压力，而不是只报请求超时。

建立运行摘要时同时报告成功、永久失败、等待重试与隔离记录，避免只展示已成功写入数量让任务看起来完整。
