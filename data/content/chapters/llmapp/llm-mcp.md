## 从具体问题认识MCP、工具协议与连接权限

MCP 用统一协议连接 AI 应用与外部工具、资源和提示模板。可以把它理解为“连接与发现的约定”：应用不必为每种工具来源发明完全不同的通信结构，但仍需要决定哪些能力对哪个用户开放。

协议兼容不等于工具安全，也不意味着把某个服务接上后，模型会自动正确使用其中所有工具。描述质量、权限与执行策略仍属于应用设计。

## Host、Client 与 Server 的职责

Host 是承载用户交互和模型编排的应用，它管理连接、上下文与许可。Client 负责与某个 Server 交换协议消息，Server 暴露工具、资源或提示能力。一个 Host 可以连接多个 Server，不应假定所有服务器支持同一组可选功能。

生命周期必须绑定版本理解：2025-11-25 的传统模式使用初始化握手，2026-07-28 的现代核心模式使用自包含请求与按请求能力协商。部署时固定双方支持的协议和 SDK，不把传统会话假设套到所有版本。详见 [2026-07-28 规范](https://modelcontextprotocol.io/specification/2026-07-28)；进阶课继续介绍双版本边界。

发现工具时得到名称、说明和输入 Schema；调用时需要带符合协议的请求并处理结果与错误。工具描述本身来自外部，不能被视为高优先级系统规则。工具数量很多时按任务筛选，避免把所有描述一次塞进上下文。

传输认证与业务授权是不同层次。HTTP 传输的授权机制按所用协议版本与服务能力实现，stdio 常通过本地进程环境提供凭据；无论哪种方式，都还要检查实际资源归属。不能把“连接已认证”理解为可以访问该服务全部租户数据。

## 把机制放到一条完整路径中

```flow
MCP 接入路径
确定连接｜Host 管理 Client 与目标 Server
协商发现｜确认版本能力和可用工具
筛选授权｜按任务与身份限制暴露范围
调用处理｜验证参数结果错误与断线状态
```

## 配套代码：MCP、工具协议与连接权限：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

tool={'name':'search_docs','inputSchema':{'type':'object','required':['query']}}
show(tool['name'])
show(tool['inputSchema']['required'])
```

对象展示工具契约的一个片段，不是完整 MCP 初始化或传输实现。协议版本和 schema 支持范围应跟随官方规范与 SDK；服务器仍必须验证真实身份、参数和资源权限，不能因工具被发现就允许执行全部能力。

## 从示例走向实际使用

接入一个只读工具开始，验证发现、调用、错误、断线重连与权限拒绝，再逐步增加写能力。保留协议版本和服务身份，出现兼容问题时能定位具体连接。

课内工具字典只是 Schema 形状示例，没有建立真实 MCP 会话。实际客户端应使用符合选定协议版本的实现并测试协商过程。
