## 从具体问题认识条件请求、ETag 与增量抓取

条件请求让客户端询问资源是否变化，而不必每次重新下载完整正文。ETag 是服务端给某个表示分配的验证标记，客户端保存它，下次通过 If-None-Match 发送；未变化时服务器可以返回 304，让客户端继续使用已有正文。

304 不是一份新的空文章，而是需要结合本地缓存解释的响应。如果本地正文已经丢失，只保留 ETag，就无法凭 304 重建内容。

## 验证器、表示与增量策略

缓存记录应把正文、ETag、Last-Modified 和来源请求条件关联起来。不同语言、身份或内容协商可能得到不同表示，因此不能只按 URL 无条件共享。私人页面的缓存必须隔离会话或授权作用域。

条件请求减少传输与解析成本，但服务器仍可能执行验证逻辑，不能认为它完全没有源站成本。ETag 不一定是内容 hash，也不保证跨不同资源具有统一含义；应把它当服务端提供的不透明验证器。弱验证器与强验证器的使用场景也有差异。

增量抓取还需要决定何时重新验证。高频变化页面与稳定历史文档可采用不同刷新周期，并保留失败时的旧数据状态。拿到 200 新正文后，先验证解析质量，再替换正式记录，避免一次登录页或错误页污染缓存。

## 把机制放到一条完整路径中

```flow
条件抓取
保存表示｜正文与验证器绑定存储
发出条件｜携带适用的 If-None-Match
解释响应｜304复用200校验新内容
更新记录｜同步正文版本与检查时间
```

## 配套代码：条件请求、ETag 与增量抓取：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

cached={'etag':'"v2"','body':'article'}
status=304
body=cached['body'] if status==304 else 'new'
show(body)
show({'If-None-Match':cached['etag']})
```

模型展示 304 分支保留旧正文，没有进行真实缓存协商。生产实现还需检查缓存命中、Vary 与身份维度，并决定解析版本变化是否重放；ETag 的值应按源站返回保存，不自行假设其内部生成算法。

## 从示例走向实际使用

测试 200→304→200 的版本变化，确认正文与元数据同步更新。再测试只有验证器没有正文、不同身份请求和服务器不支持条件请求的回退。

课内示例从已有缓存取正文，强调 304 的上下文依赖。真实客户端应按 HTTP 缓存语义更新相关元数据，而不是简单跳过所有处理。
