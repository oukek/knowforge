## 导入会执行模块顶层代码
模块提供独立名字空间，import首次加载时通常执行其顶层语句，并将模块对象放入缓存。后续同一模块身份的导入通常复用对象，所以模块级列表和连接可能成为长期共享状态。把网络请求或数据库写入放在导入时执行，会让测试与启动难以控制。

包组织多个模块，模块名与安装发行包名不一定相同。相对导入依赖包上下文，直接运行包内文件和用python -m运行模块可能有不同行为，不能靠不断修改sys.path掩盖结构问题。
## 两种导入写法绑定了不同的名字

`import math` 在当前命名空间绑定模块对象，随后用math.sqrt访问属性；`from math import sqrt` 把当时取到的sqrt对象绑定到当前名字。模块属性之后被重新赋值，不会自动让另一模块中已经复制出来的名字跟着重新绑定；这也是patch测试替身时需要替换实际查找位置的原因。

普通包可以包含__init__.py，子模块各有独立命名空间；命名空间包还有不同组织方式。安装发行包名、import模块名与源码目录名不必相同，所以安装错误时要看项目文档，不能只按import文字猜pip名称。避免在自己的目录放json.py、typing.py等遮蔽标准库。

```python
import math
from math import sqrt

print(math.sqrt(9), sqrt(16))
print(__name__)
```

## 用依赖方向组织项目，而不是用导入修补结构

可以把项目分为入口、业务服务、数据访问和公共类型：入口读取配置并组装依赖，业务层使用明确接口，数据层实现具体存储。若两个模块互相导入对方的大量实现，往往意味着职责或公共抽象需要重新划分。把import挪进函数能推迟发生时间，但不必然解决架构上的循环关系。

执行 `python -m package.module` 时，解释器按模块路径建立包上下文；直接 `python package/module.py` 则按脚本入口运行，相关路径与相对导入可能不同。项目应该提供固定启动命令，测试也按同样的安装方式运行，避免开发时依赖当前目录，而部署后包找不到。

sys.modules缓存的是当前解释器进程里的模块对象。多个worker进程各自导入，各自拥有全局状态；它不能承担跨进程计数、分布式锁或持久队列的职责。需要跨进程共享时，应显式使用外部存储或通信机制。

## 定义清晰的可运行入口
```python
def main():
    print("ready")

if __name__ == "__main__":
    main()
```
作为脚本入口时执行main，作为库导入时只定义函数。业务初始化放在显式启动函数里，可接收配置与依赖，便于测试替换。CLI参数、环境变量读取和退出码也应在边界统一处理。
## 循环导入为何暴露半初始化状态
A导入B，B又导入A，第二次可能看到尚未执行完的A模块。需要的名字还没定义时就会失败。将共同类型和接口提到第三模块、减少顶层副作用、重新安排依赖方向，通常比在所有地方临时局部import更清晰。
```flow
导入与运行
查找模块路径｜环境、包结构和名字
创建并缓存模块对象｜支持复用与循环识别
执行顶层语句｜此时可能尚未完全初始化
绑定导出名字｜调用方引用模块或属性
显式入口启动业务｜配置、资源和生命周期在此建立
```
## 交付一个可安装项目
pyproject.toml描述构建和包信息，测试从干净环境安装后再运行，避免只有源码目录碰巧在sys.path里时能用。不要用与标准库相同的文件名，如json.py，导致导入自己的文件而不是预期模块。

检查导入失败时确认解释器、模块搜索路径、实际__file__和安装版本。多进程或服务重载可能重新初始化模块，不能用“导入只执行一次”保证跨进程全局唯一副作用。
