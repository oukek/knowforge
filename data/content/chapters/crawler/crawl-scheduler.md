## 从具体问题认识调度器、有界队列与背压

调度器决定哪些采集任务何时执行。它连接发现链接的生产者与实际下载解析的消费者，承担去重、优先级、延迟重试和并发控制。没有调度边界时，一个页面发现几千个链接，就可能立即创建几千个请求。

队列让任务可以等待，但无限队列只是把过载从网络转移到内存或存储。可靠调度必须定义容量与入队策略。

## 任务状态与背压

任务至少区分待执行、执行中、等待重试和终态。调度键可包含规范 URL、请求方法和必要参数，避免错误地把不同请求合并。优先级用于安排重要内容，但要防止低优先任务长期饥饿；公平性可以按站点或租户分配。

当队列达到上限，生产者应暂停、拒绝或把任务持久化到受控存储，而不是继续创建未等待的协程。下载、解析与存储各阶段都有吞吐差异，存储变慢时也应反馈到前面，否则响应会在内存中积压。

延迟重试不宜一直占用下载并发槽。把 nextRunAt 写入调度状态，到了允许时间再领取，能让其他站点继续执行。停止程序时先停止新增任务，再处理已领取任务与检查点，保证恢复后不会跳过未完成工作。

## 把机制放到一条完整路径中

```flow
有界采集调度
发现任务｜规范化并检查范围与重复
等待队列｜按容量优先级和域公平组织
领取执行｜遵守并发与最早执行时间
结果回流｜保存成功或安排有限重试
```

## 配套代码：调度器、有界队列与背压：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

capacity=3; queue=[]; rejected=[]
for url in ['a','b','c','d']:
    (queue if len(queue)<capacity else rejected).append(url)
show(queue)
show(rejected)
```

小模型演示容量达到后必须选择拒绝或背压策略，未实现真实异步阻塞队列。实际可用 asyncio.Queue(maxsize=...) 配合固定消费者，注意 task_done、取消和异常清理；不能把拒绝后的任务悄悄丢弃而不记录。

## 从示例走向实际使用

用快速发现链接、慢速保存结果的模拟负载观察队列长度，确认达到预算后压力能够向上传播。分别记录排队时间和请求时间，避免把自己的拥堵误判为目标站点变慢。

课内容量模型演示拒绝超额任务。生产系统选择暂停还是持久化，应根据是否允许丢任务与可用资源明确设计。
