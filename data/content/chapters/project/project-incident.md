## 从具体问题认识线上故障

故障经历的技术价值，在于能解释故障如何产生、为什么扩大、如何恢复，以及后来怎样降低再次发生的概率。把故事讲成“线上出问题，我重启就好了”，只能说明做了一个动作，不能说明理解了系统。

止损、定位、修复和复盘是不同阶段。止损可以先恢复服务，最终修复则要处理根因，复盘还应检查检测与响应过程为何没有更早阻止影响。

## 按时间线呈现判断与证据

先说明影响范围与最初信号，例如某版本登录失败率升高而课程静态页面正常。接着列当时可用证据、主要假设和排除过程。不要把事后已经知道的根因写成当时一眼就看出的结论，真实的不确定性与验证过程更能体现能力。

每个恢复动作应对应目标：回滚针对最近变更，限流保护过载依赖，关闭某功能减少故障扩散。操作后需要观察业务成功率与积压恢复，不能因为进程重新启动就宣布恢复。若动作有风险，如旧版本不兼容新数据，应说明当时如何评估。

根因分析应区分触发因素、系统缺陷与防线缺口。例如一次大输入触发内存耗尽，根因不应停在“用户传了大文件”，还需检查输入限制、流式处理、队列容量与告警。改进项要有负责人和验收方式，避免只写“加强测试、提高意识”。

## 把机制放到一条完整路径中

```flow
故障叙述
发现影响｜说明症状范围与最初证据
判断止损｜解释假设与恢复动作
定位修复｜连接触发条件和传播机制
复盘验收｜验证改进能阻止同类问题
```

## 配套代码：时间线与恢复耗时

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

以虚构时间点区分发现与恢复，说明指标定义的重要性。

```javascript
const timeline={started:100,detected:130,recovered:220};
console.log(timeline.detected-timeline.started);
console.log(timeline.recovered-timeline.detected);
console.log(timeline.recovered-timeline.started);
```

分别为发现延迟、发现后恢复和总影响时长，口径不同不应混用。实际事故还需用户影响、止损证据与长期改进，时间差不能替代根因分析。

## 从示例走向实际使用

选择一个自己真正参与的事件，准备时间线、关键证据和一项已验证改进。若只是演练或协助排查，应如实说明角色，不把团队整体恢复工作都归为个人。

技术细节优先解释最关键的因果链，再根据追问展开日志、SQL 或回滚操作。不要把敏感账号、客户数据和生产凭据带入面试材料。
