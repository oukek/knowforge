## 从具体问题认识上下文工程

上下文工程是为某一次模型调用选择、整理和更新信息的过程。提示词只是其中一部分，任务状态、对话历史、工具结果、检索证据和技能说明都在竞争有限空间。内容越多不一定越好，关键在于当前决策需要什么。

例如退款助手必须保留订单金额、已退金额、审批对象和版本，而几十轮闲聊通常可以压缩。若只保留“用户同意退款”，却丢掉同意的金额，压缩就破坏了业务条件。

## 必须保留的信息与可牺牲的信息

先写状态不变量：哪些事实缺失后系统不能安全继续。把它们标为必需内容，预算不足时拒绝装配或拆任务，不能静默删掉。可选资料按相关性与边际价值排序，重复证据和冗长日志可以移到外部存储并保留引用。

摘要应是一种有契约的数据转换，明确目标、已完成动作、待办、证据、冲突与未确认事项。压缩前后可用同一组问题检查这些条件是否仍可回答。把“可能是缓存问题”压成“故障原因是缓存”就是语义升级错误。

工具调用与结果需要配对，引用仍能定位原文，权限来源不能被摘要改写。上下文装配还要防止跨用户、跨任务残留；缓存复用时验证数据版本和访问范围。

## 上下文是一次受约束的信息装配

模型调用输入包含任务规则、用户目标、历史行动、工具定义和外部证据。它们有不同信任级别、有效期和删除规则。上下文工程先决定本轮需要什么、哪些必须保留、哪些应重新查询，再决定如何排列和压缩。扩大窗口只能提高容量，不能保证模型注意到关键约束或证据没有过期。

退款任务最小状态可以包含：用户意图、已确认订单、政策版本、已执行操作 ID、待用户确认的问题、未完成步骤和已知错误。把“聊了 80 轮”压成一段流畅故事，若丢掉“用户尚未同意提交”，仍是不合格压缩。

## 预算应在装配前分配

建立输入上限，并为预期输出、工具定义、协议开销与安全余量预留空间。字符数只能用于粗估，准确计数需采用匹配模型及消息格式的计数方式；中文、代码、图片和工具 schema 的代价不能靠统一四字符规则处理。

| 信息 | 默认策略 | 失效条件 |
|---|---|---|
| 当前目标与禁止动作 | 必须保留，独立字段 | 用户明确改变目标 |
| 已提交操作凭据 | 保留稳定引用，按需查账 | 到期归档，不应凭摘要抹除 |
| 外部搜索全文 | 选择片段、去重、附来源 | 文档变更或权限收回 |
| 调试中间日志 | 保留结论和必要反例 | 阶段结束后压缩 |

必要项本身已超预算时应显式失败或拆分任务，不能静默删除规则后继续。

## 裁剪必须保留可核验性

工具结果可以先结构化，只回传当前问题需要的字段、单位、时间、版本和来源 ID。对列表采取确定性排序和分页，并标明 `truncated`、总数与继续查询方式。不能把“只取到 20 条”改写成“只有 20 条”，也不能把未查询区域当作不存在。

```js
const result = {
  items: rows.slice(0, limit),
  total: rows.length,
  truncated: rows.length > limit,
  sourceVersion: 'inventory-v7'
};
```

敏感数据的裁剪还应在进入模型前完成。权限不够时不要先把全文发给模型，再依赖提示要求它不泄漏。

## 压缩的状态契约

应用自己生成的摘要应有明确字段、来源指针和版本，保留未决事项与相互矛盾的事实，避免用新推测覆盖用户原话。对工具调用链，调用与结果要保持关联，不得留下一个失去对应调用的结果。

OpenAI 官方 compaction 还包含不透明的压缩状态项；它不是让应用自由编辑的人类摘要。使用对应服务时按其状态续接约定保留返回内容，不应猜测其内部文本或手工重写。具体阈值与 API 配置取决于使用接口；本课浏览器实验只演示应用层预算选择。

## 如何验收压缩质量

建立固定的“下一步问题集”：当前目标是什么、哪些动作已完成、还缺什么授权、关键证据从哪来、哪些事实尚未确定。对完整上下文和压缩上下文分别运行同一套检查，同时评估 token、延迟和任务成功率。不能只用字数缩短率评价质量。

当任务阶段改变时重新装配，旧候选方案可以丢弃，已接受的约束和提交凭据必须继续可查。上线后记录上下文版本、选择原因和来源引用，排障时才能区分检索未找到、裁剪丢失和生成误用。

## 把机制放到一条完整路径中

```flow
上下文装配
提取任务状态｜明确目标证据与不可丢条件
分配预算｜先保证必需信息和输出空间
选择压缩｜裁掉重复项并保留来源引用
验证装配｜检查配对权限与语义不变量
```

## 配套代码：上下文工程：预算、压缩与任务状态不变量

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。



```javascript
function pack(items, inputLimit, reserved) {
  const budget = inputLimit - reserved;
  const must = items.filter((x) => x.required);
  let used = must.reduce((sum, x) => sum + x.tokens, 0);
  if (used > budget) throw Error("required context exceeds budget");
  const chosen = [...must];
  for (const item of items
    .filter((x) => !x.required)
    .sort((a, b) => b.priority - a.priority)) {
    if (used + item.tokens <= budget) {
      chosen.push(item);
      used += item.tokens;
    }
  }
  return { ids: chosen.map((x) => x.id), used };
}
const items = [
  { id: "goal", tokens: 20, required: true },
  { id: "receipt", tokens: 15, required: true },
  { id: "evidence", tokens: 30, priority: 9 },
  { id: "debug", tokens: 50, priority: 1 },
];
console.log(pack(items, 100, 25));
try {
  pack(items, 40, 10);
} catch (e) {
  console.log(e.message);
}
```

预算单位是题目预先给定的 token 数，代码不实现真实 tokenizer。必留项无法容纳时停止；可选项按优先级放入，调换优先级可观察不同取舍。

## 从示例走向实际使用

给长任务构造多次压缩场景，检查目标、审批条件与副作用回执是否丢失。比较的是任务成功与边界保持，不只是 token 少了多少。

课内装配器用贪心顺序选可选项，易理解但不保证全局最优。它最重要的约束是必需项超预算时明确失败。
