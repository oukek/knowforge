## 从具体问题认识WebSocket、心跳与断线重连

WebSocket让客户端和服务器在一条连接上双向发送消息，适合聊天、协作和需要服务端主动通知的场景。建立连接并不等于用户已认证，连接不断也不等于每条业务消息已保存。传输状态、会话身份和消息状态必须分别描述。

与普通请求响应相比，长连接把重连、心跳、慢消费者和部署退出变成显式问题。选用它的理由应是双向交互需求，而不是看到“实时”就默认使用。

## 连接状态与业务确认分离

客户端经历连接中、已连接、关闭中和已关闭等状态，只有适当状态才可发送。代理和网络可能静默丢弃空闲连接，因此需要心跳或应用活动检测；浏览器API并不暴露所有底层控制帧操作，应用心跳应按客户端与服务端能力设计。

TCP有序传输只作用于一段连接。断线重连后若希望消息不丢不重，需要稳定消息ID、服务端持久化确认和恢复游标。客户端发送成功可能只意味着进入本地缓冲，服务端收到也可能尚未提交；界面应区分待发送、已接收、已持久和已读等业务状态。

重连使用退避与抖动，防止所有客户端在服务恢复时同时冲击。缓冲队列必须有上限，慢消费者应降速、合并状态更新或断开并恢复，而不是无限堆消息。鉴权过期、用户退出和权限撤销也应影响既有连接，不能只在第一次握手检查。

## 把机制放到一条完整路径中

```flow
可靠长连接消息
建立连接并认证｜确认用户与订阅权限
发送带ID的业务消息｜本地发送不等于持久成功
服务端处理并确认｜明确确认对应的完成点
断线后按游标恢复｜去重、重放与退避共同工作
```

## 配套代码：补拉与去重的消息归并

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

在本地模拟重连后重复收到一条消息，并补齐序号缺口。

```javascript
const local = [{id:'a', seq:1}, {id:'c', seq:3}];
const replay = [{id:'b', seq:2}, {id:'c', seq:3}];
const merged = new Map(local.map(item => [item.id, item]));
for (const item of replay) merged.set(item.id, item);
console.log([...merged.values()].sort((a,b) => a.seq-b.seq).map(item => item.id));
console.log(Math.max(...[...merged.values()].map(item => item.seq)));
```

消息 ID 负责去重，频道序号负责排序与恢复游标。这只是本地归并步骤，真实系统还需鉴权、缺口检测、ACK 和服务端幂等。

## 从示例走向实际使用

设计消息协议时写清类型、版本、ID、序号、幂等与结束语义。测试发送后立即断网、服务端保存后响应丢失、重复恢复和乱序业务事件。

服务发布先停止接受新连接，通知或等待现有连接迁移，并提供恢复路径。只统计在线连接数不足以判断健康，还要观察积压、往返延迟、重连率和业务确认延迟。
