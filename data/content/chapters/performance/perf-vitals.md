## 从具体问题认识LCP、INP、CLS 与分位数

性能指标把用户体验中的某个方面转成可比较的数据。LCP 关注主要内容何时出现，INP 关注交互后多久出现下一次画面反馈，CLS 关注页面元素是否发生意外位移。三者分别描述加载、响应和视觉稳定性，不是同一种“页面速度”。

用户看到主图很快，并不代表点击按钮也及时；按钮很灵敏，也不代表图片加载后不会把正文推走。因此需要分别定位每个指标对应的阶段。

## 从单次体验到用户群体分布

LCP 对应视口内符合条件的最大内容元素的绘制时刻，其延迟可能来自服务器响应、资源发现、下载或渲染等待。INP 把一次交互相关的等待与处理、呈现时间纳入观察，长任务可以让输入已经到达却迟迟无法处理。CLS 则根据布局移动的影响范围与位移计算，不是简单统计页面移动次数。

真实用户设备、网络与访问路径不同，平均值容易掩盖尾部问题。分位数回答“多少比例的样本不超过某个值”，例如 p75 关注四分之三用户以内的体验。小样本分位数会不稳定，比较版本时应保留样本量，并按移动端、路由等关键条件分组。

实验室测试控制条件，便于复现和定位；真实用户监测反映实际分布，但受用户构成影响。两者不能互相替代。指标采集还要遵守各指标生命周期与页面可见性规则，优先采用维护良好的官方测量实现，避免自己用几个时间戳拼出同名但含义不同的数值。

## 把机制放到一条完整路径中

```flow
体验指标定位
选择维度｜加载交互或视觉稳定
收集样本｜关联页面设备与版本
分析分布｜结合分位数样本量与分组
定位阶段｜用时间线验证具体优化
```

## 配套代码：按样本计算 p75，而不是只看平均

下面代码在课内JavaScript运行区执行；需要DOM、Node或平台SDK的真实集成，应按正文的运行边界另行验证。

使用 nearest-rank 定义演示 p75；并非 web-vitals SDK，也不是完整指标采集。

```javascript
function percentile(values, ratio) {
  const sorted=[...values].sort((a,b)=>a-b);
  return sorted[Math.ceil(sorted.length*ratio)-1];
}
const samples=[100,100,100,1000];
console.log(samples.reduce((a,b)=>a+b,0)/samples.length);
console.log(percentile(samples,0.75));
console.log(percentile(samples,0.95));
```

均值为 325，但 p75 为 100，p95 落在 1000；不同统计量表达不同问题。真实 CWV 聚合需说明指标生命周期、足量样本与设备分组。

## 从示例走向实际使用

先选择一个具体问题：主图慢就拆资源链路，交互慢就看主线程任务，布局跳动就检查尺寸预留和异步插入。优化后用相同口径比较，并确认没有牺牲其他体验。

课内分位数采用一种明确的离散计算方法，适合说明分布；分析平台可能采用不同插值算法，报表比较前应确认口径一致。
