## JavaScript 为什么需要事件循环

页面需要同时面对用户输入、网络返回、计时器和视觉更新。如果一次网络请求必须在 JavaScript 调用栈上等到返回，用户输入也只能跟着等。浏览器把等待交给相应宿主能力，在结果准备好以后安排后续代码；事件循环负责不断寻找可执行工作。这里的“异步”是工作分阶段完成，不等于回调都在不同 CPU 核心上并行执行。

先认识调用栈。函数调用时进入栈，返回时退出栈；同步函数通常运行到返回、抛错或显式挂起的位置才让出控制。按钮回调中执行十秒大循环，浏览器不能简单从循环中间插入另一个普通点击回调。其它线程可能仍在收网络数据，但当前主线程不能及时执行 JavaScript 和部分渲染工作。

## Task 与 microtask 分别存放什么

一次脚本执行、某些用户交互回调和计时器回调会作为任务（task）被调度。“宏任务”是常见教学叫法，规范通常说 task。浏览器存在不同任务来源，不能假设所有工作都进入一个统一的全局 FIFO 队列。计时器到期只是满足可调度条件，不承诺指定毫秒马上执行。

微任务用于在某些检查点处理更紧邻当前工作的后续步骤，Promise reaction 和 queueMicrotask 属于典型例子。当前任务的同步代码结束并到达适当检查点后，会处理微任务，而且微任务里继续加入的微任务也会在本次检查点继续被取出。于是无限追加微任务可以阻止后续任务和渲染获得机会。

```flow
主线程如何接续工作（简化模型）
选择一个可运行任务｜例如一段脚本、点击或到期定时器
执行同步代码｜函数入栈、调用、返回
微任务检查点｜执行 Promise 回调及新增微任务直到队列为空
合适的渲染机会｜处理与本次更新相关的渲染工作
再次选择任务｜不是每次循环都必定绘制一帧
```

图中是理解常见输出题的模型。完整浏览器还会在其它规范规定的位置执行检查点，渲染也有刷新率、可见性、性能预算等条件。因此不要用“每个宏任务后必定重绘”推导所有实际行为。

## 一行一行追踪登记与执行

```javascript
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => {
  console.log('C');
  queueMicrotask(() => console.log('E'));
});
console.log('D');
```

执行第一行立即打印 A；第二行向宿主登记计时器，当前栈不等待；第三行登记已兑现 Promise 的成功处理器；最后同步打印 D。随后微任务检查点执行 C，并把 E 加入微任务队列；检查点继续执行 E。之后计时器回调有机会运行，打印 B。这里要区分“代码所在行被执行”和“登记的回调被执行”，它们不是同一时刻。

输出为 A、D、C、E、B。不应因此得出“Promise 一定比定时器快”：若 Promise 依赖一个尚未完成的网络操作，它的 reaction 还没准备好，计时器当然可能先运行。微任务优先规则作用于已经可以排队的回调，不会让未来数据提前到达。

## await 暂停了谁

```javascript
async function example() {
  console.log('inside');
  await 0;
  console.log('resume');
}
example();
console.log('outside');
```

调用 async 函数时，遇到第一个 await 之前仍同步执行，因此先 inside。await 使当前 async 函数的后续部分挂起，调用方继续输出 outside；随后恢复函数输出 resume。它没有暂停整个线程，也没有创建后台计算线程。即使 await 的是普通值，后续也不是在当前同步调用里直接接着运行。

把 CPU 密集代码包装成 `Promise.resolve().then(bigLoop)` 只是更换了开始执行的时机，计算仍在同一线程。真正需要隔离 CPU 工作时使用 Worker；任务很小但数量多时，可以分批处理并主动给其它任务机会。并不是异步关键字越多页面就越流畅。

## requestAnimationFrame 与渲染的关系

rAF 的回调在合适的渲染更新阶段执行，常用于读取本次动画时间并提交视觉更新。它不是固定16毫秒的定时器，后台页面可能被降频或暂停，高刷新率屏幕也不同。回调中先改 DOM 再读几何，依然可能强制同步布局。

如果要让 loading 有机会被看到，仅执行 `loading=true; await Promise.resolve(); bigLoop()` 仍可能不够，因为微任务继续占据本轮检查点；一次 DOM 更新不等于屏幕已显示。业务应将重计算移到 Worker，或用实际任务边界分片并测量交互延迟，而不是靠猜测 setTimeout 的毫秒数保证绘制。

## 把调度知识用于可维护的代码

搜索时异步返回可能乱序，这是业务请求竞争，与微任务队列有序并不矛盾；使用请求序号和取消信号。组件卸载后还存在回调，需要注销订阅和忽略过期结果。生产代码应按完成信号组织依赖，避免靠“延迟100毫秒应该好了”拼接流程。

Node.js 也有事件循环，但包含 libuv 阶段、I/O 回调和 process.nextTick 等特有机制，不能把本课浏览器图直接当成 Node 全部规则。学习输出顺序时先注明运行环境、脚本类型及任务来源，再解释同步、微任务和任务之间的关系。
