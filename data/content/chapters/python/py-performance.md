## 性能慢不一定是语言慢
一次任务可能花时间在算法重复计算、数据库、网络、文件或大量对象分配。先分解墙钟时间与CPU时间，再选工具。优化一个只占总耗时1%的小循环，即使快一倍也难改变整体体验。

规模增长会放大复杂度差异，list成员查找每次扫描与set平均快速查询是不同算法选择。微基准在很小输入上的结果，不能替代真实数据规模、内存和I/O分析。
## 时间指标要对应用户真实等待

墙钟时间是从开始到结束经过的时间，包含网络等待、排队和CPU执行；CPU时间更接近进程实际占用处理器的工作量。一个接口墙钟很慢但CPU很低，优先查依赖等待与资源排队，而不是立刻优化Python循环。吞吐是单位时间完成的工作数量，延迟是单个任务等待时间，高吞吐不保证每个用户都快。

平均值容易掩盖尾部。100次请求里99次很快、1次极慢，平均值可能仍漂亮，但用户会感到偶发卡死。观察p95、p99以及超时比例，并按缓存命中、输入规模和依赖状态分组，才能知道慢请求为什么不同。

## 建立一个可重复的测量样本

```python
from timeit import repeat

values = list(range(1000))
allowed = set(values)
list_times = repeat(lambda: 999 in values, number=1000, repeat=3)
set_times = repeat(lambda: 999 in allowed, number=1000, repeat=3)
print(len(list_times), len(set_times))
```

这个微基准故意只测已构造容器中的查找，不包含构造set的成本。因此它能回答“重复成员查询”的局部问题，不能直接证明整个请求应该改用集合。若实际每次只查一次且先构造巨大集合，结论可能不同。记录测量边界比发布一个倍数更重要。

分析函数热点时要区分自身耗时与包含子调用的累计耗时。一个入口函数累计时间很长，可能只是调用了慢数据库；修改入口几行代码不会消除下游等待。优化应提出明确机制：减少重复扫描、批量查询、降低对象分配或避免无效序列化，然后在正确性测试通过后重测代表性负载。

## 先减少重复工作
```python
wanted = ["a", "c"]
rows = ["a", "b", "c", "d"]
allowed = set(wanted)
result = [row for row in rows if row in allowed]
print(result)
```
预先构建集合有一次成本，但重复查询可以受益；若只查询一次或键不可哈希，选择可能不同。不能把任何list都改成set，因为顺序和重复项语义也会改变。
## 使用剖析工具建立证据
cProfile帮助观察函数调用耗时，timeit适合隔离小段代码比较，tracemalloc可分析Python层分配。工具各自有盲区：原生扩展、系统I/O与整个进程内存不一定完全出现在同一种记录里。应记录输入规模、解释器版本、环境和是否热缓存。
```flow
优化闭环
定义目标与负载｜耗时、吞吐、尾延迟或内存
测量并定位热点｜CPU、等待或分配
提出一个原因明确的修改｜算法、批量、缓存或并发
验证正确性｜输出、顺序、边界不改变
重复测量｜确认收益与代价，保留可回退方案
```
## 缓存与并发不是免费午餐
缓存需要容量、失效和身份隔离，可能把CPU问题换成内存与一致性问题。并发需要下游容量、队列与超时，可能提高吞吐却增加尾延迟。生成器减少峰值内存，但若最终仍全量排序，某些内存成本不可避免。

测试不仅比较正常数据，还要包含最坏形状、空数据和大输入。不要为了一个更漂亮的基准牺牲错误处理与可读性；重要优化应能解释消除了哪一段工作。
