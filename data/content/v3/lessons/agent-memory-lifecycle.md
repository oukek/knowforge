## 记忆不是一个无限增长的向量表
会话检查点保存某条执行线程的状态，长期存储保存跨会话有意义的信息。LangGraph 中 checkpointer 与 store 对应不同作用域；应用仍需定义保存什么、谁能读、何时失效。把每句对话嵌入向量库，会把临时假设、敏感信息和互相矛盾的结论混在一起。

先区分用户明确声明的偏好、业务系统的事实、模型推测和运行日志。用户说“这次用英文”未必代表永久偏好；助手猜测的公司规模不能自动成为下次销售决策的事实。
## 一条记忆应带哪些元数据
建议记录主体与租户、key、value、来源、确认状态、有效期、版本和撤回标志。来源最好指向可追踪事件，事实更改保留更新关系，避免只写一个 updated_at 让“最后到达”覆盖真相。来自权威业务系统的订单状态应在行动前重新查询，而非长期信任聊天记忆。

```python
fact = dict(tenant='a', subject='u1', key='language', value='zh',
            source='user-confirmed', confirmed=True, expires_at=100, revoked=False)
```

不要把 access token、数据库口令等秘密作为一般记忆送入模型。身份和授权从可信上下文获取，不能让记忆中的 tenant 覆盖当前登录主体。
## 冲突解决是业务策略
同一用户两条已确认偏好相互冲突时，可以按明确版本替代关系处理，或保留冲突并询问。不能仅凭 embedding 分数更高就认定更新。接收时间晚也可能是迟到旧事件，需要比较事件版本、来源与适用范围。

| 类型 | 推荐规则 | 例外 |
|---|---|---|
| 一次性指令 | 限当前任务 | 用户明确设为长期偏好 |
| 权威事实 | 按来源版本更新 | 行动前可能仍需刷新 |
| 模型推测 | 不自动提升为确认事实 | 经人工或权威系统验证 |
| 相互冲突的确认项 | 显式冲突或有据替代 | 不采用任意最后写入胜出 |

不同来源的可信度必须是宿主策略，不应由模型给自己的输出打高分。
## 读取也需要上下文与权限
先按租户、主体和用途过滤，再做相似检索；读取时检查撤回、TTL 和当前访问范围。过期不一定代表数据物理删除，但它不应继续影响决策。生成摘要时保留来源引用，便于后续撤回传播到派生内容。

共享团队记忆还需防止私有会话流入公共 store。子 Agent 只获得其任务必需的记忆视图，不能因为它是内部模块就读取全部用户历史。测试同名用户、跨租户同 ID 和权限变更。
## 可运行实验：拒绝未确认与冲突
实验只选择当前租户、未撤回、未过期且明确确认的事实。若没有候选返回 missing，若值冲突返回 conflict，而不是随便选最后一条。对确认且同值的多来源可以合并来源，但不能丢失原始出处。

试着加入 `confirmed=False` 的模型推测，它不应覆盖用户事实；把过期时间调到当前时刻，应被排除；把两个值设成相同，冲突消失。这个例子定义的是保守策略，真实业务可以设计有版本的替换规则。
## 遗忘与验收
用户删除记忆时，应处理主记录、向量索引、缓存、摘要和备份恢复策略。保存 tombstone 或删除代次，防止迟到同步把已删除数据复活；记录最小必要审计信息，而不在审计日志重新复制敏感原文。

验收包含新增、纠正、冲突、过期、撤回、跨线程读取、跨租户和离线同步。分别统计记忆命中带来的任务改善与错误记忆造成的损害；“记住得更多”不是质量指标。关键是可纠正、可解释和可遗忘。
