## goroutine 是运行时调度的并发任务
在函数调用前写 go，会让它作为 goroutine 运行，当前调用方继续执行。goroutine 不是与操作系统线程一一对应的固定对象，Go 运行时把许多任务安排在线程上。并发表示多个工作生命周期重叠，并行表示同一时刻在多个执行资源上运行，二者不能混用。

主 goroutine 结束会导致程序退出，不会自动等所有后台任务完成。因而 `go work()` 之后随便 sleep 一秒不是正确同步：任务可能更快，也可能慢于一秒。必须有明确等待与退出契约。
## go关键字启动了什么，main退出又意味着什么

普通函数调用要等被调用函数返回后才继续；`go work()`安排一个新的goroutine执行work，当前goroutine可以继续推进。新任务何时开始、先打印哪一行通常没有顺序保证。main返回时进程结束，不会自动等待所有后台goroutine，所以“我已经启动它”并不等于工作一定完成。

goroutine由Go运行时调度到操作系统线程上，初始栈较轻量并可按需增长，但仍占内存、调度与资源。创建十万个等待网络的goroutine可能同时建立十万个请求或保留巨大对象，不能把轻量理解为没有容量上限。并发工作应有数量预算和可观察生命周期。

## 等待完成、传递结果和共享数据需要不同工具

WaitGroup记录尚未完成的工作数量，Add在启动相关工作前建立计数，Done在退出时减计数，Wait等待归零。它负责等待，不收集返回值，也不自动传播错误或取消其它任务。结果可以写入各自独占的位置，或通过channel汇总；多个任务修改同一位置仍需同步。

闭包会捕获外部变量，要明确每个goroutine实际使用哪份值以及是否共享对象。较新Go版本改变了某些循环变量语义，但不能把“循环变量已独立”扩大成“slice、指针和map都不再共享”。显式传参和明确数据所有权仍更容易阅读。

任务失败时，需要由拥有者决定是继续其它工作还是统一取消。每个阻塞操作都应考虑退出路径，例如发送结果时消费者已经离开，发送方可能永久堵住。等待所有任务结束与保证没有泄漏，是并发函数完成契约的一部分。

## 用 WaitGroup 等待工作结束
```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	results := make([]int, 3)
	for i := range results {
		wg.Add(1)
		go func(index int) {
			defer wg.Done()
			results[index] = index * index
		}(i)
	}
	wg.Wait()
	fmt.Println(results)
}
```
这里每个 goroutine 写不同元素，主程序在 Wait 返回后读取，不需要为了输出顺序依赖任务完成先后。WaitGroup 负责等待，不会自动传播业务错误、限制任务数量或取消其它任务。Add 的调用安排应避免与等待错误竞争。
## 调度器如何利用线程
常见解释用 G 表示 goroutine、M 表示操作系统线程、P 表示运行 Go 代码所需的调度资源。这个模型帮助理解为什么大量 goroutine 不等于大量线程，以及阻塞、系统调用和网络等待会如何影响调度。具体队列和抢占实现随版本变化，不应背固定源码细节当语言保证。
```flow
并发任务的生命周期
创建工作｜定义输入、所有权与错误通道
启动 goroutine｜进入可调度任务集合
运行或等待｜计算、锁、channel、网络等
完成或取消｜释放资源，报告结果
调用方收束｜确认所有属于本次任务的工作已结束
```
## 泄漏与过量并发
向无人接收的 channel 发送、永远等不到关闭信号、忘记取消子任务，都会让 goroutine 长期不退出。即使栈可增长、起始成本较小，一百万个等待任务也有内存与调度成本。使用有界工作池、队列上限和 context，把任务数量与资源预算联系起来。

排查时看 goroutine profile、阻塞与互斥锁记录，不要只看 CPU。CPU 低也可能所有任务都堵在连接池上。每个 go 语句都应能回答由谁等待、由谁取消、错误返回给谁。
