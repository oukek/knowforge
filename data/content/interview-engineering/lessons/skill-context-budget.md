## 渐进披露解决了哪一部分
把元数据、主体说明和外部资源分层能减少无关全文，但大量技能的 name/description 本身仍会占满目录。多个技能同时激活、引用链递归、历史工具结果持续累积，也会让上下文失控。问题是活跃信息总量与任务相关性，不只是单个 SKILL.md 的长度。
## 用两级目录减少候选集合
先按业务域、角色和权限过滤，再从短摘要、关键词或向量检索挑候选，必要时用轻量分类器或模型复排。只对候选加载详细适用条件，真正执行前才加载步骤和资源。保留用户显式点名的技能与强制规则，路由不确定时澄清或有界扩搜，不能静默丢掉必须遵循的约束。

检索目录应含用途、触发与不适用条件、输入输出、依赖、费用和风险标签。不能只按技能名字模糊匹配，也不能把授权当相似度阈值。需要执行什么权限由宿主检查，读到某技能文本不代表自动获得网络、文件或付款权限。
## 预算分配和退出机制
把上下文预算分给系统约束、任务、活跃技能、证据、最近历史与工具输出，为模型输出预留空间。按估算 token 分配上限，限制同时激活数、引用深度和工具结果长度；完成的子任务用带来源摘要归档并可重新读取，避免摘要叠摘要丢失限制。硬性规则与待确认事项不能用普通摘要随意压掉。
## 评估不是只看 token 下降
记录候选召回、错误激活、漏掉关键技能、首次有效行动时间、费用与任务成功。设计跨域任务、名字相近、显式指定、多个技能协作和恶意资源指令样本；比较全量目录、分类目录与检索目录的效果。缓存按技能版本和权限域分区，更新后失效，避免旧说明继续指导写操作。
## 可运行预算装配器
示例把必需技能先放入，再按相关性选择可容纳的候选，跳过超预算项。真实系统应先计算必需部分是否超限，若超限需拆任务或压缩说明，不能强行截断；token 估算不是精确计费，仍需记录实际用量回流。
## 面试回答的重点
可以先指出渐进披露有价值但不保证无限扩展，再给出目录检索、按需激活、生命周期清理和可量化回归。避免“再把提示压短一点”这一种手段。对于重要步骤重复读引发成本的问题，可使用版本引用和受控缓存，但必须确保模型确实掌握当前约束。

## 朋友原题与口述参考
**原题记录：** skill渐进式披露还是太多，怎么搞？

先区分目录元数据过多、激活过多、资源递归和历史膨胀。两级路由先按领域与权限缩小目录，再检索候选、复核适用条件，只加载当前阶段步骤与必要资源。显式指定和强制规则保留。

设全局 token 预算、激活数、引用深度和结果上限，完成后归档并用版本引用重新获取；不能压掉关键权限和未决事项。评估候选召回、漏技能、错激活、任务成功和费用，不把减少 token 当唯一成功。权限仍由执行层判断，Skill 文本不等于执行授权。

## 延伸追问与分析
**一千个 Skill 的描述也放不进上下文，该怎样设计技能检索？**

把目录移到可查询索引，先按角色/领域筛选再做词项与语义检索，取有限候选加载详细适用条件。保留显式调用路径与检索失败回退，按关键技能召回和错激活评估；加载结果带版本和预算。

检查点：外部目录、候选召回、显式路径。

**摘要压缩后 Agent 漏掉了审批条件，怎样避免再次发生？**

将审批、权限和任务硬约束作为宿主规则与结构化状态独立保存，摘要只压可恢复的辅助内容。执行前再次验证审批版本与作用范围，用摘要遗漏样本回归，不能只在提示里强调不要忘记。

检查点：结构化约束、执行验证、遗漏回归。

**Skill 内容更新后，有些会话还在使用旧规则，如何管理？**

每次激活绑定版本和有效期，缓存键含版本与权限域。重要策略变更由宿主即时执行，长任务在安全边界重新验证；对已经执行的副作用留审计，而非假装重载能撤销过去操作。

检查点：版本缓存、安全边界、历史审计。

## 实践任务与验收
构造 100 个教学技能，每个有用途、负面触发条件和 200 token 的主体，设计“查订单但不退款”“先查询再需要审批的修改”等跨域任务。分别比较全量主体、只有摘要目录、检索前五个候选三种装配方式，记录候选命中、实际加载 token 和首次有效工具调用。仅命中技能名字却漏掉必要审批步骤应判任务失败。

给资源返回设置上限并模拟一个引用环 A→B→A，系统应检测已加载的版本引用并停止展开，而不是不断压缩后继续读取。再修改一个技能版本，确认后续任务不复用旧正文；在长期会话中只清除已完成子任务的可恢复材料。产出一份上下文账单，列明哪些 token 不能省、哪些来自冗余目录、哪些由工具重复返回造成，用证据决定优化顺序。
