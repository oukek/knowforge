## 从具体问题认识Agent 记忆生命周期

Agent 的长期记忆需要像业务数据一样管理生命周期。事实、偏好、推测和一次任务中的临时状态不能混存成无差别文本。否则旧推测可能在多次检索后被当成可靠事实。

例如“用户喜欢中文”与“这次请用英文”不一定矛盾：前者是默认偏好，后者是当前任务指令。记忆解释必须带作用域。

## 来源、冲突与遗忘策略

条目记录主体、类型、值、来源、确认状态、生效范围和时间。用户明确确认的事实通常比模型推断更可信，但新的明确更正也应能替换旧值。优先级是业务政策，需要可解释，不能简单按最后写入覆盖。

冲突可能来自真实变化，也可能来自误提取、跨账号污染或过期资料。保留多个候选及来源，无法确定时请求澄清或暂不注入。向量相似度用于找相关记忆，不负责解决事实冲突。

遗忘包括撤销、过期和用户删除，并传播到索引、摘要与缓存。读取时再次检查可见性和有效期，防止已删除条目被旧缓存重新带回上下文。审计保留需求与用户可见记忆的用途分别设计。

## 记忆不是一个无限增长的向量表

会话检查点保存某条执行线程的状态，长期存储保存跨会话有意义的信息。LangGraph 中 checkpointer 与 store 对应不同作用域；应用仍需定义保存什么、谁能读、何时失效。把每句对话嵌入向量库，会把临时假设、敏感信息和互相矛盾的结论混在一起。

先区分用户明确声明的偏好、业务系统的事实、模型推测和运行日志。用户说“这次用英文”未必代表永久偏好；助手猜测的公司规模不能自动成为下次销售决策的事实。

## 一条记忆应带哪些元数据

建议记录主体与租户、key、value、来源、确认状态、有效期、版本和撤回标志。来源最好指向可追踪事件，事实更改保留更新关系，避免只写一个 updated_at 让“最后到达”覆盖真相。来自权威业务系统的订单状态应在行动前重新查询，而非长期信任聊天记忆。

```python
fact = dict(tenant='a', subject='u1', key='language', value='zh',
            source='user-confirmed', confirmed=True, expires_at=100, revoked=False)
```

不要把 access token、数据库口令等秘密作为一般记忆送入模型。身份和授权从可信上下文获取，不能让记忆中的 tenant 覆盖当前登录主体。

## 冲突解决是业务策略

同一用户两条已确认偏好相互冲突时，可以按明确版本替代关系处理，或保留冲突并询问。不能仅凭 embedding 分数更高就认定更新。接收时间晚也可能是迟到旧事件，需要比较事件版本、来源与适用范围。

| 类型 | 推荐规则 | 例外 |
|---|---|---|
| 一次性指令 | 限当前任务 | 用户明确设为长期偏好 |
| 权威事实 | 按来源版本更新 | 行动前可能仍需刷新 |
| 模型推测 | 不自动提升为确认事实 | 经人工或权威系统验证 |
| 相互冲突的确认项 | 显式冲突或有据替代 | 不采用任意最后写入胜出 |

不同来源的可信度必须是宿主策略，不应由模型给自己的输出打高分。

## 读取也需要上下文与权限

先按租户、主体和用途过滤，再做相似检索；读取时检查撤回、TTL 和当前访问范围。过期不一定代表数据物理删除，但它不应继续影响决策。生成摘要时保留来源引用，便于后续撤回传播到派生内容。

共享团队记忆还需防止私有会话流入公共 store。子 Agent 只获得其任务必需的记忆视图，不能因为它是内部模块就读取全部用户历史。测试同名用户、跨租户同 ID 和权限变更。

## 遗忘与验收

用户删除记忆时，应处理主记录、向量索引、缓存、摘要和备份恢复策略。保存 tombstone 或删除代次，防止迟到同步把已删除数据复活；记录最小必要审计信息，而不在审计日志重新复制敏感原文。

验收包含新增、纠正、冲突、过期、撤回、跨线程读取、跨租户和离线同步。分别统计记忆命中带来的任务改善与错误记忆造成的损害；“记住得更多”不是质量指标。关键是可纠正、可解释和可遗忘。

## 把机制放到一条完整路径中

```flow
长期记忆治理
提取与分类｜区分事实偏好推测和临时状态
验证与入库｜保存主体来源范围及有效期
按需解析｜发现冲突并选择可靠相关信息
更新与遗忘｜同步撤销派生索引摘要和缓存
```

## 配套代码：Agent 记忆生命周期：事实、偏好、冲突与遗忘

下面代码在课内Python运行区执行；浏览器环境与本机CPython的网络、文件和原生扩展能力不同。



```python
def resolve(records, tenant, key, now):
    candidates = [r for r in records if r['tenant']==tenant and r['key']==key
        and r['confirmed'] and not r['revoked'] and now<r['expires_at']]
    values = sorted({r['value'] for r in candidates})
    if not values:
        return {'status':'missing'}
    if len(values)>1:
        return {'status':'conflict','values':values}
    return {'status':'resolved','value':values[0]}

base = dict(tenant='a', key='language', confirmed=True, revoked=False, expires_at=100)
rows = [{**base,'value':'zh'}, {**base,'value':'en'}]
print(resolve(rows,'a','language',50))
print(resolve(rows[:1]+[{**base,'value':'en','confirmed':False}],'a','language',50))
print(resolve(rows,'a','language',100))
```

多个有效确认值冲突时拒绝静默覆盖；未确认推测不参与，now 等于到期时刻已失效。实验用固定时间，方便复现边界。

## 从示例走向实际使用

构造偏好变更、多个来源冲突、同名不同用户和到期边界样本。记录为何选择某条记忆，让用户能纠正而不是面对无法解释的个性化。

课内 resolve 对不同有效值返回 conflict，不擅自选择一个；真实产品可以在明确业务规则下进一步处理。
