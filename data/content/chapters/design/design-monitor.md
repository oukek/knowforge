## 从具体问题认识系统设计

监控平台包含客户端采集、接收服务、存储聚合、查询和告警。每一层都可能丢数据或产生压力，因此不能只做一个异常列表页面就认为平台完整。平台需要把事件转成可解释的影响范围与排查线索。

例如同一个错误在一个用户设备上重复一千次，与一千个用户各发生一次，业务影响不同。事件次数、会话数与受影响用户数应分别统计。

## 从事件协议到查询与告警

采集协议规定事件类型、版本、时间、应用标识和可接受字段，接收端校验大小与权限并执行限流。原始事件适合排查细节，聚合数据适合趋势查询；保留期与存储成本应按用途区分。不能无限保留所有用户输入作为“以后可能有用”的日志。

错误聚合可以结合归一化堆栈、类型与版本，减少动态参数造成的碎片。source map 应与构建版本精确匹配，否则源码定位会指向错误行。发布记录、请求追踪和用户操作摘要应通过关联 ID 连接，避免查询时只能人工猜测。

告警计算需要可信分母与窗口。若某版本只有十次请求，失败一次的比例很高，但与十万次请求中大面积失败的处理优先级不同。应结合绝对影响、持续时间、业务重要性和历史基线，提供去重与恢复通知，防止告警风暴。

## 把机制放到一条完整路径中

```flow
监控平台链路
事件采集｜遵守协议并裁剪敏感字段
可靠接收｜校验限流去重与缓冲
存储聚合｜关联版本请求和源码位置
查询告警｜按真实影响产生可行动信号
```

## 配套代码：按发布版本聚合故障率

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

同一错误在不同发布中应分组，避免均值隐藏新版本回归。

```javascript
const events=[{release:'v1',ok:true},{release:'v1',ok:true},{release:'v2',ok:false},{release:'v2',ok:true}];
const groups=new Map();
for(const event of events) {
  const group=groups.get(event.release)??{total:0,failed:0};
  group.total++;if(!event.ok)group.failed++;groups.set(event.release,group);
}
console.log([...groups].map(([release,group])=>[release,group.failed/group.total]));
```

分组后 v2 的失败率明显不同；真实告警还需最低样本、用户影响、采样权重和版本关联，不能据两条演示事件做发布决策。

## 从示例走向实际使用

从一个最小闭环开始：人工触发已知错误，确认接收、聚合、源码定位、告警与恢复都正确。再测试接收服务不可用时客户端是否有界缓存且不影响主业务。

课内按版本统计失败率说明分组的重要性；实际平台还需处理采样、迟到事件、时钟偏差与重复上报。
