## 单元测试先确定可观察契约
函数的输入范围、错误行为与返回值构成契约。测试正常例子只是开始，还要覆盖空值、边界、无效输入和状态变化。表驱动测试将多组输入与预期放在数据表里，减少重复代码，但案例必须来自不同风险，不是把同一种正常输入复制十遍。

测试文件以 _test.go 结尾，测试函数接受 *testing.T；程序例子和基准有各自命名与签名规则。go test ./... 覆盖当前模块包集合，不能证明未执行路径正确，特别是并发与外部依赖。
## 测试文件如何参与构建

以_test.go结尾的文件参与go test，测试函数使用Test前缀和*testing.T参数。测试可以与被测包同名以访问包内实现，也可以使用外部测试包更接近调用方视角。选择取决于需要验证的边界，不应为了方便把所有内部细节都变成公开API。

表驱动测试把多组输入与预期放进结构体切片，通过t.Run命名子测试，适合边界清晰的纯函数。预期应来自独立业务规则，而不是复制被测算法计算一遍。浮点比较、时间值和随机输入要使用明确契约，不能靠无差别截断让测试通过。

## 并发、HTTP与外部依赖怎样隔离

httptest可以直接调用Handler或启动本地测试服务器，分别覆盖业务处理与真实HTTP交互。数据库测试使用独立库和可清理数据，不能连接生产实例。外部接口可通过小接口替身控制成功、超时和错误，但替身不证明真实服务协议一定匹配，仍需单独契约或集成验证。

t.Parallel让测试并发执行，也会暴露全局配置、端口和共享文件之间的冲突。每个测试应拥有自己的资源，使用t.Cleanup注册清理，使断言失败时仍能执行。等待异步结果优先用channel或明确条件，固定sleep把正确性寄托于机器速度，容易产生偶发失败。

模糊测试探索意外输入，适合解析器、编码往返和边界函数；保存失败样本才能形成回归。竞态检测只覆盖实际执行的调度路径，基准测试则测性能，三者不是互相替代。先有正确契约，再用适合风险的工具验证。

## 一个可独立测试的纯函数
```go
package main

import "fmt"

func Clamp(value, low, high int) int {
	if value < low {
		return low
	}
	if value > high {
		return high
	}
	return value
}
func main() {
	fmt.Println(Clamp(-1, 0, 10))
	fmt.Println(Clamp(20, 0, 10))
}
```
将 Clamp 放进对应包后，测试可用表覆盖低于下限、等于边界、区间内、高于上限，并明确 low>high 时的契约。如果输入约束未定义，测试作者和实现者可能各自猜一套规则。
## 基准不是只比一个纳秒数字
基准应避免把无关初始化混入被测部分，使用代表性规模并记录分配次数。比较不同实现时保持相同环境、输入和输出契约，警惕编译器消除未使用结果。缓存热度、GC与并发都会影响结果，不用单次数字推断生产吞吐。
```flow
验证逐层加深
确定输入与行为契约｜正常、边界、错误
单元与表驱动测试｜小范围快速定位
模糊测试｜自动探索输入组合与不变量
竞态与集成测试｜并发、协议、数据库等真实边界
基准与剖析｜正确后再判断热点和资源成本
```
## 模糊测试与并发检查
模糊测试适合解析器、编码解码往返等可以定义不变量的场景。先提供种子输入，再让工具探索变异；失败样本应保留成回归用例。不要把真实外部付费接口放进无限生成输入的测试循环。

-race 帮助发现实际执行的竞态，context 取消和 channel 关闭还需要设计确定的同步测试，避免固定 sleep。测试替身应模拟必要故障，如提交失败或半段响应，而不是复制真实实现，导致实现和测试犯同一个错。
