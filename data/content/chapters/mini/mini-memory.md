## 从具体问题认识图片、内存告警与资源释放

文件大小与图片解码后的内存占用不是一回事。一张压缩后几百 KB 的图片，解码成像素后可能占用数 MB；同时显示很多大图时，即使网络下载很快，内存与绘制压力仍可能导致卡顿或进程被回收。

内存问题还包括仍被引用的页面数据、定时器回调和事件监听。对象不再出现在屏幕上，不代表它已经不可达；只要某个长期存在的引用仍指向它，垃圾回收就不能按开发者的意图释放它。

## 沿着资源与引用寻找内存来源

粗略估算普通 RGBA 像素缓冲时，可用宽乘高乘每像素字节数理解数量级；实际实现还可能包含额外缓冲、纹理和平台管理开销。把四千像素宽的原图缩成小缩略图显示，并不会保证只按缩略图大小占用所有中间资源。因此应在服务端提供适合显示尺寸的图片变体。

缓存需要容量和淘汰策略。无限保存浏览过的图片与接口响应，短时命中率看起来很好，长期使用却会持续增长。缓存键还应考虑尺寸与版本，避免相同资源保存大量近似副本。页面退出时释放页面独占资源，共享缓存则由统一管理者控制生命周期。

排查泄漏要比较重复操作前后的稳定基线，例如连续进入退出详情十次，再等待正常回收，看实例数量与内存是否仍阶梯式上涨。单次峰值可能是临时解码，持续增长才更像保留问题。收到平台内存告警时，应清理可重建缓存和停止非必要工作，但不能把告警处理当成唯一治理方案。

## 把机制放到一条完整路径中

```flow
资源内存生命周期
获取｜选择与显示尺寸匹配的资源
解码展示｜关注像素缓冲和可见数量
缓存管理｜设置容量版本与淘汰规则
退出清理｜断开引用并释放可重建资源
```

## 配套代码：压缩文件大小不等于解码内存

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

按 RGBA 每像素四字节估算驻留，不模拟宿主实际内存分配。

```javascript
function rgbaMiB(width, height, copies=1) { return width*height*4*copies/1024/1024; }
console.log(rgbaMiB(2048, 2048));
console.log(rgbaMiB(2048, 2048, 3));
console.log(rgbaMiB(512, 512));
```

2048² RGBA 像素约 16MiB，三份约 48MiB；缩略到 512² 约 1MiB。真实纹理、解码缓存与格式存在额外开销，这只是估算，不是内存上限。
