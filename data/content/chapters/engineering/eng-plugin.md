## 从具体问题认识Loader、Plugin 与模块转换流程

构建扩展通常有两类职责：把某个模块的内容转换成另一种形式，以及在整个构建生命周期中参与解析、生成或统计。Webpack 的 Loader 与 Plugin 体现了这种分工，但不同工具的名称与钩子并不完全一致。

例如把 TypeScript 转成 JavaScript 是模块转换；在构建结束后生成资源体积报告，则需要看到多个产物和构建阶段。先明确自己需要哪一层能力，才能选对扩展入口。

## 转换函数之外还有依赖与来源信息

一个可靠转换不只是输入字符串、输出字符串。它还可能需要声明额外依赖、生成 source map、报告错误位置，并使用配置影响缓存。若读取了一个模板文件却没声明依赖，模板变化后构建缓存可能仍返回旧结果。

处理语法应使用相应解析器和 AST。简单字符串替换无法区分关键字、字符串内容和注释，例如把所有 const 替换成 let 可能误改用户文本。AST 将语法结构表示为节点，转换器针对节点修改，再生成代码与映射信息。

插件钩子有执行阶段和并发语义。读取模块、修改模块、生成产物和写入文件并不是同一时间点；钩子太晚可能无法影响依赖图，太早则还没有完整产物。插件还应避免每个模块重复执行昂贵初始化，并在热更新或关闭时释放监听资源。

## 把机制放到一条完整路径中

```flow
构建扩展职责
确定阶段｜模块转换还是全局生命周期
解析输入｜保留语法与依赖信息
执行变换｜生成结果及来源映射
缓存验证｜输入或配置变化时正确失效
```

## 配套代码：单模块转换与产物级检查

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

用函数模拟不同层级的扩展职责，不执行真实 Loader/Plugin。

```javascript
const transform=source => source.replace('const','let');
const assets=[{name:'a.js',bytes:80},{name:'b.js',bytes:50}];
console.log(transform('const count=1;'));
console.log(assets.reduce((sum,file)=>sum+file.bytes,0));
console.log(assets.every(file=>file.bytes<=100));
```

转换函数看单个模块，产物检查能观察整个资产集合。这里的文本替换不是可靠语法转译，真实 Babel/Loader 应操作 AST 或使用成熟转换器。

## 从示例走向实际使用

先用一个最小输入输出例子定义转换契约，再加入语法边界、source map 和缓存失效测试。涉及构建统计时，使用产物阶段的正式接口，不扫描猜测中的临时目录。

课内字符串替换仅演示“转换”和“产物统计”属于不同职责，不能直接当生产语法转换器。真实插件应声明支持的工具版本与运行阶段。
