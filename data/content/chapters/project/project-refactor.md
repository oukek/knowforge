## 从具体问题认识重构、技术债与渐进迁移

重构是在保持外部行为的前提下改善内部结构；功能改造会改变行为，两者可以在同一项目中发生，但应分别说明。技术债不是所有“不够优雅”的代码，而是让未来修改、验证或运行持续付出额外成本的结构问题。

例如同一权限规则复制在多个路由中，新增规则时容易漏改，这就是可具体描述的维护成本。提取统一业务入口是否值得，应看错误与变更成本，而不只是文件看起来更整齐。

## 通过渐进迁移控制未知行为

先识别现有行为与调用边界，为关键输入输出建立特征测试或契约测试。旧实现可能有未写进文档但用户依赖的行为，直接重写容易意外改变。不能把所有旧行为都视为正确，但需要明确哪些保持、哪些作为独立修复调整。

渐进迁移可以在旧接口外建立适配层，先替换内部一个模块，再逐步切换调用方。读路径可在条件允许时做影子比较，写路径则必须防止双写重复副作用。数据结构迁移应有兼容窗口与回退方案，避免代码回滚后无法读取新数据。

重构收益可以体现在修改范围缩小、重复规则减少、缺陷率下降或测试更容易，但不要只用删除代码行数证明成功。新的抽象若需要大量配置才能适配每个调用方，可能只是把复杂度换了位置。

## 把机制放到一条完整路径中

```flow
渐进重构
识别成本｜找到重复规则与高风险边界
记录行为｜建立契约和必要回归证据
逐步替换｜通过适配层小范围迁移
验证收尾｜确认兼容后删除旧路径
```

## 配套代码：适配层让新旧契约渐进迁移

下面代码在课内JavaScript运行区执行；需要DOM、Node或平台SDK的真实集成，应按正文的运行边界另行验证。

将旧接口字段转换到统一契约，切换实现不迫使全部消费者同时修改。

```javascript
function adaptLegacy(record) { return {id:record.user_id,name:record.user_name}; }
const legacy={user_id:'A',user_name:'Ada'};
const modern={id:'B',name:'Lin'};
console.log(adaptLegacy(legacy));
console.log([adaptLegacy(legacy),modern].map(user=>user.name));
```

适配层隔离旧格式，帮助小步替换。真实迁移应定义兼容期、测试、回退与旧路径删除计划，不能让适配层永久吞掉所有业务差异。

## 从示例走向实际使用

把大重构拆成可独立验证的小步，每步都有明确行为边界与回退点。先处理经常变化且容易出错的区域，而不是一次统一所有历史风格。

面试中说明为什么选择渐进路径、如何保证兼容和如何确认旧路径可以删除，这比只展示重构后的目录树更有说服力。
