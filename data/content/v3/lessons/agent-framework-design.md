## 先判断是不是需要 Agent
确定的校验、订单状态机和权限规则通常用普通函数更可靠。只有当下一步需要根据不确定信息进行选择时，才有必要引入模型决策。Agent 的核心可以表示为 state → policy → action → observation → state；模型负责候选行动，宿主程序负责验证、执行和记录。停止条件至少包含最终结果、步数、时间、成本与无法推进的检测。

Workflow 强调显式路径和可检查的执行边界；Agent 强调在授权行动空间内动态选择。真实系统常把两者组合：外层工作流固定认证、检索、审批和提交，中间某个节点允许模型自主研究，而不是让所有业务约束都变成提示词。
## 三种框架怎么比较
| 维度 | Microsoft Agent Framework | LangGraph | OpenAI Agents SDK |
|---|---|---|---|
| 主要组织方式 | Agent、客户端、会话、中间件和显式 workflow | 状态图、节点、边、reducer 与持久执行 | Agent、Runner、工具、handoff 与会话 |
| 适合重点研究 | 企业集成与多语言宿主边界 | 条件分支、暂停恢复、状态更新冲突 | 工具循环与专家协作的较轻封装 |
| 仍需应用承担 | 认证、数据权限、幂等、部署与评估 | 同左；checkpoint 不代替副作用去重 | 同左；guardrail 不代替资源授权 |

比较的不是抽象数量，而是团队能否解释一次失败发生在哪一层。用相同的任务、工具实现和评估集比较；否则模型和数据差异会被误归因为框架性能。
## 本地最小循环的设计
正文的浏览器实验使用确定性策略模拟两次工具行动。它不会调用模型；你应该把这套约束理解透，再接入 SDK。每个行动包含 tool_name、经验证的参数、operation_id，执行结果包含状态、结构化值和可追踪的错误。不要把工具原始堆栈、数据库口令或任意 HTML 原样塞回模型。
## 生产中的四个边界
一是身份边界：认证主体由服务端注入，不能由模型提供 tenant_id 决定。二是副作用边界：写入前审批和幂等，重放后不能重复执行。三是信息边界：工具结果是不可信数据，不能因为它被检索出来就升级成系统指令。四是运行边界：取消、超时、最大轮数、并发和费用都由宿主强制执行。
## 选型实验与迁移题
实现同一“查工单→建议分类→人工确认→创建草稿”流程，在工具超时、模型返回不存在工具、审批等待后重启、用户撤销四条路径上对比。记录业务成功率、未授权调用率、恢复正确率、P95 和每成功任务成本。框架切换前先固定这些契约，避免把整个系统绑在特定消息类上。
