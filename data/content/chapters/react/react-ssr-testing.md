## 服务端输出与客户端交互的分工
SSR 把组件渲染为 HTML，让浏览器较早获得页面结构；客户端使用匹配的初始数据进行 hydration，接上事件与状态管理。SSR 与 Server Components 不是同义词：前者描述 HTML 生成位置，后者涉及组件执行与客户端包的边界，通常依赖框架支持，不能仅凭一个文件名随意启用。

服务端不能使用 window、DOM 节点或用户真实视口。客户端首次结构如果依赖随机数、当前时间或不同数据，可能与服务器输出不一致。解决方法是共享必要初始数据、明确浏览器专属部分与加载占位，而不是直接压掉警告。
## 服务端HTML与客户端状态必须对得上

SSR先在服务器生成可见HTML，hydration在浏览器把组件与已有DOM关联并接管交互。服务器生成“当前时间A”，客户端首次生成“当前时间B”，就可能不匹配；根据window宽度分支、随机ID和不一致初始数据也会造成同类问题。需要明确哪些值来自服务器初始状态，哪些只能在客户端挂载后读取。

服务端组件与SSR不是同一个概念。SSR描述HTML如何生成与发送，服务端组件架构还涉及哪些组件代码在服务器执行、如何传递结果及与客户端组件边界协作，通常依赖具体框架支持。不要把普通函数组件放到Node里执行一次就称为完整服务端组件方案。

## 测试证据应覆盖生成、接管和真实交互

静态HTML测试可以确认初始内容存在，组件测试验证事件与状态，浏览器测试验证水合后按钮、表单与导航是否工作。只快照一份HTML无法发现监听没接上、重复请求或焦点丢失。慢网络与脚本延迟也应测试，确保服务器内容可读且交互准备状态明确。

每个SSR请求应隔离用户状态，序列化只发送客户端所需且允许公开的数据。缓存响应时考虑用户与租户范围，不能因为同一路径就给所有人返回同一份私有HTML。初始状态安全注入、CSP与接口授权仍是独立边界。

发布时同时观察服务端错误、客户端水合告警和用户性能。SSR可能改善首屏内容出现，却增加服务器计算、依赖等待与缓存复杂度；选择应基于页面需求与测量，不能把它当所有项目默认更高级的版本。

## 从最小 hydration 入口认识契约
```jsx
// 客户端：服务端已在 #root 内输出同一 App 的 HTML。
import {hydrateRoot} from 'react-dom/client';
import App from './App.jsx';
const initialData=JSON.parse(document.querySelector('#initial-data').textContent);
hydrateRoot(document.querySelector('#root'), <App data={initialData} />);
```
服务端必须安全序列化 initial-data，避免把用户文本当 script 或 HTML 语法。例子只是客户端入口，真实项目还需路由、构建清单、流式响应和错误处理，优先采用成熟框架。用户专属数据不应进入全局公共缓存。
## 错误边界接住什么
错误边界用于处理后代渲染等受支持生命周期中的异常，展示替代界面并报告诊断信息。事件处理函数、独立异步回调和普通网络失败仍需各自的错误处理，不能因外层有错误边界就移除 try/catch 和错误状态。
```flow
渲染到交互的验证链
服务端请求｜隔离身份、数据与应用实例
输出 HTML｜正确内容、安全序列化
浏览器激活｜初始结构匹配并接上事件
操作与异步结果｜正常状态与错误状态可见
恢复｜边界重试、路由刷新或用户纠正输入
```
## 组件测试与端到端测试如何配合
组件测试通过角色和可见文本寻找元素，模拟真实输入、点击和提交，断言用户看到的结果。不要把所有测试都写成检查内部 state 或函数调用次数，否则实现小改就让测试失效，却未必发现行为错误。

端到端测试再覆盖登录、真实 API 契约、深层路径刷新、跨页面状态和慢网络。SSR 需要额外验证服务器 HTML、禁用 JavaScript 的基本内容与 hydration 后交互；并发不同用户请求时检查无数据串用。开发模式的额外渲染检查是发现问题的工具，不应作为线上调用次数的精确模型。
