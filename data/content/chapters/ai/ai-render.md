## 从具体问题认识流式 UI、长对话与安全 Markdown

流式 UI 在内容尚未完成时持续展示变化。它需要兼顾反馈及时、主线程成本、滚动位置与内容安全。每收到一个字符就重新解析整段 Markdown，短回答可能正常，长回答却可能造成明显卡顿。

流式内容还经常处于半成品状态，例如代码围栏未闭合、链接只到一半。界面需要能平稳显示中间态，不能假设每个增量都是完整文档。

## 增量缓冲与稳定阅读位置

接收层先把增量加入缓冲，按适当节奏批量提交到响应式状态，减少渲染次数。最终完成或取消时刷新剩余缓冲，避免最后几个字符丢失。对长对话可以分块渲染或虚拟化，但要保留复制、选择与可访问性。

自动滚动应尊重用户意图：用户已在底部时跟随新内容，用户向上阅读时不要强制拉回，提供新内容提示与回到底部按钮。布局变化、代码块和图片加载可能改变高度，需要稳定锚点，而不是每帧无条件 scrollTo。

模型输出是不可信内容。Markdown 渲染后应使用可靠清理与安全链接策略，禁止危险 HTML、脚本与协议。代码块展示与代码执行必须分开，用户看到一段代码不代表同意运行。引用和工具状态使用结构化组件，比把所有信息混进 Markdown 更容易验证。

## 把机制放到一条完整路径中

```flow
流式界面
接收增量｜按任务身份进入缓冲
批量提交｜控制响应式与解析频率
安全渲染｜处理半成品Markdown和危险内容
保持阅读｜尊重滚动意图并刷新最终残余
```

## 配套代码：按批提交而不是每 token 渲染

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

用固定批量模拟调度边界，不构造 DOM，也不实现 Markdown 渲染。

```javascript
let buffer='',text='',commits=0;
function flush(){if(buffer){text+=buffer;buffer='';commits++;}}
for(const [index,token] of ['你','好','，','世','界'].entries()) {
  buffer+=token;if((index+1)%2===0)flush();
}
flush();
console.log(text);
console.log(commits);
```

五个 token 只提交三次且最终缓冲被刷新，避免末尾丢字。真实 UI 更适合按帧/时间预算提交，同时处理自动跟随、安全清洗与长列表更新范围。

## 从示例走向实际使用

用长代码块、表格、未闭合围栏和恶意链接测试流式渲染，检查 PC、手机与 iPad 上的滚动和复制。阶段状态应来自后端事件，而不是固定动画假装进度。

课内批量 flush 演示减少提交次数，生产间隔应根据实际响应与渲染成本测量，不必为每个 token 强制更新组件。
