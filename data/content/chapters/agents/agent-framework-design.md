## 从具体问题认识Agent Framework 选型

Agent Framework 帮助组织模型、工具、状态和执行循环，但不同框架把不同概念放在中心。有的围绕 Agent 与 Runner，有的围绕状态图，有的同时提供 Agent 和显式工作流。选型首先要知道应用需要哪一种控制方式。

如果任务永远按“读取、校验、写入”执行，普通程序可能更简单；如果中间需要根据观察选择工具，可以把这部分交给 Agent，而将交易提交等关键路径保持确定性。

## 从控制权和恢复边界理解框架

循环决定模型何时再次被调用，工作流决定节点之间怎样推进，宿主负责认证、资源预算与业务提交。框架可以提供机制，但不会自动知道某个订单属于谁，也不会替产品决定失败后向用户收多少额度。

比较框架时看状态由谁拥有、并发更新怎样合并、暂停后怎样恢复、工具怎样被限制，以及事件能否映射到前端任务状态。接口短并不等于整体系统简单，某些省略的部分可能只是转移到应用代码。

用相同任务、模型、工具和评估集做小型验证，包含正常路径、人工审批、服务重启与工具重复执行。迁移成本还包括状态格式、历史记录和观测数据，而不只是改几个 import。

## 先判断是不是需要 Agent

确定的校验、订单状态机和权限规则通常用普通函数更可靠。只有当下一步需要根据不确定信息进行选择时，才有必要引入模型决策。Agent 的核心可以表示为 state → policy → action → observation → state；模型负责候选行动，宿主程序负责验证、执行和记录。停止条件至少包含最终结果、步数、时间、成本与无法推进的检测。

Workflow 强调显式路径和可检查的执行边界；Agent 强调在授权行动空间内动态选择。真实系统常把两者组合：外层工作流固定认证、检索、审批和提交，中间某个节点允许模型自主研究，而不是让所有业务约束都变成提示词。

## 三种框架怎么比较

| 维度 | Microsoft Agent Framework | LangGraph | OpenAI Agents SDK |
|---|---|---|---|
| 主要组织方式 | Agent、客户端、会话、中间件和显式 workflow | 状态图、节点、边、reducer 与持久执行 | Agent、Runner、工具、handoff 与会话 |
| 适合重点研究 | 企业集成与多语言宿主边界 | 条件分支、暂停恢复、状态更新冲突 | 工具循环与专家协作的较轻封装 |
| 仍需应用承担 | 认证、数据权限、幂等、部署与评估 | 同左；checkpoint 不代替副作用去重 | 同左；guardrail 不代替资源授权 |

比较的不是抽象数量，而是团队能否解释一次失败发生在哪一层。用相同的任务、工具实现和评估集比较；否则模型和数据差异会被误归因为框架性能。

## 本地最小循环的设计

正文的浏览器实验使用确定性策略模拟两次工具行动。它不会调用模型；你应该把这套约束理解透，再接入 SDK。每个行动包含 tool_name、经验证的参数、operation_id，执行结果包含状态、结构化值和可追踪的错误。不要把工具原始堆栈、数据库口令或任意 HTML 原样塞回模型。

## 生产中的四个边界

一是身份边界：认证主体由服务端注入，不能由模型提供 tenant_id 决定。二是副作用边界：写入前审批和幂等，重放后不能重复执行。三是信息边界：工具结果是不可信数据，不能因为它被检索出来就升级成系统指令。四是运行边界：取消、超时、最大轮数、并发和费用都由宿主强制执行。

## 选型实验与迁移题

实现同一“查工单→建议分类→人工确认→创建草稿”流程，在工具超时、模型返回不存在工具、审批等待后重启、用户撤销四条路径上对比。记录业务成功率、未授权调用率、恢复正确率、P95 和每成功任务成本。框架切换前先固定这些契约，避免把整个系统绑在特定消息类上。

## 把机制放到一条完整路径中

```flow
框架选型
描述任务｜区分固定流程与动态决策
明确责任｜模型框架宿主和业务各管什么
验证边界｜状态审批恢复与副作用幂等
同题比较｜用质量成本和维护证据作选择
```

## 配套代码：Agent Framework 选型：循环、工作流与宿主责任

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

浏览器内的确定性实验，用于验证关键不变量。真实服务/SDK 完整示例见正文；不会连接模型或外部服务。

```javascript
const actions = [
  { tool: "lookup", args: { id: 7 } },
  { tool: "finish", args: { text: "已核对" } },
];
let steps = 0;
const events = [];
for (const action of actions) {
  if (++steps > 3) throw Error("step limit");
  if (!["lookup", "finish"].includes(action.tool)) throw Error("unknown tool");
  events.push(action.tool);
  if (action.tool === "finish") break;
}
console.log(events);
console.log({ steps, stopped: events.at(-1) === "finish" });
```

策略是固定数组，目的是暴露执行器的边界。把动作改为不存在的工具，会在执行前被拒绝；去掉 finish 后需由预算或无法推进检测终止，不能无限等待模型“自觉停下”。

## 从示例走向实际使用

框架比较表用于梳理抽象边界，不作为品牌排名。先写业务不变量，再验证各框架能否以清楚、可测试的方式表达。

课内最小循环没有模型依赖，帮助看清停止和工具白名单；真实框架接入后仍应保留这些宿主约束。
