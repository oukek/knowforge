## 从具体问题认识强缓存、协商缓存与版本发布

HTTP缓存保存响应，使后续请求可以复用已有内容。首先要回答能否保存、能保存多久、何时必须向服务器确认，以及不同用户或请求头是否应命中同一份响应。浏览器私有缓存与CDN共享缓存面对的身份范围不同，不能使用同一套“全部缓存一天”策略。

新鲜度表示当前缓存是否仍可按规则直接使用，验证器则帮助询问内容是否变化。缓存过期不等于立即删除，只是后续使用通常需要验证或重新获取。

## Cache-Control、验证器与发布版本

max-age规定新鲜期，no-cache允许保存但使用前需要按规则验证，no-store要求不要存储该响应；三者不是程度不同的同义词。private限制共享缓存，Vary让缓存区分影响表示的请求头；遗漏语言、压缩或身份维度可能返回错误内容。

ETag标识某份表示的版本，客户端用If-None-Match发送条件请求；未变化时服务器可返回304，客户端复用已有正文。Last-Modified与If-Modified-Since使用修改时间，精度和可靠性取决于资源生成方式。304不是一份新的空资源，也不能凭一个状态码忽略缓存元数据更新。

静态资源适合内容哈希文件名与较长缓存，因为内容变了URL也变；HTML入口需要较及时更新，以引用新资源。发布时保留一段旧资源，避免已打开页面的懒加载引用被删除。更新入口、上传资源、CDN刷新与回滚之间有顺序关系，缓存策略也是发布协议的一部分。

## 把机制放到一条完整路径中

```flow
缓存响应的决策
确定是否允许存储｜敏感性与共享范围
检查新鲜度与请求条件｜可直接使用或需要验证
发送验证器｜ETag或修改时间参与协商
复用或替换正文｜同时更新元数据与版本关联
```

## 配套代码：新鲜、验证与不存储的策略模型

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

更改 cache-control 与资源年龄，观察决策。未模拟真实 HTTP 缓存完整规范。

```javascript
function decision({noStore = false, noCache = false, age, maxAge}) {
  if (noStore) return '不存储';
  if (noCache || age >= maxAge) return '向服务端验证';
  return '复用新鲜响应';
}
console.log(decision({age: 10, maxAge: 60}));
console.log(decision({noCache: true, age: 10, maxAge: 60}));
console.log(decision({noStore: true, age: 0, maxAge: 60}));
```

no-cache 允许存储但要求验证，no-store 才是不存储。模型仅覆盖基本决策，没有实现 Vary、共享缓存、Age 计算或启发式新鲜期。

## 从示例走向实际使用

为公开静态文件、个性化API、登录页和敏感下载分别设置策略。用开发者工具验证真实请求头、响应头、Age与命中情况，强制刷新和禁用缓存模式不能代表普通用户路径。

测试新旧页面混用、回滚、条件请求及多语言表示。缓存命中改善速度，但用户身份、权限撤销和数据新鲜性要求仍须满足，不能因性能指标漂亮就允许跨用户共享响应。
