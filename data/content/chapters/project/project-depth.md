## 从具体问题认识追问树与可验证个人贡献

面试追问通常沿着一个结论继续问依据、机制、边界和验证。例如你说“使用缓存提高性能”，后续会问缓存什么、键如何设计、何时失效、失败时怎样，以及数据说明收益有多大。深度来自能够连接这些问题，而不是准备更多术语。

个人贡献也需要可识别的边界。你可以参与大型系统的一小部分，但应能讲清自己负责的决策、实现与验证，而不是把系统规模当成个人能力的替代证据。

## 为核心决策建立追问树

选择项目中三到五个关键决策，每个决策展开为什么需要、机制怎样工作、替代方案是什么、最坏情况如何以及如何验证。以幂等接口为例，不能停在“用了 Redis 锁”，还要说明幂等作用域、参数冲突、锁过期与持久结果的关系。

把自己知道的事实与推测分开。没有负责数据库内核，也可以说明观察到的执行计划与查询改造；不了解某个底层细节时，先给出已知边界，再说明会如何验证。用确定语气猜测实现通常比承认范围更容易暴露问题。

证据可以是设计记录、测试用例、故障时间线或性能数据，不需要公开敏感源码。解释自己的判断如何改变结果，以及与同事如何分工，能让贡献更具体。团队协作不削弱个人能力，模糊归属才会削弱可信度。

## 把机制放到一条完整路径中

```flow
项目追问树
选择决策｜聚焦自己真正参与的关键点
展开机制｜解释数据状态与执行过程
检验边界｜讨论失败替代方案和限制
连接证据｜用测试记录与结果说明贡献
```

## 配套代码：把技术主张拆成可验证追问

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

按实现、边界与证据组织追问树，不自动判断候选人是否掌握。

```javascript
const claim={name:'并发池',checks:{mechanism:true,implementation:true,boundary:false,evidence:false}};
console.log(Object.entries(claim.checks).filter(([,ready])=>!ready).map(([key])=>key));
console.log(Object.values(claim.checks).filter(Boolean).length);
```

实现过不等于边界和证据齐全，清单用于定位准备缺口。布尔值来自自己的核验，不是 AI 或程序根据几个关键词评定能力。

## 从示例走向实际使用

模拟面试时让自己对每个重要名词连续追问三层，直到能给出例子或指出尚不理解的地方。把不会的问题回到课程中补机制，再用新例子复述。

准备失败与调整案例同样重要。一个经过证据纠正的方案，往往比声称第一次就完美更能展示工程判断。
