## 从具体问题认识HTTP/1.1、HTTP/2 与 HTTP/3

HTTP定义请求方法、状态码、头与表示等应用语义。HTTP/1.1、HTTP/2与HTTP/3主要改变消息如何在连接上编码、并发和传输，GET和POST不会因为版本升级就变成另一套业务含义。性能比较应把协议、网络丢包、资源形状和服务实现一起考虑。

“多路复用”表示多个流共享连接，不代表带宽无限，也不保证某个大响应不会争用资源。连接数、流数与请求数是三个不同量。

## 从顺序消息到多流传输

HTTP/1.1支持持久连接，但常见浏览器请求并发往往依赖多条连接，队头等待与连接建立成本会影响资源瀑布。HTTP/2把消息分成带流标识的帧，在同一连接交错传输，并通过头压缩减少重复元数据；流量控制和优先级机制仍需要实现配合。

HTTP/2通常基于TCP，某段字节丢失时TCP有序交付可能阻挡连接上其它流的数据继续交给上层。HTTP/3建立在QUIC上，提供不同流之间的传输独立性并整合安全握手相关能力，减少这类跨流传输队头阻塞，但每条流内部仍有顺序与重传需求，拥塞与链路瓶颈仍存在。

资源合并、域名分片等曾经适应旧协议的优化，换到多路复用环境后可能增加不必要成本。是否拆包应根据缓存复用、首屏关键路径和实际请求开销决定，不能把“HTTP/2不怕请求多”当成无限碎片化的理由。

## 把机制放到一条完整路径中

```flow
HTTP语义与传输分层
应用形成方法与表示｜业务契约独立于版本
消息编码成协议单元｜文本消息或带流标识的帧
底层连接传输｜TCP与QUIC有不同阻塞特征
重组并交给应用｜成功收到响应仍需业务校验
```

## 配套代码：传输层队头阻塞的简化模型

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

比较一个流丢包时其他流能否继续交付；这不是 HTTP/QUIC 协议实现。

```javascript
function deliver(protocol, lost) {
  const streams = ['A', 'B', 'C'];
  if (protocol === 'h2' && lost) return [];
  return streams.filter(name => name !== lost);
}
console.log(deliver('h2', 'B'));
console.log(deliver('h3', 'B'));
```

模型把 H2 的 TCP 字节流阻塞与 QUIC 的按流交付区别凸显出来；真实网络仍有拥塞、优先级和应用依赖，不能据此宣称 H3 在任何网络都更快。

## 从示例走向实际使用

通过开发者工具确认实际协商协议，不能仅凭服务器支持就认为用户都在使用。代理、CDN和源站之间也可能使用不同版本，端到端瓶颈不只在浏览器一段。

比较冷连接与热连接、不同丢包和延迟下的页面指标。协议升级不能替代压缩资源、减少无用脚本和优化服务器处理，TTFB或主线程长任务仍需各自定位。
