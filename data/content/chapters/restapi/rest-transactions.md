## 从具体问题认识事务、业务不变量与 Outbox

事务让一组相关数据库变化作为一个整体提交或回滚。业务不变量是无论并发怎样发生都应成立的规则，例如余额不能因同一操作重复扣减，订单与待发送通知必须有一致关联。先定义不变量，才能判断事务应包住哪些操作。

一次 HTTP 请求不是天然一个数据库事务，也不是所有外部网络调用都适合放在数据库事务里等待。事务范围越长，锁与连接占用通常越难控制。

## 本地原子性与跨系统一致性

相关数据库写入应在同一事务内完成，并使用条件更新、唯一索引或必要锁处理竞争。先在事务外检查库存，再无条件扣减，仍可能被并发请求同时通过。事务隔离级别也不能代替正确业务条件。

数据库与消息服务之间没有普通本地事务的原子保证。Outbox 把待发事件与业务行一起保存，再由独立发送器投递。发送可能重复，因此消费者需要幂等；它提供可恢复的交付路径，不是自动的跨系统恰好一次执行。

外部操作失败需要补偿或状态机，例如支付已成功但本地确认暂时失败，应通过查询与对账恢复，而不是简单回滚内存变量。补偿也可能失败，必须记录状态与重试，不应把它描述成反向执行就必然恢复原状。

## 把机制放到一条完整路径中

```flow
业务一致性
定义不变量｜列出必须共同成立的事实
本地事务｜原子保存相关业务与事件
跨系统推进｜异步投递并幂等消费
失败恢复｜依靠持久状态查询重试或补偿
```

## 配套代码：事务、业务不变量与 Outbox：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

transaction={'orders':[],'outbox':[]}
transaction['orders'].append({'id':'o1'})
transaction['outbox'].append({'event_id':'e1','order_id':'o1'})
show(transaction)
```

字典仅展示业务记录与事件记录应共享提交边界，不提供真实事务或故障原子性。实现应在数据库中一起提交，再由可靠投递器处理外部发送；消费者仍需面对重复和乱序。

## 从示例走向实际使用

围绕一个写操作列出每个崩溃断点，说明哪些数据已提交、哪些副作用可能发生、恢复依据是什么。优先保持事务短且边界清楚。

课内同时追加订单与 outbox 只是数据关系示意，真实原子性来自数据库事务。普通 ID 与索引即可表达关联，业务层负责校验与生命周期。
