## 从具体问题认识AI 应用是什么

AI 应用把模型能力放进真实业务流程。用户输入之后，系统还要认证、校验任务范围、取得必要数据、调用模型、验证结果、保存记录并展示状态。模型只是其中一个组件，整条链路才决定用户是否真正完成任务。

以主观题评阅为例，后端应知道题目、知识点、参考标准与用户答案，不能把输入框直接转发成无限制聊天接口。

## 输入契约到业务结果的分层

前端负责收集答案、显示运行阶段与结果，后端负责权限、资源预算、题目关联和模型调用。服务商密钥留在后端，用户只能提交业务允许的字段，不能任意指定系统提示、上游地址或工具。输入长度与任务频率也要受控。

模型输出先作为候选评阅结果，经过结构与内容检查后再进入业务记录。结果应包含可解释依据，例如哪些要点满足、哪里存在错误和怎样改进，而不只给一个分数。若输出截断或结构不合法，应记录失败类型，不能把半段文本当成功评阅。

任务执行可能较长，因此状态、取消、重试和历史关联需要持久化。每次调用记录模型与提示版本、使用量、耗时和尝试链，便于核对与评估。记录内容要遵守访问与保留策略，不能为了可观测性向所有管理员暴露所有敏感输入。

## AI 应用不等于调用一次模型

**AI 应用是围绕用户目标设计的一整条流程。** 例如订单助手收到“订单到哪里了”，先确认用户身份，取得订单号，检查访问权限，再查订单服务，最后把可公开的状态组织成回答。

这里模型可能帮助理解问题和表达结果，但订单数据库仍是状态来源，后端代码负责权限和真实查询。一个文本回答流畅不代表订单查对了；评估还需要检查查询结果、隐私、延迟和异常时是否能安全退出。

例如订单服务超时时，助手应告知查询失败并提供重试，而不是猜测物流已经送达。

AI 应用用模型能力解决用户问题，可能做分类、抽取、知识问答、内容生成或行动辅助。一次模型请求只是链路中的一段。用户真正关心资料是否找到、草稿是否正确、订单是否完成，而不是服务是否返回了一段文字。

典型链路是输入与认证 → 任务契约 → 事实获取 → 模型推理 → 结构/业务校验 → 展示或执行 → 记录与评估。环节可以裁剪组合，但权限和业务正确性不能因为接了模型就消失。

## 前端与后端各负责什么

前端处理输入、任务进度、流式呈现、取消、确认和错误解释；后端保护凭据、身份与资源权限，安排模型和工具调用，管理预算、持久状态及审计。模型负责候选内容或行动选择，业务服务才提交事实变更。

| 层 | 关键契约 | 常见故障 |
|---|---|---|
| UI | 草稿、生成中、待确认、已完成 | 半成品当成功 |
| API 网关 | 认证、配额、请求身份 | 密钥暴露或串账号 |
| 模型适配 | 输入与归一化结果 | 拒绝/截断被抹平 |
| 业务执行 | 授权、幂等、版本 | 重试重复写入 |

API Key 不应发给网页用户，跨域部署还要正确处理来源、会话与运行资源路径。

## 同步与异步任务如何取舍

短文本抽取可同步返回完整结果；长视频解析或多步 Agent 适合持久任务 ID、事件流和状态查询。SSE 解决增量传输，不自动保存任务；后台队列解决排队执行，也不自动保证业务效果恰好一次。

把连接取消、运行取消和业务撤销分开。客户端断开可能只是不再接收内容，远端工具仍已提交；恢复时要按操作身份查账，不能盲目再跑全部步骤。

## 最小可交付项目应该证明什么

先选一个边界清楚的任务，如把工单转成待审核草稿。建立正确、缺失、恶意和工具失败样本，测任务成功、人工审核与返工、延迟和每成功任务成本。用 fake 模型开发确定性契约，接真实模型后再做质量评估。

交付还包括配置、部署、版本、观察与回退。没有真实业务验收时如实称为原型，不用一次演示成功推断生产稳定性；FDE 强调把这些技术环节接到客户流程和可测价值。

## 把机制放到一条完整路径中

```flow
AI 应用链路
业务入口｜认证校验题目关联与预算
准备上下文｜获取授权资料和任务规则
模型执行｜记录阶段尝试与使用量
结果落地｜验证保存并向用户解释反馈
```

## 配套代码：AI 应用是什么：从输入到业务结果的完整链路

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。



```javascript
const transitions = {
  draft: { start: "running" },
  running: { review: "needs_review", fail: "failed", cancel: "cancelled" },
  needs_review: { commit: "completed", cancel: "cancelled" },
};
function next(state, event) {
  const target = transitions[state]?.[event];
  if (!target) throw Error("invalid transition");
  return target;
}
let state = "draft";
for (const event of ["start", "review", "commit"]) state = next(state, event);
console.log(state);
try {
  next("running", "socket_closed");
} catch (e) {
  console.log(e.message);
}
```

显式状态机区分传输事件和业务完成。真实 commit 还需服务端确认、权限、幂等与版本校验。

## 从示例走向实际使用

先实现一条窄任务闭环，如固定题目的评阅，再扩展模拟面试与变式出题。每个功能有独立输入输出契约和评估集，避免共用一个模糊万能提示。

验收时检查正常完成、超时、取消、断网恢复和重复提交。一个成功模型响应并不代表应用在这些路径上已经可靠。
