## 从具体问题认识线上故障排查

线上排障是在信息不完整、业务仍受影响的情况下，逐步缩小问题范围。第一目标通常是恢复可用性并控制损失，根因分析随后继续。重启有时能止损，但如果没有保留证据，也可能把最有价值的现场一起清掉。

例如用户说页面一直加载，原因可能是前端脚本异常、网关等待、数据库锁或上游服务超时。症状位于界面，不代表根因一定在前端；需要按请求路径分段验证。

## 用可证伪的假设组织调查

先确认影响对象、开始时间、错误比例和最近变化，给事件建立统一时间线。指标说明规模与趋势，日志提供离散事件细节，链路追踪连接一次请求在各服务中的耗时。三类证据相互补充，不能只搜到一条错误日志就认定它代表全部用户。

假设必须能被证据支持或否定。例如“数据库连接池排队导致慢请求”，应预测池等待时间上升而实际 SQL 时间未必变长；若只看到 SQL 执行变慢，需调整假设。每次验证尽量只改变一个关键因素，避免同时改配置、重启和回滚后无法知道何者有效。

止损操作也有风险。回滚可能不兼容新写入的数据，扩容可能进一步压垮共享数据库，重试可能放大上游过载。应先明确操作针对哪段瓶颈及其可逆性，并保留观察窗口。恢复不仅看错误率下降，还要检查排队积压、数据一致性和关键业务成功率。

## 先确认影响并控制损失

先回答哪些用户/租户、什么操作、何时开始、错误率和延迟如何变化，建立事件时间线与负责人。用户侧探针确认真实失败，再决定回滚、降级、限流或暂停高风险写入。已知故障的止损优先于在生产长时间追完美根因，但要保存关键日志、版本、指标和请求 ID，避免重启抹掉证据。

## 从症状到链路拆分

延迟、流量、错误和饱和是常用观察维度。按客户端/CDN/网关/应用/连接池/数据库/外部模型拆耗时，区分排队、连接、首字与执行。502 常表明代理无法拿到有效上游响应，不等同数据库返回 502；进程退出、监听地址、反向代理配置、上游超时或依赖启动失败都需证据验证。

## 日志、指标、链路各做什么

指标判断范围和变化，trace 定位一次请求跨组件的耗时和错误，结构化日志解释具体分支与异常。通过 traceId/requestId、部署版本、租户和端点关联，日志脱敏且控制基数与采样。只搜索 error 会漏掉排队、超时取消和业务错误码；只看平均 CPU 也会漏掉单实例事件循环阻塞或连接池耗尽。

## 用假设驱动排查

列候选原因和能区分它们的观测：最近发布后全租户失败看变更与启动；只有一租户慢看数据量、热点、配额；Node CPU 不高但请求排队看下游/连接池；CPU 高且事件循环延迟升高看同步计算与 GC。每次做最小、可回退的实验，记录结果再更新假设，避免同时改十项导致无法归因。

数据库看慢 SQL、实际计划、锁等待、长事务与连接；模型看供应商错误分类、限额、TTFT、断流；容器/PM2 看进程退出、内存与有效环境配置。任何命令都要针对具体进程与时间窗，不盲目输出所有环境变量泄露密钥。

## 验证恢复与复盘

止损后用同类请求和分租户指标确认恢复，观察错误、P95、队列与积压消退，防“服务起来了”但后台仍堆积。复盘给触发、根因/放大因素、为何监控没拦住、长期修复与验证期限；不把个人失误当唯一根因。回归测试复现实际交错或资源条件，修根因而非只加超时。

## 可运行观测模型

示例分解两条请求的耗时，展示总延迟相近也可能分别由队列和上游导致。真实追踪应统一时钟/单调计时语义，注意跨服务墙钟偏移。面试讲一个排查过程要说明排除了哪些假设以及凭什么，不能只背工具列表。

## 把机制放到一条完整路径中

```flow
证据驱动排障
确认影响｜建立时间线与业务范围
控制损失｜选择针对瓶颈的恢复动作
验证假设｜用指标日志与链路排除原因
确认恢复｜检查积压一致性并形成改进
```

## 从示例走向实际使用

把常见故障按入口、应用、数据库、依赖与客户端建立检查路径，记录每一步需要的证据和权限。复盘产物应包括触发条件、传播机制、恢复动作和可验证改进，而不只是“加强监控”。

面试回答可以用一次具体时间线解释如何缩小范围；没有亲历的故障应明确是演练方案，不编造线上规模与恢复数据。
