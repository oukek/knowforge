## 从具体问题认识证据契约

证据契约规定系统凭什么可以给出某个主张。它不只要求答案末尾有链接，还要求来源存在、允许访问、版本有效，并且具体内容确实支持结论。引用是进入验证的入口，不是验证完成的标记。

例如“该订单可全额退款”需要订单状态、退款政策和已退金额共同支持，单独一份通用政策通常不足以确认这笔订单的操作。

## 资格验证与语义支持分开

资格层检查证据 ID 是否来自本次受控集合、租户和权限是否匹配、版本是否仍有效。这类条件可由程序确定性检查，放在语义评审之前，防止外部或过期来源被包装成合法依据。

语义层把回答拆成主张，判断每个主张是完整支持、部分支持、矛盾还是证据不足。支持关系可能依赖多段信息，应保留条件与推导步骤；不能把几个相关段落简单拼接就认为覆盖了完整结论。

资料冲突时先依据业务定义的权威性与生效范围处理；规则不能解决时呈现冲突或请求确认。程序能证明 ID 合法，却通常不能单独证明自然语言推断正确，因此两层结果需要分别记录。

## 一个可点击链接只证明很少的事

答案引用真实文档，仍可能把“仅限企业版”说成“所有用户都支持”。引用正确性至少分为：引用 ID 是否存在，片段是否来自该版本，当前用户能否读取，证据是否仍有效，片段是否支持对应主张。前四项可以大量使用确定性检查，最后一项通常还需要规则、人工或受校验的语义评审。

不要把向量相似度视为支持度。文档谈到同一主题，不代表证明答案里的金额、日期、因果或例外条件。尤其是否定词、条件范围和跨文档推断，容易在概括中丢失。

## 为主张而设计数据结构

用稳定 claim_id 连接一段具体主张和一个或多个 evidence_id。证据至少包含 source_id、version、片段定位和获取时间；授权上下文由宿主校验，不能让模型提交“我有权限”字段来豁免检查。原文锚点可以是页码加段落 ID，或版本化文本范围，避免只留会随页面改变的字符偏移。

```js
const claim = { id: 'c1', text: '企业版可保留日志 90 天', evidenceIds: ['policy:7:p3'] };
const evidence = { id: 'policy:7:p3', version: 7, tenant: 'a', validUntil: 100 };
```

结构化输出使引用关系容易解析，不会自动使主张真实。先检查结构，再逐条验证来源与语义，失败时应撤下该主张、补检索或明确证据不足。

## 验证链应如何排序

先拒绝不存在的 ID，再验证租户和资源可见性，再比较版本及有效期，最后进行支持检查。不要在拒绝权限前把原文送给外部评审模型。服务返回的拒绝信息避免暴露其他租户文档是否存在，可在内部日志保存受限诊断代码。

| 检查 | 能捕获的错误 | 仍需补充 |
|---|---|---|
| ID 与版本 | 编造引用、旧链接 | 正文是否支持结论 |
| ACL 与时效 | 跨租户、过期政策 | 更新传播是否及时 |
| 语义支持 | 条件被删、数字误述 | 评审本身的误判与漏判 |

引用同时经过多层校验才适合展示，不能把“通过 JSON Schema”当成引用验收。

## 多证据与冲突怎么表达

如果一条主张需要“订单购买日期”和“政策生效日期”共同支持，应记录两个来源和推导规则。不能只引用政策而省略订单事实。若两份政策冲突，先按明确的适用范围和生效规则选择；无法判定时保留冲突并询问，而非让模型自行挑语气更确定的一份。

对计算结果，最好让确定性函数输出输入引用和计算式，例如 `refund = paid - used`，同时保留币种和舍入规则。模型负责解释，数值和适用条件可由程序再次核验。

## 验收与面试表达

使用“引用存在但不支持”“部分支持”“数值支持但条件不支持”“正确内容但无权限”“两个来源相互冲突”的样本集。分别计算引用有效率、主张支持率、证据覆盖率和拒答质量。答案越长主张越多，应检查是否通过添加无关引用刷高平均分。

生产记录模型输出、证据版本和校验决定，文档撤回后能定位受影响的缓存答案。保留来源指针用于审计，不代表可以无限期保留敏感原文；保存策略也应服从访问和删除规则。

## 把机制放到一条完整路径中

```flow
主张证据契约
提出主张｜拆分事实范围与操作前提
资格检查｜核对身份权限时间与版本
支持检查｜判断完整部分矛盾或缺失
输出决定｜回答限定范围或说明证据不足
```

## 配套代码：证据契约：引用有效不等于主张被支持

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。



```javascript
function eligible(claim, evidence, tenant, now, currentVersions) {
  return (
    claim.evidenceIds.length > 0 &&
    claim.evidenceIds.every((id) => {
      const e = evidence[id];
      return (
        e &&
        e.tenant === tenant &&
        now < e.validUntil &&
        e.version === currentVersions[e.sourceId]
      );
    })
  );
}
const docs = {
  good: { tenant: "a", sourceId: "p", version: 7, validUntil: 100 },
  other: { tenant: "b", sourceId: "p", version: 7, validUntil: 100 },
  old: { tenant: "a", sourceId: "p", version: 6, validUntil: 100 },
};
const check = (ids) =>
  Boolean(eligible({ evidenceIds: ids }, docs, "a", 50, { p: 7 }));
console.log(["good", "other", "old", "missing"].map((id) => check([id])));
console.log(check([]));
console.log("引用资格不等于语义支持");
```

检查租户、版本、时效和非空引用。把主张改成相反含义并不会改变此函数结果，说明需要额外的语义支持验证。

## 从示例走向实际使用

测试“真实链接但结论扩大范围”“旧版本仍可打开”“跨租户同名政策”和“两个来源共同支持”等样本。展示证据位置，让用户可以复核，而不是只显示绿色可信标记。

课内 eligible 只计算引用资格，函数名刻意不叫 truthful；业务正确性仍需要内容核对与必要的人审。
