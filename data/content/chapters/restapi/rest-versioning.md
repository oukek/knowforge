## 从具体问题认识版本演进、兼容性与弃用策略

API 演进要同时服务新旧客户端。服务端上线通常比所有用户更新客户端更快，因此兼容期是常态。版本号只是标记，真正兼容性取决于字段、类型、枚举、错误与业务语义是否仍符合旧客户端预期。

新增一个可选字段通常较容易兼容，但新增枚举值也可能让客户端 switch 没有分支而崩溃；把金额单位从元改成分，即使字段仍是 number，也属于严重语义变化。

## 扩展、迁移与删除的顺序

先定义消费者对未知字段和未知枚举的处理策略。响应可扩展并不表示请求可以接受任意字段；服务端仍应严格控制可写内容。必填字段增加、类型变化、默认值变化与排序改变，都需要评估已有调用者。

渐进发布常先让服务端同时支持新旧格式，再发布新客户端，观察旧用量下降后才移除旧能力。数据库也可先扩展结构、迁移数据、切换读写，再清理旧列。直接同时删除旧接口与发布新前端，会让缓存页面和旧移动端立刻失效。

版本可以放在路径、媒体类型或其他明确协议中，选择取决于工具与业务，不能靠隐藏行为变化代替版本策略。弃用应有文档、使用统计、迁移说明和合理窗口；没有消费者观测时，很难判断旧版本是否真的无人使用。

## 把机制放到一条完整路径中

```flow
兼容演进
评估变化｜检查类型枚举语义与消费者
先扩展｜服务端兼容新旧契约
逐步迁移｜发布客户端并观察旧用量
受控删除｜完成验证后移除旧能力
```

## 配套代码：版本演进、兼容性与弃用策略：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

known={'queued':'等待','running':'处理中','done':'完成'}
show([known.get(status,'未知状态，请刷新') for status in ['queued','paused']])
```

未知枚举分支避免程序直接崩溃，但业务仍需决定能否安全继续操作。对支付、权限等高影响状态，应保守禁止不确定操作并提示刷新，而不是用任意默认成功值吞掉差异。

## 从示例走向实际使用

为一次字段变更列出旧前端配新后端、新前端配旧后端和混合缓存三种组合，明确哪些必须支持。契约测试覆盖这些组合，而不是只测同时升级后的理想状态。

课内未知状态显示兜底，避免直接崩溃；真实产品还需决定是否禁止危险操作，并向用户说明需要刷新或升级。
