## 从具体问题认识SaaS 租户隔离

租户是 SaaS 中具有独立业务与权限边界的一组用户或组织。租户隔离不仅是数据库每行增加 tenant_id，还包括身份、查询、缓存、文件、任务、日志和资源配额。任何一条路径漏掉边界，都可能让甲公司的数据进入乙公司的结果。

大客户的需求可能还包含独立资源、备份恢复、地域与运维边界，因此数据隔离强度和资源隔离强度需要分别讨论。

## 共享与独立部署之间的选择

共享表通过租户字段区分数据，成本低但要求所有访问路径可靠带上作用域；独立 schema 或数据库增加数据管理边界，也增加迁移、连接与备份管理成本；独立实例或部署进一步隔离资源，但运维成本更高。不存在只按客户人数自动决定的唯一方案。

租户身份应来自服务端验证的会话与成员关系，而不是直接相信请求体中的 tenant_id。查询、更新和删除都要校验资源归属，复合唯一约束通常需要包含租户作用域。缓存键、对象存储路径、向量检索过滤和后台任务上下文也必须遵守同一边界。

大客户可采用共享控制面与独立数据面的组织方式，但需要统一版本、配置和迁移流程。迁移时处理全量复制、增量追赶、校验、切流与回退，不能只复制几张表就更改连接地址。资源隔离还包括限流、并发与队列公平性，防止一个租户占满所有模型调用或数据库连接。

## 从威胁和业务要求定义租户

用户不等于租户，一个用户可以属于多个组织，角色随组织变化。认证回答是谁，租户授权回答可访问哪个组织及资源。租户上下文应来自验证过的成员关系或服务身份，不能信任客户端随意提交的 tenantId。数据隔离与 CPU/连接池/队列等资源隔离是两条责任线。

## 三类数据部署方案

共享库共享表成本低，但每条访问都要受租户约束；独立 schema/库有更清晰的数据管理边界，连接和迁移成本更高；独立实例或整套资源可满足高隔离与性能要求，但成本和运维复杂度最高。MySQL 不应被假定具有 PostgreSQL 式通用行级安全策略，需在服务/数据访问层及授权服务强制处理。

| 方案 | 适合起点 | 主要验证 |
| --- | --- | --- |
| pool 共享表 | 大量标准租户 | 所有路径租户条件、唯一键、资源公平 |
| bridge 独立库/schema | 中高隔离、定制运维 | 路由、连接池、批量迁移与备份 |
| silo 独立实例/栈 | 合同/地域/高负载客户 | 控制面统一、容量、成本和恢复 |
这不是按客户金额机械分级，真正依据是合规、性能、恢复目标、驻留和合同约束。

## 不只 SQL 加一个条件

主键查询、更新、删除、关联、批量导入、报表与后台任务都需隔离；联合唯一键常要包含 tenantId，外键/关联也需防跨租户绑定。缓存键、对象存储路径、搜索 ACL、消息、向量索引、导出文件和日志都要带正确租户域。ORM 全局过滤可降低遗漏但不能替代测试，原生 SQL 与管理员路径尤其容易绕过。

## 大客户如何独立且可维护

控制面维护租户到数据面资源的映射、版本、地域与策略，数据面执行隔离。迁移按快照复制、增量追平、校验、短写暂停或安全切流、观察与回退推进；路由版本和幂等跨切换保持一致。避免为每家长期维护独立代码分支，配置差异与发布策略应受统一控制面管理。

## 资源隔离与示例

给租户配置并发、数据库连接、队列、token 和费用配额，按租户观测尾延迟与饱和，防 noisy neighbor。下方内存示例强制通过 session 的租户过滤，说明即使资源 ID 正确仍不能直接返回。实际系统使用参数化 SQL 和统一仓储层，未命中时避免暴露资源是否属于别人。

## 把机制放到一条完整路径中

```flow
租户隔离链路
验证身份｜从会话确定可访问租户
限定数据｜查询缓存文件与检索统一作用域
限制资源｜并发配额和队列保持公平
独立演进｜按需求迁移数据面并验证回退
```

## 从示例走向实际使用

测试至少包含跨租户读取、修改、搜索、导出、缓存命中与异步任务恢复。使用相同资源 ID 或相同幂等键在不同租户中构造冲突，检查作用域是否完整。

可以用普通 ID、索引与事务维护业务关联，不必依赖数据库外键；但业务层必须负责存在性、归属和删除生命周期的一致处理。
