## 从具体问题认识长任务、虚拟化与主线程预算

浏览器主线程需要执行脚本、处理输入以及参与布局和绘制。一段连续执行很久的 JavaScript 会让其他工作等待，即使这段代码最终计算正确，用户也会感到按钮失灵或滚动卡住。长任务描述的就是这种持续占用主线程的工作。

把函数声明成 async 不会自动让计算移到后台。await 一个已解决 Promise 主要改变微任务调度，也不等于给浏览器一个新的渲染机会。

## 减少工作量与让出执行机会

首先检查是否有不必要工作：重复计算、渲染全部列表、连续读写布局或一次解析巨大数据。减少总工作量通常比把同样的浪费拆成更多任务更有效。虚拟列表限制可见节点，缓存纯计算结果则要正确处理输入变化。

必须执行的大量工作可以分块，在块之间通过合适任务调度让出主线程。块大小应按实际耗时与交互需求控制，不能机械地每一千项一块，因为每项成本可能不同。持续安排微任务可能仍让输入和渲染等待，必须区分微任务与新的任务机会。

Web Worker 适合可分离的 CPU 计算，但不能直接操作 DOM，通信与数据复制也有成本。主线程负责交互和最终展示，worker 返回可验证结果。取消过期任务、限制并发和避免大对象反复传输，同样是 worker 方案的一部分。

## 把机制放到一条完整路径中

```flow
主线程工作治理
测量任务｜找到持续占用的调用栈
减少工作｜避免重复计算与过量渲染
拆分或迁移｜让出任务机会或使用worker
验证交互｜同时观察响应时间与总成本
```

## 配套代码：微任务并不等于让出一个任务

下面代码在课内JavaScript运行区执行；需要DOM、Node或平台SDK的真实集成，应按正文的运行边界另行验证。

同步计算切为微任务仍可能先于定时器和渲染机会全部完成。

```javascript
console.log('同步');
setTimeout(()=>console.log('下一任务'),0);
for(let i=0;i<3;i++) queueMicrotask(()=>console.log('微任务',i));
```

微任务在检查点持续清空，递归微任务不天然给输入和绘制机会。真正拆分长任务要减少工作，或使用宿主任務调度/Worker，并测交互延迟。

## 从示例走向实际使用

用性能面板找到具体长任务的调用栈，再判断是算法复杂度、数据规模还是布局交错导致。修改后重复同一用户操作，查看交互延迟与总耗时，而不是只看某个函数变短。

课内微任务示例说明连续微任务会在下一任务前执行。实际分块应使用目标浏览器支持的调度方式，并在低性能设备上验证可响应性。
