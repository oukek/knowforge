## 从威胁和业务要求定义租户
用户不等于租户，一个用户可以属于多个组织，角色随组织变化。认证回答是谁，租户授权回答可访问哪个组织及资源。租户上下文应来自验证过的成员关系或服务身份，不能信任客户端随意提交的 tenantId。数据隔离与 CPU/连接池/队列等资源隔离是两条责任线。
## 三类数据部署方案
共享库共享表成本低，但每条访问都要受租户约束；独立 schema/库有更清晰的数据管理边界，连接和迁移成本更高；独立实例或整套资源可满足高隔离与性能要求，但成本和运维复杂度最高。MySQL 不应被假定具有 PostgreSQL 式通用行级安全策略，需在服务/数据访问层及授权服务强制处理。

| 方案 | 适合起点 | 主要验证 |
| --- | --- | --- |
| pool 共享表 | 大量标准租户 | 所有路径租户条件、唯一键、资源公平 |
| bridge 独立库/schema | 中高隔离、定制运维 | 路由、连接池、批量迁移与备份 |
| silo 独立实例/栈 | 合同/地域/高负载客户 | 控制面统一、容量、成本和恢复 |
这不是按客户金额机械分级，真正依据是合规、性能、恢复目标、驻留和合同约束。
## 不只 SQL 加一个条件
主键查询、更新、删除、关联、批量导入、报表与后台任务都需隔离；联合唯一键常要包含 tenantId，外键/关联也需防跨租户绑定。缓存键、对象存储路径、搜索 ACL、消息、向量索引、导出文件和日志都要带正确租户域。ORM 全局过滤可降低遗漏但不能替代测试，原生 SQL 与管理员路径尤其容易绕过。
## 大客户如何独立且可维护
控制面维护租户到数据面资源的映射、版本、地域与策略，数据面执行隔离。迁移按快照复制、增量追平、校验、短写暂停或安全切流、观察与回退推进；路由版本和幂等跨切换保持一致。避免为每家长期维护独立代码分支，配置差异与发布策略应受统一控制面管理。
## 资源隔离与示例
给租户配置并发、数据库连接、队列、token 和费用配额，按租户观测尾延迟与饱和，防 noisy neighbor。下方内存示例强制通过 session 的租户过滤，说明即使资源 ID 正确仍不能直接返回。实际系统使用参数化 SQL 和统一仓储层，未命中时避免暴露资源是否属于别人。
## 验收与面试追问
创建两个租户使用相同本地编号，交错执行增删改查、缓存与导出，再测后台 worker 和管理员操作。大客户方案需要备份还原、迁移回退和容量实测。独立数据库本身也不能防应用错误路由，隔离要在身份、路由、访问、资源和审计多层一致执行。

## 朋友原题与口述参考
**原题记录：** 你这边是如何设计租户隔离的，如果是大客户呢？方案是什么？

先验证用户在当前组织的成员关系，由服务端建立租户上下文；所有 SQL、关联、唯一键、缓存、存储、队列、向量和导出都受租户域约束，再做资源配额防邻居干扰。共享表不等于只在某个接口多加 where。

标准租户可共享，大客户按性能、地域、合同和恢复要求独立库/实例或独立栈，统一控制面管理路由与版本。迁移采用快照/增量追平、校验、切流与回退，避免长期分叉。独立库也要防错误路由，跨租户测试与审计不可省；未做过的规模应说明是方案而非真实经历。

## 延伸追问与分析
**查询都带 tenant_id，但缓存中仍串数据，问题通常在哪？**

缓存键可能只有 resourceId，没有租户/权限/版本域，或复用未校验身份的缓存结果。统一 key 构造、先鉴权再取值，并测试两个租户相同 ID 与权限变更后的失效。

检查点：缓存域、鉴权顺序、碰撞回归。

**大租户迁独立库时怎样避免丢写或重复写？**

记录复制快照与增量边界，迁移期间保持稳定幂等 ID，追平并校验后通过有版本的路由切换。需短暂停写或明确双写/补偿策略，监控旧路由迟到写与回滚窗口，不能只修改连接字符串。

检查点：增量边界、幂等路由、回退窗口。

**后台队列没有浏览器登录态，如何保证任务不跨租户执行？**

任务携带由可信入口生成的租户/主体与目标版本，worker 重新验证服务权限和资源归属，不把消息字段直接当授权事实。数据访问层仍强制租户域，并审计原始发起者与执行身份。

检查点：可信上下文、再授权、执行审计。
