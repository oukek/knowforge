## 从具体问题认识技术选型

技术选型是在约束下选择能承担目标的方案。约束包括团队经验、交付时间、现有系统、性能与运维要求；如果这些条件没有写清，讨论很容易变成谁更喜欢某个工具。架构的价值是解释取舍，并让未来变化有可管理的路径。

例如一个三人团队做内部学习系统，和多个团队独立发布的大型平台，即使页面相似，也可能需要不同的模块与部署方式。

## 比较方案时同时计算获得与付出

先把需求拆成必须满足与可以优化两类。必须满足的条件用于排除不可行方案，例如运行环境、数据边界或明确的延迟要求；可优化项再比较成本与收益。评分表可以帮助讨论，但权重来自业务判断，不应伪装成客观数学真理。

至少比较一个简单基线与一个更复杂方案。缓存、队列、微服务和多集群都能解决特定问题，也会增加一致性、监控和恢复成本。应说明什么时候简单方案开始不够用，以及达到什么证据后才值得迁移，而不是提前引入所有可能用到的组件。

可逆性影响决策方式。可以通过适配层替换的库，试点成本较低；数据模型、公开 API 和大量客户集成一旦形成，迁移代价更高。对难逆转决策，应增加原型验证和兼容设计；对容易调整的细节，不必无限讨论。

## 把机制放到一条完整路径中

```flow
约束下的选型
定义目标｜列出业务需求与硬约束
比较备选｜包括简单基线和实际成本
验证风险｜针对高代价假设做原型
记录决策｜写下取舍与重新评估条件
```

## 配套代码：硬约束优先于加权偏好

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

先淘汰不满足兼容要求的方案，再在可行候选里比较指标。

```javascript
const candidates=[{name:'新方案',compatible:false,score:95},{name:'稳定方案',compatible:true,score:80},{name:'折中方案',compatible:true,score:85}];
console.log(candidates.filter(item=>item.compatible).sort((a,b)=>b.score-a.score)[0].name);
console.log([...candidates].sort((a,b)=>b.score-a.score)[0].name);
```

不先处理硬约束会选出高分却不可交付的方案。分数来自人为权重和实测依据，不是客观万能排名；真实选型要记录假设、试点和退出策略。

## 从示例走向实际使用

写一页决策记录，包含背景、约束、备选、选择依据、已知代价和重新评估条件。后来环境变化时，可以知道原结论基于什么，而不是把过去选择简单评价为对错。

面试时用具体场景解释为什么没有选择另一个方案，并给出可验证触发条件。不要只罗列工具优点，也不要声称某个架构适合所有规模。
