## 从具体问题认识传统双线程模型与平台差异

小程序不是把网页缩小后放进微信。业务代码需要处理登录、请求和页面状态；视图需要把 WXML 与 WXSS 变成用户看见的界面。传统小程序把这两类职责放在不同的执行环境中，常称为逻辑层和视图层。这里的“双线程”首先是职责与通信模型，不表示微信整个进程永远只有两个操作系统线程。

例如点击商品数量的加号，事件先由视图传到逻辑层，业务代码计算新数量，再把需要显示的变化送回视图。一次点击至少涉及事件、状态计算和视图更新，理解这条路径才能解释为什么 JavaScript 算完了，屏幕却还没有更新。

## 状态为什么需要跨环境传递

在普通网页中，业务 JavaScript 可以调用 DOM API 直接修改节点。小程序的逻辑层通常不能用 document.querySelector 操作页面，它通过框架提供的数据绑定和平台接口工作。WXML 描述结构，WXSS 描述样式，data 表示参与视图绑定的数据，setData 把变化提交给渲染链路。直接改 this.data 内的字段并不等于通知视图更新。

跨环境通信有固定开销，也有随数据量增长的序列化、传输和消费开销。假设列表有一千条记录，只更新其中一条的收藏状态，却发送整个列表，逻辑计算可能只有一次布尔取反，视图更新的成本却远不止这个操作。应把“业务状态变化多少”和“跨层发送多少”分别观察，而不是只统计 setData 次数。

不同宿主、系统和渲染模式可能采用不同实现；传统 WebView、Skyline 的渲染路径不能画成完全相同的一张线程图。页面数量、插件、原生组件也会影响真实资源分布。工程上先确认当前页面使用什么渲染模式，再根据该模式检查支持的组件、布局与通信能力。

## 把机制放到一条完整路径中

```flow
一次小程序交互
视图事件｜用户点击加号
逻辑处理｜校验并计算新状态
跨层提交｜发送实际变化的数据
视图更新｜布局绘制后显示结果
```

## 配套代码：跨层消息不能共享同一个对象

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

用 JSON 往返模拟传统跨层传输，观察副本与原对象的区别。

```javascript
const logic = {selected: false};
const view = JSON.parse(JSON.stringify(logic));
logic.selected = true;
console.log(logic.selected);
console.log(view.selected);
console.log(logic === view);
```

视图得到独立序列化结果后，逻辑对象的直接变化不会自动修改该副本。真实宿主通信和 Skyline 不完全等于 JSON 往返，这个模型只说明边界和显式提交。

## 从示例走向实际使用

排查一次列表卡顿时，先记录数据返回、业务处理开始结束、提交更新、页面可见等时间点。若网络慢，减少 setData 不能让请求提前完成；若每次滚动都发送巨大的列表，换更快的接口也消除不了视图压力。

本课实验只帮助拆分链路成本。实际测量应在真机、固定数据和固定操作下重复，区分首次进入与再次进入，避免把开发者工具的表现当成所有手机的表现。
