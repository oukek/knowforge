## 从职责分层而非背表格开始
MySQL 服务层负责连接、解析、优化和 binlog 等公共能力，存储引擎负责记录、索引、并发控制和相应恢复。InnoDB 常用于事务型业务；MyISAM、MEMORY 不是“更老所以没有意义”，而是在事务、锁粒度、持久性和特定工作负载上取舍不同。不同版本、引擎插件应分别确认能力。
## 常见引擎如何比较
| 维度 | InnoDB | MyISAM | MEMORY |
| --- | --- | --- | --- |
| 用户事务与回滚 | 支持 | 不支持 | 不支持 |
| 典型并发机制 | 行级索引锁、MVCC，也有表级锁 | 表级锁 | 表级锁 |
| 记录组织 | 聚簇组织，二级键定位主键 | 数据与索引分离 | 内存数据，常见 HASH/B-tree |
| 重启后数据 | 结合日志恢复持久数据 | 需关注崩溃与修复边界 | 表定义可保留，数据丢失 |
| 典型选择 | 订单、账户、通用 OLTP | 受约束的历史或专用负载 | 可重建、容量有界的临时数据 |
“用了行锁”不表示只锁一条业务记录。没有合适索引可能扫描并锁住更多范围；元数据锁、DDL 和表级意向锁仍会出现。
## 三种日志为什么不能互相替代
undo 保留回滚与一致性读需要的旧版本信息；redo 支持已记录变更的崩溃恢复；binlog 位于服务层，支持复制和时间点恢复等用途。提交耐久性还取决于刷盘参数、操作系统和存储保障，不能只说“有 redo 就绝不丢数据”。长事务会推迟旧版本清理，造成历史链与空间压力。

账户转账必须把扣款、入账和相关状态放在合适事务中，且所有参与表都要具备需要的事务能力。外部消息和支付接口不能随数据库回滚自动撤销，可用 outbox 与幂等消费衔接，不能把网络调用包进 BEGIN 就称为分布式事务。
## 验证环境与恢复演练
```sql
SHOW ENGINES;
SHOW CREATE TABLE orders;
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'sync_binlog';
```
确认表实际引擎、版本、数据量与事务边界。恢复能力通过备份还原、binlog 回放、复制延迟与故障演练验证。不要在生产上故意强杀数据库来证明机制，也不要将表引擎转换当作无成本操作：需考虑重建、锁、空间和回滚时间。
## 可运行模型与限制
JS 模型把事务的待提交操作与已提交日志分开，崩溃恢复只重放已确认的操作。它解释提交记录和未提交状态的区别，不能代表 InnoDB 页刷写、两阶段提交和真实 fsync 时序。尝试在提交前抛异常，观察原始余额是否变化，再说明真实数据库需要哪些日志与原子性保证。
## 如何组织面试答案
先给业务要求：并发更新、事务一致性、恢复目标、数据容量；再比较引擎，而不是以 SELECT COUNT(*) 的一个特例决定选型。追问 MyISAM 是否更快时，应要求具体读写比例、索引、数据热度与并发；性能是工作负载测量结果，不是引擎名称的固定属性。

## 朋友原题与口述参考
**原题记录：** innodb跟其他引擎的区别？

按事务、并发控制、索引组织、持久性和恢复比较。InnoDB 提供用户事务、MVCC、行级索引锁和日志恢复，适合多数 OLTP；MyISAM 无用户事务回滚，主要表锁，数据和索引分离；MEMORY 主要保存内存数据，重启后数据不保留，也不能代替事务库。

InnoDB 仍存在表级/元数据锁，范围与索引会影响锁的范围。undo、redo 与服务层 binlog 职责不同，耐久性受刷盘配置影响。选型以业务一致性、恢复目标与实际压测为依据，不凭“某引擎查询快”就切换。

## 延伸追问与分析
**为什么 InnoDB 已有 redo，还需要 binlog？**

二者层次与目的不同：redo 服务于引擎崩溃恢复，binlog 表达服务层变更并用于复制、时间点恢复。不能拿 redo 直接当跨版本逻辑备份。提交时还需协调两类日志的一致性，并核对相应刷盘配置与恢复目标。

检查点：日志层次、复制恢复、耐久配置。

**把转账表的一张改成 MEMORY 后，事务回滚还能保证转账原子性吗？**

不能假设跨事务与非事务表仍可整体回滚。参与表的能力决定保证边界；需保持关键账务在事务引擎内，失败时检查非事务副作用。缓存只作可重建投影，不能充当唯一账本。

检查点：引擎边界、原子性、账本投影。

**业务量没变，undo 和表空间持续增长，怎样定位？**

检查长事务、一致性快照持续时间、历史链、purge 进展和异常会话，再关联备份/报表任务。不能只扩盘；控制事务长度、批次并发与超时，确认释放后空间复用和文件缩减是不同事情。

检查点：长事务、历史清理、空间复用。
