## 从具体问题认识AI、机器学习、深度学习与生成式 AI

想象一个客服系统需要完成四件事：按固定规则计算退款、识别用户在投诉什么、起草回复、查询订单后决定下一步。它们都与“智能服务”有关，但需要的机制并不相同。计算退款可以是确定性程序，分类可以是学习模型，起草属于生成任务，多步选择行动才涉及智能体组织。

先把这些任务分开，就能理解 AI、机器学习、深度学习与生成式 AI 为什么不是四个可以互换的产品名称。学习本课的目标，是把需求放到正确层次，而不是背缩写。

## 用输入、学习方式和输出认识概念层次

规则程序的行为主要来自人工写出的条件；机器学习系统从样本中调整模型，使某类预测或决策表现更好。深度学习使用多层神经网络学习表示，是机器学习中的一类方法。生成式任务关心产生新内容，判别式任务关心分类或判断，任务类型与模型结构并不是同一分类轴。

同一个应用可以组合多个机制。退款金额由程序精确计算，语言模型把结果解释给用户，权限服务判断是否能查看订单，工作流控制是否需要人工确认。模型会写自然语言，不代表它应该接管所有确定性步骤。

“模型”通常指结构与参数组成的可计算系统，“训练算法”决定参数如何更新，“推理服务”把模型部署成可调用能力，“应用”则加入数据、界面、状态和权限。故障发生在哪层，需要分别检查；模型回答错误与数据库查错租户，不是同一种问题。

## 四个词处在不同层级

AI（Artificial Intelligence，人工智能）是让系统完成感知、推断、规划等智能任务的广泛领域；机器学习 ML 研究从数据学习规律的方法；深度学习 DL 使用多层神经网络学习表示。生成式 AI 强调生成文本、图像、音频等内容，是任务与能力描述，不能把它理解为所有 AI 的同义词。

这些概念不是一条严格的产品升级排行榜。推荐排序、欺诈检测、OCR 和路径规划都可以是 AI 应用，不一定需要聊天模型；规则引擎也能和学习模型组合。判断一个方案应先看输入、输出、约束和验证方式，而不是看名字有没有 Agent。

## 模型、算法和应用分别是什么

算法是计算或学习步骤；模型是可用于推断的结构及参数；数据用于训练、评估或运行时提供事实；应用把模型、界面、业务流程、存储、权限与监控组成完整服务。同一个模型可以驱动多个应用，同一应用也可以路由到不同模型。

| 层 | 例子 | 不能混淆 |
|---|---|---|
| 问题 | 判断某笔订单可否退款 | 这是业务目标，不是模型名称 |
| 方法 | 规则、分类器或检索加生成 | 要通过相同验收比较 |
| 模型 | 分类网络、语言模型 | 模型不知道所有实时业务事实 |
| 产品 | 客服退款工作台 | 还需要认证、查账和人工接管 |

“用了神经网络”不等于“会生成内容”，“能生成内容”也不等于“能自主完成业务”。

## 怎样从需求选择最小方案

固定税率计算、金额校验和权限判断通常由确定性函数实现；从工单文本识别类别可能用分类模型；依据多篇资料组织回答可以用检索和生成；需要根据观察多步选择行动时才考虑 Agent。确定性规则和概率模型的边界应在设计时写清。

假设有四个需求：计算折扣、识别垃圾邮件、起草邮件、查询后创建日程。前两个不必强行套 Agent，第三个可以是一次生成，第四个可能需要工具与状态。需求复杂也不自动意味着必须多 Agent，很多流程用显式工作流更可检查。

## 误区、边界与学习路线

不要把“大模型”当作数据库、计算器和授权系统的通用替代；不要把 AI 产品的失败都归因于模型参数少。训练数据质量、接入事实、任务契约和交互设计都会影响结果。模型能力和系统能力应分别测试。

建议按 LLM → token → embedding → Transformer → 训练与推理学习模型基础，再进入应用架构、RAG、工具调用和 Agent。每一步都能解释“输入是什么、计算了什么、输出保证什么”，比一次背几十个缩写更有用。

## 把机制放到一条完整路径中

```flow
从业务问题到 AI 方案
定义任务｜确定输入输出与错误代价
选择方法｜规则预测生成或行动循环
接入模型｜明确训练能力与推理接口
构成应用｜加入数据权限状态与验证
```

## 配套代码：AI、机器学习、深度学习与生成式 AI：概念地图

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。



```javascript
function chooseApproach(task) {
  if (task.deterministic) return "rules";
  if (task.needsAction && task.dynamicSteps) return "agent";
  if (task.generatesContent) return "generation";
  return "prediction";
}
const tasks = [
  { deterministic: true },
  { generatesContent: false },
  { generatesContent: true },
  { needsAction: true, dynamicSteps: true },
];
console.log(tasks.map(chooseApproach));
console.log(["authorization", "validation", "audit"]);
```

决策表强调问题类型与业务底座。它不是以模型大小打分，也不保证任何具体产品必须选择某种框架。

## 从示例走向实际使用

拿一个真实需求，写出输入、期望输出、错误代价与可验证标准，再比较规则、传统模型、一次生成和多步 Agent。若简单方案已满足要求，复杂模型不一定增加价值。
