## 函数重新执行，状态怎样保留下来
普通局部变量在函数每次调用时重新建立，不能独立承担组件跨渲染状态。React 根据组件身份保存 Hook 状态，并在渲染时把当前值交给组件。这次渲染得到的 count 是一个快照；调用 setCount 是请求后续更新，不会回头修改当前函数局部变量。

因此事件回调里调用 setCount 后立即 console.log(count)，看到旧快照是正常的。定时器回调也闭包捕获创建它那次渲染的变量。若需要最新操作基于前一个状态，应使用更新函数，而不是假设闭包中的数字实时变化。
## 一次渲染拿到的是固定的输入集合

可以把组件一次调用理解为：给定本次props与state，计算应该显示的元素，同时创建引用这份输入的事件处理函数。之后调用setState，只是把新更新提交给React；当前这次调用中的常量不会被追溯修改。因此setCount后打印旧count，与未来界面显示新count并不矛盾。

状态初始化参数主要用于建立初始状态，不是每次props变化都强制覆盖已有state。编辑器若从initialText建立草稿，父传入新initialText时是否重置，需要明确组件身份或显式同步策略；不能既希望保留用户编辑又无条件按props覆盖。

## 更新队列、不可变数据与状态结构

替换值表达“下一状态设为这个结果”，更新函数表达“根据队列处理到的前状态继续计算”。后者适合连续计数等依赖前值的操作，函数必须纯净，不在里面发请求或写外部变量。批处理减少重复渲染，但不等于所有业务动作成为一个数据库事务。

对象状态更新需要保留未修改字段，例如`setUser(old => ({...old, name}))`。嵌套对象应沿修改路径复制，而非只复制最外层后继续改共享内部值；也不必每次深复制整份巨大树。结构过深时可以按ID规范化数据，让修改范围更明确。

能由现有状态推导的值通常无需再存state，比如过滤结果和总数。多个布尔值还可能组成不可能状态，如loading与success与error同时为真；用明确的状态枚举或reducer能表达合法转移。好的状态设计减少同步工作，而不是增加更多Effect去修补不一致。

## 连续三次更新为何不同
```jsx
import { useState } from 'react';
export default function Counter() {
  const [count,setCount]=useState(0);
  return <button onClick={()=>{
    setCount(n=>n+1);
    setCount(n=>n+1);
    setCount(n=>n+1);
  }}>{count}</button>;
}
```
函数更新依次接收队列中的前一个结果，最终加3。若改成三次 setCount(count+1)，三个表达式都由同一快照计算，提交的是相同替换值。更新函数应纯净，不在里面发请求或修改外部数据，因为框架在检查和调度中可能多次调用相关计算。
## 数组和对象不是直接改了就能可靠更新
```javascript
// 在组件事件处理里：更新指定项，保留其它项的身份。
setRows(previous => previous.map(row =>
  row.id === editingId ? {...row,title:newTitle} : row
));
```
新的外层数组与被修改项，让变化路径清楚可见。直接 rows[0].title=... 会修改现有快照引用，破坏历史值和比较假设；只复制外层后继续改共享内部对象也不等于完成隔离。不可变修改不是“所有东西每次深拷贝”，应按变更路径复制。
```flow
状态更新如何累积
本次渲染快照｜事件处理读取的是这个值
提交多个更新｜替换值或纯更新函数
React 处理更新队列｜按顺序计算下一份状态
重新渲染｜组件得到新的快照
提交所需 DOM 变化｜渲染次数与 DOM 修改次数不是同一个数
```
## 派生状态与重置规则
过滤列表、总价等能由 props/state 直接算出的值通常不需要再用 Effect 存一份 state，否则会多一次同步与过时窗口。组件身份由类型、位置与 key 等决定，更换 key 可以有意重置整份子组件状态，但随机 key 会让每次渲染都变成重新创建。

批处理减少重复工作，具体边界还取决于更新来源和调度，不能作为业务事务保证。连续动作的正确性应通过更新函数与明确状态机表达，而不是依赖某次渲染恰好被合并。
