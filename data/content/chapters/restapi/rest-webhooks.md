## 从具体问题认识Webhook、签名、重放防护与幂等消费

Webhook 是一个系统在事件发生后主动向另一个系统发送 HTTP 通知。接收方需要确认消息来自可信来源、没有被篡改，并且重复通知不会重复产生业务影响。HTTP 请求收到一次，不代表业务事件只会发送一次。

支付或任务服务可能因为未收到确认而重试同一个事件，因此接收端应把重复交付当成正常情况设计。

## 验签、防重放与可靠消费

签名通常对原始请求体及约定元信息计算，接收方使用共享密钥或公钥验证。若先解析 JSON 再重新序列化，空白或字段顺序变化可能导致签名不匹配，所以应保留协议要求的原始字节。比较签名使用适合的安全比较方式，并支持密钥轮换。

有效签名不等于事件新鲜。协议可包含时间戳并限制允许窗口，再结合事件 ID 去重，防止旧消息被重复应用。时间窗口应考虑双方时钟与正常重试，不能只看时间就丢弃所有延迟合法事件。

接收后先可靠保存或完成必要事务，再返回成功确认。若先回 2xx 后只放进内存，进程崩溃会丢事件。下游处理较慢时可持久入队并异步执行，状态更新按业务版本处理乱序，不能假设网络到达顺序等于事件发生顺序。

## 把机制放到一条完整路径中

```flow
Webhook 接收
读取原文｜保留验签所需字节与元信息
验证来源｜签名时间与目标契约检查
持久接收｜去重并可靠记录事件
幂等处理｜按版本应用后返回或记录确认
```
