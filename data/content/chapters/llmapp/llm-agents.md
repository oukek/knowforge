## 从具体问题认识Agent、工作流、状态机与停止条件

Agent 是在目标和边界内，根据当前状态选择下一步行动、观察结果并继续的程序。与固定一次模型请求相比，它增加了循环和状态；与普通工作流相比，部分路径可能由模型动态决定。自主程度是设计选择，不是越高越好。

例如学习助手需要先找知识点，再查看用户答案，必要时生成补充练习。哪些步骤固定、哪些允许模型选择，应该由业务可靠性要求决定。

## 行动循环、状态与退出条件

一个最小循环包含观察、决策、行动与更新。观察是当前可见信息，决策产生回答或工具提议，行动执行受控工具，更新把结果写入状态。状态需要区分用户目标、已完成工作、证据与待解决问题，不能只靠不断累积聊天记录。

每轮都检查总时间、token、工具次数与允许动作。退出原因包括成功、信息不足、需要用户确认、预算耗尽和不可恢复错误。maxSteps 只能兜底防止无限循环，不能代替任务成功判断；提前停止也需要向用户说明完成了什么。

重复动作可能表示卡住，也可能是状态改变后的合理重查。检测循环应结合动作、参数、相关状态和结果，例如连续相同查询返回相同内容且没有新证据时停止。仅按工具名去重会错误阻止多次查询不同资料。

## 把机制放到一条完整路径中

```flow
Agent 的一轮
观察状态｜目标证据已完成项与剩余预算
选择动作｜回答查询或请求确认
验证执行｜在权限和资源边界内使用工具
更新或退出｜记录结果并判断是否继续
```

## 配套代码：Agent、工作流、状态机与停止条件：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

actions=['search:a','read:1','search:a']
seen=set(); status='running'
for action in actions:
    if action in seen: status='stopped: repeated action'; break
    seen.add(action)
show(status)
show(len(seen))
```

重复动作检测是简单护栏，真实任务可能需要带不同状态重复同一工具，因此摘要应包含有效状态与参数。示例没有自主模型决策，最终成功还需由业务产物验证，而不是只要循环结束就算成功。

## 从示例走向实际使用

先实现固定流程基线，再把确实需要动态判断的节点交给模型。比较任务成功率与成本，避免为了“像 Agent”而引入不必要的循环。

课内重复动作集合是最简停机演示。生产实现应采用更细的状态签名，并保留每轮动作与退出原因供复盘。
