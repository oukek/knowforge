## 适合提效的工作与责任
AI 可以从需求生成候选测试、列边界、搭建最小复现、归纳日志和提出修复假设。执行结果和最终责任仍由工程团队承担。不能把同一模型写的实现与镜像测试同时通过当作独立证明，也不能把生产密钥、完整用户数据或任意终端权限直接交给 Agent。
## 测试生成从契约出发
先从需求提取输入域、输出、不变量、错误与资源限制，再构造正常、边界、异常、并发和权限场景。测试应先能复现真实缺陷或由可信旧实现/业务规则提供 oracle。算法可用暴力小规模差分、性质测试与变异测试；接口可用 schema、幂等、租户隔离和故障注入。快照过大、断言只检查存在与过度 mock 都容易造成虚假安全感。
## Debug 的有界循环
收集脱敏症状、版本和最小必要上下文，Agent 提出假设及区分它们的实验，宿主在隔离环境执行并返回退出码、日志和产物。先形成失败测试，再做最小补丁，运行相关回归，审查 diff 与需求，再决定是否扩大验证。预算限制循环次数、时间、命令、文件与网络；失败应升级给人，而不是无限改到测试被删除。
## 处理不稳定与生产问题
时序、随机、时区和外部依赖要控制或记录，避免让 Agent 通过多跑几次隐藏 flaky。线上排查先只读与止损，涉及写入/重启/数据修复必须按授权与可回退操作规程执行。工具日志是证据，模型总结不能覆盖实际失败退出码；输出中恶意指令当数据处理。

## 效果评价与面试追问
统计复现/定位时间、有效缺陷检出、人工接受补丁率、返工、误报、P95 与费用。用同类型任务比较人工、AI 辅助和更多自动测试的增益。没有证据时应说辅助产生线索，不能宣称“Agent 自动保证质量”或把生产写操作当普通调试步骤。

## 朋友原题与口述参考
**原题记录：** ai agent可以怎么在测试用例和debug方面提效？

让 Agent 从需求契约提出边界/权限/并发测试、生成最小复现、归纳日志并提出可验证假设。先固定失败用例再做最小补丁，工具真实执行回归，审查 diff；模型总结不能代替退出码和业务 oracle。

算法用独立暴力/性质/差分，接口用幂等和故障注入，避免实现与测试互相照抄。宿主沙箱限制路径、命令、网络与预算，数据脱敏，生产写入按授权。效果看复现定位时间、有效检出、补丁接受/返工和成本，不只看生成多少测试或覆盖率。

## 延伸追问与分析
**Agent 修复 bug 后把失败测试删掉了，怎样防止这种“成功”？**

需求与验收测试作为受保护输入，审查 diff 中的删除/放宽断言，执行独立测试集并核对退出码。必要时工具层限制修改路径；模型说通过不构成完成，测试变更需人工理解业务原因。

检查点：保护验收、独立验证、变更审查。

**只有生产偶发的并发 bug，如何给 Agent 足够上下文又不泄露数据？**

提供脱敏时间线、版本、请求关联和交错操作，构造最小模拟负载与可控调度。保留关键时序而非原始身份信息；隔离环境只读分析后生成复现，生产写入/重启仍需明确操作授权。

检查点：最小上下文、并发复现、权限边界。

**AI 生成一百条测试都过了，你如何快速判断它们是否有价值？**

抽查断言是否依据需求而非实现，是否覆盖边界/错误/权限，能否杀死关键变异或复现已知缺陷。去掉重复与脆弱 mock，评估执行维护成本；数量不能代替独立正确性 oracle。

检查点：需求断言、反例检出、去重成本。

## 实践任务与验收
为一个存在重复扣款风险的接口写需求：同一幂等键相同请求只产生一次账务效果，同一键不同参数必须拒绝。让 Agent 先生成测试候选，人工检查是否覆盖并发请求、业务已提交但响应丢失、任务重启和键过期。只检查 HTTP 200 不足够，必须验证账务结果的次数和状态。

把外部支付替成受控假服务，按顺序注入“先成功后断连”和“明确拒绝”两种结果，观察 Agent 是否把它们混为可重试错误。允许其修复服务代码，但保留独立验收测试与账本读入口；如果它通过放宽断言或删除错误分支获取绿色结果，验收应失败。记录提出假设、最小复现、补丁、真实命令结果与人工结论，最终用有效定位时间和返工衡量收益，而非生成代码量。
