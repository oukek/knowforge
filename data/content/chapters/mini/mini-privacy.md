## 从具体问题认识隐私授权、手机号与最小采集

隐私授权需要区分三个问题：用户是谁、当前功能能调用什么平台能力、取得的数据允许用于什么业务目的。登录回答第一个问题，系统或平台权限回答第二个问题，数据用途说明和业务处理回答第三个问题。把它们混成一次弹窗，会让拒绝后的行为难以解释。

例如用户可以浏览课程，但上传头像才需要选择图片；用户可以保存学习进度，但电话联系才需要手机号。数据需求来自具体功能，而不是因为平台提供了接口就全部采集。

## 沿着数据生命周期设计权限

首先列出数据从哪里来、用于什么、谁能访问、保留多久和如何删除。客户端获得某项能力并不代表服务端可无限期存储所有原始信息。接口返回时应裁剪无关字段，日志中对敏感信息脱敏，后台访问则按实际职责授权。

权限申请发生在用户能理解原因的操作附近。拒绝后，界面应说明该功能受到什么影响，并提供可行替代，例如手动填写非敏感信息或继续浏览。不要在每次进入页面时反复弹出同一请求，也不要把拒绝当作系统异常不断重试。

平台接口、系统权限与具体业务资格会随版本变化。接入手机号等能力时，应核对当前接口要求和凭证流程，不把旧版加密数据方案套用到所有新接口。撤销授权后，需要停止依赖该授权的新采集；已经保存的数据如何处理，则应按告知用户的规则及适用要求执行。

## 把机制放到一条完整路径中

```flow
最小必要的数据处理
功能需求｜说明为什么需要这项数据
主动申请｜在相关操作中请求能力
受控使用｜限制字段访问与保存范围
撤销删除｜提供可执行的退出路径
```

## 配套代码：授权拒绝也保留非必要功能

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

把浏览和需要手机号的业务区分，避免用一个权限开关挡住全部流程。

```javascript
function available(action, hasPhoneConsent) {
  return action === '浏览' || hasPhoneConsent;
}
console.log(available('浏览', false));
console.log(available('手机号联系', false));
console.log(available('手机号联系', true));
```

浏览与手机号用途分开，拒绝授权仍能完成不依赖手机号的任务。真实系统还需合法用途、平台资格、服务端凭证验证和替代流程，不是只有一个布尔值。

## 从示例走向实际使用

为授权流程准备未询问、同意、拒绝、系统禁止和授权过期等状态，分别写出用户下一步可以做什么。自动化测试可以验证状态流转，真实权限弹窗和不同系统行为仍需真机检查。

本课是工程上的数据最小化与权限分层方法，不替代具体业务的合规审查。上线时应核对当前微信规则和实际经营范围，而不是照搬一份永久不变的权限清单。
