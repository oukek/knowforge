## 先按工作性质拆分
I/O等待期间CPU可能闲置，协程或线程可以让其它工作推进；CPU密集计算需要实际计算资源，进程、释放GIL的扩展或合适的无GIL构建可能提供不同并行方式。不要由“Python有GIL”推断所有线程都无用，也不要由“async”推断能自动多核计算。

常见CPython构建中的GIL限制同一时刻执行Python字节码的线程，但I/O和某些原生扩展可能释放它。可选自由线程构建有不同约束与生态兼容要求，应明确解释器版本和构建，不能把某一实现结论当全部Python语言保证。
## 线程、进程和协程的内存关系

同一进程中的线程通常共享地址空间，因此可以直接访问同一个列表或对象；便利的同时也带来数据竞争。进程拥有更强的内存隔离，传递任务一般需要序列化、共享内存或消息通信。协程通常运行在一个事件循环线程中，靠等待点协作切换，但多个协程仍可能在“读取→await→写入”的逻辑之间交错，单线程也不保证业务操作原子。

并发描述多个任务在一段时间内共同推进，并行描述同一时刻由多个执行资源真正计算。一个CPU核心可以通过调度实现并发，但不能因此获得无限计算能力。I/O工作、CPU工作和混合工作需要分别测量，不能只根据任务数量选择方案。

## 共享状态必须保护整个业务操作

```python
from concurrent.futures import ThreadPoolExecutor
from threading import Lock

balance = {"value": 0}
lock = Lock()

def add_one(_):
    with lock:
        balance["value"] += 1

with ThreadPoolExecutor(max_workers=4) as pool:
    list(pool.map(add_one, range(100)))
print(balance["value"])
```

锁保护的是“读取、计算、写回”这个整体，而不只是某条赋值语句。实际业务若先检查库存、释放锁、再扣减，检查与修改之间仍可能被其它线程插入。临界区应覆盖维护不变量所需的步骤，同时尽量短，不在持锁时等待慢网络。

将任务交给进程池时，函数与参数通常需要可序列化，入口要按平台和启动方式正确保护。线程里的阻塞调用不会因等待它的协程被取消就必然终止；所有并发方案都需要任务容量、退出信号和收尾协议。先明确谁拥有数据、谁拥有任务，再决定线程数或worker数。

## 用线程执行互不依赖的任务
```python
from concurrent.futures import ThreadPoolExecutor

def square(value):
    return value * value

with ThreadPoolExecutor(max_workers=2) as pool:
    print(list(pool.map(square, [2, 3, 4])))
```
这个短计算仅说明接口，不声称线程让它更快。真实选择应使用有代表性的I/O或CPU负载测量，线程创建、排队与调度也有开销。线程池上限控制工作线程，提交队列是否有界还需另外检查。
## 进程隔离也有传输成本
进程有独立内存，任务参数和结果通常需要序列化与进程间传递。大对象复制可能吞掉计算收益，某些资源不能直接传递。启动方式和平台不同，还需要正确的主模块保护，不能在导入时递归创建进程。
```flow
选择执行方式
原生异步I/O｜协程与事件循环，控制任务数量
同步阻塞I/O｜受控线程池，明确取消局限
大量Python CPU计算｜评估进程或合适原生实现
共享可变数据｜锁、消息传递或不可变所有权
```
## 正确性与资源预算优先
GIL不保证复合业务操作线程安全，例如检查余额后扣减仍可能竞争。锁保护不变量，队列协调数据流；避免持锁调用慢外部服务。任务数、连接数、内存和总时间要一起限制。

测试失败传播、取消、进程退出和资源回收。并发度不是越大越好，吞吐提升也可能以尾延迟恶化为代价，应根据实际下游容量与服务目标选择。
