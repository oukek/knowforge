## 从具体问题认识长任务、轮询、SSE 与取消状态机

长任务不适合依赖一条一直不断开的 HTTP 连接维持生命。接口可以先创建任务并返回任务 ID，执行器在后台推进，客户端通过查询或事件订阅观察状态。连接生命周期与任务生命周期因此分离。

用户刷新页面后仍应能找到任务，网络断开也不应自动把已接受工作变成未知状态。任务最终结果应来自持久记录，而不是浏览器是否还开着加载动画。

## 状态机、事件与取消

任务状态可以包含 queued、running、succeeded、failed、cancel_requested 和 cancelled，每个转换有明确触发条件。取消请求只是表达停止意图；执行器确认停止并处理资源后，才进入取消终态。外部副作用已经发生时，可能只能停止后续步骤或执行补偿。

轮询简单且容易恢复，但要控制间隔和停止条件；SSE 适合服务端单向推送事件，WebSocket 适合双向实时通信需求。无论采用哪种传输，事件应带任务 ID、序号和阶段，重连后可从最后确认位置补事件或重新查询快照。

进度百分比需要可定义的总工作量。模型生成或动态任务图难以准确预测时，阶段、已完成步骤与耗时通常比假装精确的百分比更诚实。终态只写一次并与结果、计费等保持一致，重复事件不能让已完成任务退回运行中。

## 把机制放到一条完整路径中

```flow
持久长任务
创建接受｜保存参数返回任务身份
后台执行｜记录阶段尝试与资源使用
状态观察｜轮询或订阅可恢复事件
结束取消｜按事实提交唯一终态与结果
```

## 配套代码：长任务、轮询、SSE 与取消状态机：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

allowed={'queued':{'running','cancelled'},'running':{'succeeded','failed','cancel_requested'},'succeeded':set()}
show('running' in allowed['queued'])
show('running' in allowed['succeeded'])
```

状态迁移模型防止已完成任务随意回到运行中。真实任务重试可建立新 attempt 或显式迁移规则，并保留历史；模型未实现后台队列、持久化或 SSE 重放，这些应在工程集成中分别验证。

## 从示例走向实际使用

测试刷新恢复、重复事件、网络重连、排队取消、执行中取消与服务重启。界面应显示真实阶段和可用操作，不把连接断开直接等同任务失败。

课内 allowed 表演示合法转换，真实执行器还需要租约、尝试记录和条件提交，避免多个执行器同时写终态。
