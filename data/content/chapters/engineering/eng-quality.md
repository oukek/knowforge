## 从具体问题认识TypeScript、代码规范与质量门槛

质量门槛是把团队希望稳定满足的条件变成可执行检查，例如类型一致、格式统一、关键业务测试通过和产物体积不过度增长。它的目的不是让工具越多越好，而是尽早发现那些代价高且容易重复发生的错误。

TypeScript 能帮助检查代码中的类型关系，但网络输入、数据库旧数据和用户存储在运行时仍可能不符合声明。静态类型与运行时校验应在边界上配合。

## 不同检查覆盖不同失败类型

格式化减少无意义的样式差异，Lint 发现可疑写法与约定违反，类型检查发现不一致的调用关系，测试验证指定输入下的行为。任何一项都不能单独证明软件正确：类型完全正确的函数仍可能使用错误业务公式，测试通过也可能没有覆盖真实边界。

检查应分层安排。开发时执行快速反馈，提交时检查受影响代码，CI 执行必要的完整验证。过慢且经常误报的门槛会诱使团队绕过它，因此规则需要明确价值、可解释失败信息和合理维护者。不能通过随意放宽规则来掩盖真正问题。

外部数据进入系统时，先校验结构，再映射为内部可信类型；不要用类型断言直接把未知对象伪装成 User。对于资源归属、余额和状态转换，还需业务约束与事务验证，这些不是字段类型能表达完的。

## 把机制放到一条完整路径中

```flow
质量反馈链
边界识别｜找出高风险输入与行为
静态检查｜类型规则和格式提供早期反馈
行为验证｜测试关键不变量与失败路径
持续改进｜用真实缺陷调整门槛
```

## 配套代码：外部数据需要运行时校验

下面代码在课内JavaScript运行区执行；需要DOM、Node或平台SDK的真实集成，应按正文的运行边界另行验证。

TypeScript 类型不在运行时保护 JSON；用小型校验函数说明边界。

```javascript
function parseUser(input) {
  if (!input || typeof input.id!=='string' || !Number.isInteger(input.age)) throw new TypeError('用户格式错误');
  return {id:input.id,age:input.age};
}
console.log(parseUser({id:'A',age:20}));
try { parseUser({id:'A',age:null}); } catch(error) { console.log(error.name); }
```

显式校验挡住实际响应中的 null，返回可信领域对象。真实复杂契约适合 schema 库，仍需业务边界和错误恢复，不能用类型断言代替校验。

## 从示例走向实际使用

从近期真实缺陷反推检查：若常见问题是接口字段变化，就补契约检查；若常见问题是部署路径错误，就补产物启动验证。避免写只重复实现细节、却不验证业务行为的测试。

课内 parseUser 展示运行时边界校验。继续修改输入为空、年龄为字符串或超出业务范围，区分类型错误与业务错误，并设计清晰反馈。
