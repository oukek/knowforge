## 从具体问题认识埋点 SDK、批量上报与可靠交付

埋点 SDK 在应用中收集事件并发送到服务端。它运行在用户设备上，网络、页面生命周期和存储都可能不稳定，因此不能假设每个事件只发送一次，也不能保证页面关闭时最后一次请求必然成功。

批量上报减少请求开销，但批次越大，等待时间和失败重传成本也越高。SDK 的核心是一个有容量、状态与重试规则的交付队列。

## 至少一次交付与服务端去重

事件在产生时分配稳定 ID，进入队列后按数量或时间触发发送。服务端确认接收后才能移除相应事件；如果确认丢失，客户端会重发，所以服务端需要按事件 ID 去重。只在客户端记录“已调用发送函数”不能证明数据已经保存。

队列必须有容量上限与丢弃策略。普通行为统计可以在过载时抽样或丢弃低价值事件，关键业务账本则应由服务端事务记录，不能依赖浏览器埋点作为唯一证据。重试采用退避并区分永久错误，避免离线设备持续消耗电量。

页面离开时可使用适合生命周期的发送机制，但仍受浏览器限制，不能承诺百分之百送达。SDK 还需隔离自身异常，不能因为监控接口失败而让主业务失败；采集钩子、定时器和全局包装要可卸载，重复初始化不能重复上报。

## 把机制放到一条完整路径中

```flow
埋点交付队列
生成事件｜分配稳定ID与协议版本
有界缓冲｜按容量和时间形成批次
发送确认｜失败退避并保留未确认事件
服务去重｜重复交付只计入一次
```

## 配套代码：至少一次传输与服务端事件去重

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

同一事件被重传，接收端按 ID 保留一次业务效果。

```javascript
const received=new Set(); let stored=0;
function accept(event) {
  if(received.has(event.id)) return '重复';
  received.add(event.id); stored++; return '接收';
}
console.log(accept({id:'e1'}));
console.log(accept({id:'e1'}));
console.log(stored);
```

丢失 ACK 后重传会重复到达，稳定 ID 支持去重。真实平台还需可靠持久化后确认、有界客户端队列、退避和去重保留期，内存 Set 不是持久交付保证。

## 从示例走向实际使用

定义事件名称、版本、字段类型与敏感信息规则，再实现采集。事件协议变化要考虑旧客户端继续发送的情况，服务端应提供可观察的拒绝原因。

测试确认丢失、批次部分失败、重复初始化、队列满和离线恢复。课内 Set 去重仅演示事件身份，生产去重需要持久存储、作用域和合理保留期。
