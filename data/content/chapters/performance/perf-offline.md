## 从具体问题认识离线缓存、版本与写入队列

离线能力包含读取与写入两种不同问题。读取可以展示已有缓存，写入则需要保存用户意图，并在恢复网络后与服务端状态协调。把页面资源缓存下来，并不会自动让编辑、提交和多设备同步正确。

例如手机离线修改学习计划时，电脑可能已经修改了同一份计划。恢复网络后直接覆盖服务器，会丢失另一个设备的更新，因此需要版本或冲突协议。

## 缓存版本与待同步操作

静态资源缓存关注应用文件是否匹配同一版本；业务数据缓存关注内容何时获取、是否过期和属于哪个用户。两个层次应分别管理。退出登录后，不能继续把前一个用户的私人缓存展示给下一个用户。

离线写入队列保存操作 ID、目标资源、基于的版本、参数和同步状态。服务器按幂等身份处理重试，避免网络恢复后重复执行。基于版本的条件更新可检测并发修改：若客户端基于版本 2 编辑，而服务器已是版本 3，就应进入冲突处理，而不是无条件覆盖。

冲突解决取决于数据语义。独立新增记录可以合并集合；同一个字段的两次修改可能需要用户选择；计数器应考虑记录增量事件而非覆盖总值。最后写入获胜虽然简单，但会丢失信息，不能不加说明地用于所有学习答案与笔记。

## 把机制放到一条完整路径中

```flow
离线修改同步
本地记录｜保存草稿操作ID与基础版本
等待网络｜持久化队列并显示待同步
条件提交｜服务端去重并检查版本
冲突处理｜按数据语义合并或请求选择
```

## 配套代码：版本冲突不能静默覆盖

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

以基础版本为前提做条件写入，用内存模型代表服务端权威数据。

```javascript
let document={version:2,text:'服务器内容'};
function sync(baseVersion,text) {
  if(baseVersion!==document.version) return '冲突';
  document={version:document.version+1,text}; return '已保存';
}
console.log(sync(1,'离线旧稿'));
console.log(document.text);
console.log(sync(2,'新稿'));
console.log(document.version);
```

基于旧版本的写入不能直接覆盖新内容；匹配后才递增版本。真实离线系统还需要持久队列、幂等、合并 UI 和用户/租户隔离。

## 从示例走向实际使用

界面明确区分本地已保存、等待同步、服务器已确认与存在冲突。用户关闭页面后队列仍应可恢复，并有容量与失败处理策略。

测试同一操作重复发送、两端修改相同字段、升级后读取旧队列，以及退出登录再登录另一账号。离线功能的可靠性来自这些恢复路径，而不只是断网时页面还能打开。
