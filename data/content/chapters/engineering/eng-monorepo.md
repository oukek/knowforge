## 从具体问题认识Monorepo、依赖治理与可复现构建

Monorepo 是在一个仓库中管理多个相关项目或包，例如前端应用、后端服务、共享类型与组件库。它方便跨包修改和统一工具，但不会自动解决依赖混乱；仓库越集中，越需要清楚哪些包可以依赖哪些包。

应用依赖组件库，组件库依赖基础工具，这形成有方向的依赖图。构建顺序、受影响测试和缓存失效，都可以围绕这张图推导。

## 依赖边界与可复现输入

每个包应显式声明自己使用的依赖，不能因为根目录碰巧安装了某个库就直接引用。提升安装或共享 node_modules 可能掩盖遗漏，直到单独发布或 CI 环境才暴露。公共包应通过稳定入口导出能力，避免跨包引用内部文件导致边界失效。

锁文件记录具体依赖解析结果，配合固定运行时与包管理器版本，减少“同一提交不同机器构建不同”的情况。可复现并不只看依赖版本，还包括环境变量、生成时间、外部下载和未声明文件输入。构建缓存键必须涵盖真正影响结果的输入。

受影响构建从变化包沿反向依赖传播，找出需要重新验证的消费者。若共享基础包变化，只测这个包可能漏掉集成问题；若所有改动都全量重建，又会失去图分析的收益。循环依赖会使初始化、发布和缓存推导复杂，应通过职责拆分处理。

## 把机制放到一条完整路径中

```flow
多包构建
声明边界｜每个包维护直接依赖与入口
解析图｜确定依赖方向与受影响范围
固定输入｜锁定工具依赖和配置
按图执行｜复用有效缓存并验证消费者
```

## 配套代码：任务图的依赖优先顺序

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

递归按依赖输出构建顺序；模型只覆盖无环依赖图。

```javascript
const dependencies={app:['ui','core'],ui:['core'],core:[]};
const visited=new Set(),order=[];
function build(name) {
  if (visited.has(name)) return;
  visited.add(name);
  dependencies[name].forEach(build); order.push(name);
}
build('app');
console.log(order);
```

共享 core 只构建一次，依赖在消费者之前。真实任务图需要环检测、输入/输出缓存键和环境约束；本模型将 visited 提前标记，不能用来可靠检测循环。

## 从示例走向实际使用

先画包依赖图并定义允许方向，再选任务编排工具。为共享包设置公开 API、版本与兼容约定，避免“同仓库所以随意改”的隐性耦合。

用干净环境执行锁定安装与构建，检查是否依赖本地残留文件。课内拓扑顺序示例不包含循环检测，生产任务图需要在发现环时明确失败。
