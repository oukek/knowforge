## AI 应用不等于调用一次模型
AI 应用用模型能力解决用户问题，可能做分类、抽取、知识问答、内容生成或行动辅助。一次模型请求只是链路中的一段。用户真正关心资料是否找到、草稿是否正确、订单是否完成，而不是服务是否返回了一段文字。

典型链路是输入与认证 → 任务契约 → 事实获取 → 模型推理 → 结构/业务校验 → 展示或执行 → 记录与评估。环节可以裁剪组合，但权限和业务正确性不能因为接了模型就消失。
## 前端与后端各负责什么
前端处理输入、任务进度、流式呈现、取消、确认和错误解释；后端保护凭据、身份与资源权限，安排模型和工具调用，管理预算、持久状态及审计。模型负责候选内容或行动选择，业务服务才提交事实变更。

| 层 | 关键契约 | 常见故障 |
|---|---|---|
| UI | 草稿、生成中、待确认、已完成 | 半成品当成功 |
| API 网关 | 认证、配额、请求身份 | 密钥暴露或串账号 |
| 模型适配 | 输入与归一化结果 | 拒绝/截断被抹平 |
| 业务执行 | 授权、幂等、版本 | 重试重复写入 |

API Key 不应发给网页用户，跨域部署还要正确处理来源、会话与运行资源路径。
## 同步与异步任务如何取舍
短文本抽取可同步返回完整结果；长视频解析或多步 Agent 适合持久任务 ID、事件流和状态查询。SSE 解决增量传输，不自动保存任务；后台队列解决排队执行，也不自动保证业务效果恰好一次。

把连接取消、运行取消和业务撤销分开。客户端断开可能只是不再接收内容，远端工具仍已提交；恢复时要按操作身份查账，不能盲目再跑全部步骤。
## 可运行实验：状态迁移要显式
实验定义 draft → running → needs_review → completed，以及 failed/cancelled 分支。running 不能直接被任意网络断开改为 completed。对于高风险动作，needs_review 后的提交必须经独立验证；此处只演示状态机，不实现真实确认或支付。

添加未知事件应拒绝，终态后重复提交也应拒绝或走明确幂等接口。将 UI 文案和持久任务状态分别建模，能避免刷新后展示错误完成状态。
## 最小可交付项目应该证明什么
先选一个边界清楚的任务，如把工单转成待审核草稿。建立正确、缺失、恶意和工具失败样本，测任务成功、人工审核与返工、延迟和每成功任务成本。用 fake 模型开发确定性契约，接真实模型后再做质量评估。

交付还包括配置、部署、版本、观察与回退。没有真实业务验收时如实称为原型，不用一次演示成功推断生产稳定性；FDE 强调把这些技术环节接到客户流程和可测价值。
