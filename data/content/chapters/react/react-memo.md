## 先找实际昂贵的工作
组件重新渲染不一定很贵，也不一定导致 DOM 更新。优化前用 Profiler 和浏览器性能记录分清昂贵计算、组件范围与布局绘制。memo 允许在 props 满足比较条件时跳过某些重新渲染；useMemo 缓存计算值，useCallback 缓存函数引用。它们解决的是复用条件，不是任何性能问题的通用开关。

缓存需要比较依赖并占用内存，滥用会让代码难读而没有收益。更关键的是结果必须先正确：缺失依赖得到旧闭包，即使少渲染几次也不是有效优化。
## 三种缓存API分别缓存什么

memo主要让组件在props满足比较条件时有机会跳过父更新带来的重复渲染；useMemo缓存某次计算结果；useCallback缓存函数引用。它们都不是跨请求持久化，也不能替代正确状态设计。依赖错误会保存过期结果，盲目添加还会引入比较和维护成本。

对象和函数每次在组件体里创建时通常有新引用。给memo子组件传入新对象，字段看似相同但浅比较可能认为变化；稳定引用需要根据真实依赖构造。反过来，原地修改旧对象使引用不变，会破坏比较前提，导致需要更新的内容被误认为相同。

## 先定位昂贵工作，再选择优化边界

如果父组件每次输入都重新计算巨大过滤结果，useMemo可能减少依赖未变时的重复计算；如果每次输入恰好都改变过滤条件，它仍需重算，可能需要索引、分页、虚拟列表或Worker。若瓶颈是大量DOM和布局，缓存一个小函数引用并不能解决。

memo不会阻止组件自己的state更新，也不会使必要的Context更新消失。自定义比较函数必须正确考虑影响输出和闭包行为的所有props，漏掉函数prop尤其可能让事件继续使用旧状态。比较本身若比渲染更贵，也没有收益。

现代工具链可能提供编译器层面的优化，应按项目实际启用情况理解，不假设所有React项目都拥有同样行为。先保持渲染纯净与状态结构清晰，再通过Profiler验证优化前后提交耗时，而不是以出现多少memo作为质量指标。

## 一段有实际意义的缓存
```jsx
import { useMemo,memo } from 'react';
const Results = memo(function Results({rows}) {
  return <ul>{rows.map(row=><li key={row.id}>{row.title}</li>)}</ul>;
});
export default function Search({items,query}) {
  const rows=useMemo(
    ()=>items.filter(item=>item.title.includes(query)),
    [items,query]
  );
  return <Results rows={rows} />;
}
```
如果 items/query 未变，rows 的引用可以复用，Results 才有机会受益。若父组件每次都创建新的 items，即使内容相同，依赖仍会变化。反过来直接原地修改同一数组又可能使缓存错误地认为没有变化。缓存与不可变数据约定是一组协作条件。
## 函数引用稳定不等于函数自动使用最新数据
useCallback 只按依赖复用函数对象。若函数使用某个 state 却不列入依赖，它可能持续读旧值。可以在语义合适时用函数式状态更新，或重新组织职责，不能简单把依赖数组清空“优化”。memo 自定义比较器也必须考虑影响输出与行为的 props，包括回调闭包。
```flow
是否值得缓存
性能记录找到热点｜确认时间花在哪里
确定稳定输入｜数据身份与语义一致
加入必要缓存｜保持完整依赖与纯计算
再次测量｜收益是否覆盖比较与维护成本
验证行为｜切换输入、重排、快速交互不出现旧结果
```
## 不能靠 memo 解决的问题
渲染几万条真实 DOM 的布局成本需要分页或虚拟列表；高频全局状态变化需要缩小订阅范围；同步大循环可能需要算法改进或 Worker。SSR 隔离、请求竞态和资源泄漏也不是 useMemo 的职责。

将 memo 当性能提示，不能将它当保存业务状态或保证副作用只执行一次的机制。框架与编译器优化会演进，代码的正确性不应依赖某个计算结果永远缓存。
