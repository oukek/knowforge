## 从具体问题认识提示词结构、任务契约与版本管理

生产提示词是业务逻辑的一部分，需要像代码一样有版本、输入契约与回归验证。它定义模型当前要完成的任务、可使用的信息、输出格式和信息不足时的行为。随手修改一个形容词，也可能影响评阅尺度或工具选择。

例如主观题评阅应明确只评价给定题目与答案，依据哪些要点，如何区分错误与遗漏，而不应开放成任意聊天。

## 模板、变量与评估版本

把稳定规则与动态数据分开：模板负责任务与结构，变量提供题目、参考标准和用户回答。动态字段有长度与类型限制，不能让用户直接替换系统规则。资料和答案都按不可信输入组织，提示中的分隔帮助理解，真正权限仍由后端控制。

示例应覆盖关键边界，且与评分或抽取规则一致。过多相似示例会占用预算，也可能让模型过度模仿表面措辞。明确缺信息、矛盾、越界请求与无法完成时的结果类型，比不断追加“务必准确”更可验证。

版本记录关联模型、输出 Schema 与评估集。一次提示变化先在固定样本上比较，再灰度观察真实任务。若同时更换模型、检索索引和提示，很难判断效果来自哪项变化，应尽量做可解释对照。

## 把机制放到一条完整路径中

```flow
提示发布
定义契约｜任务依据输出与失败规则
安全装配｜校验动态变量并区分来源
固定评估｜比较版本在真实切片的表现
灰度记录｜关联任务并支持回退
```

## 配套代码：提示词结构、任务契约与版本管理：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

template={'version':'v2','task':'extract title','output':'JSON object','on_missing':'return null'}
show(template)
show(template['on_missing'])
```

模板只展示提示资产应有的可追溯元素，没有发起推理。真实提示应与数据、schema 和评估一起管理；缺失时返回 null 的指令仍需在服务端验证，模型输出不符合时要进入明确错误分支。

## 从示例走向实际使用

为提示建立正常样本、恶意闲聊请求、极短答案、冗长无关答案和部分正确答案。检查评阅是否始终围绕题目，不把用户输入当成新的应用指令。

课内模板对象展示可版本化字段，真实提示内容需要与业务评分规则一致，并保留可回滚历史。
