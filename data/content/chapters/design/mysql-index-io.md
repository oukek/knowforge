## 从具体问题认识MySQL 索引访问路径

索引是帮助数据库定位记录的数据结构。InnoDB 的聚簇索引叶子页保存行数据，通常按主键组织；二级索引叶子记录保存索引键与对应主键。通过二级索引找到主键后，再访问聚簇索引取得其他列，常称为回表。

例如 users 有主键 id 和 email 索引，按 email 查询 name 时，索引能定位用户，但若 name 不在索引中，还需要取得行数据。查询只需索引已有的列时，则有机会使用覆盖访问。

## 逻辑访问路径与磁盘读不是同一回事

B+ 树把大量键组织到页中，非叶子节点帮助缩小范围，叶子节点保存相应记录。数据库访问以页为重要单位，页可能已经在缓冲池中，因此一次逻辑回表不一定产生一次磁盘 I/O。反过来，扫描许多未缓存页，即使没有额外回表，也可能有大量物理读取。

二级索引顺序由索引键及相关主键信息组织，不等于目标聚簇页按同样顺序访问。范围查询返回许多不同主键时，回表可能分散访问数据页；缓存、批量访问优化、物理布局与存储设备都会影响实际随机访问成本。不能简单回答“二级索引必然随机 I/O、主键必然顺序 I/O”。

覆盖索引通过包含所需列减少获取额外行数据的需要，但索引变宽会增加空间、写放大与缓存压力。索引条件下推则是在适当阶段提前过滤，减少不必要行访问，与覆盖不是同一个优化。执行计划说明选择的路径，真实耗时与读页统计才帮助判断收益。

## 先建立两棵树的模型

这里讨论 MySQL 8.4 的 InnoDB，不能把所有数据库的“非聚簇索引”一概而论。聚簇索引叶子组织整行记录，通常由主键决定；没有显式主键时会选择符合条件的唯一非空索引，否则生成内部行 ID。二级索引叶子携带二级键以及聚簇键，用后者定位记录。因此主键过宽会放大所有二级索引的空间、缓存和写入成本。

假设 orders 的主键是 id，二级索引为 (tenant_id, created_at)。定位某租户最近订单时先走二级树；如果只取索引已有的 id、tenant_id、created_at，通常可覆盖；如果还取未入索引的 amount，就需要去聚簇树取记录，这一步称回表。

## 回表与随机 I/O 不是同一层概念

沿二级索引范围扫描时，叶子逻辑上按二级键顺序相邻，但得到的主键序列可能是 8、100、3。按这个序列取聚簇页具有随机访问特征。不过 Buffer Pool 命中后不发生磁盘读；逻辑页相邻也不保证物理块连续。实际代价还取决于缓存冷热、页分裂、预读、存储介质与命中行数，不能答“二级索引必然随机磁盘 I/O”。

MRR 可以先收集并按主键排序，再批量读取记录，改善局部性；是否选择由优化器、成本与版本配置决定。顺序访问一般吞吐更好，SSD 也有随机访问成本，但不要把机械盘寻道模型直接当成所有环境的结论。

## 怎样减少回表，怎样验证

优先减少不必要的列与候选记录，再为稳定的高价值查询设计覆盖索引。复合索引顺序需兼顾等值过滤、范围、排序、选择性与写放大。ICP 是在索引层先过滤可判断的条件，减少取整行次数；它与完全覆盖不同，Using index condition 不等于 Using index。

```sql
CREATE INDEX idx_orders_tenant_time ON orders(tenant_id, created_at);
EXPLAIN ANALYZE SELECT id, created_at FROM orders
WHERE tenant_id=7 AND created_at >= '2026-10-01' ORDER BY created_at LIMIT 20;
-- 对照 SELECT id, created_at, amount，并观察真实 rows、loops、耗时与缓存条件。
```
EXPLAIN ANALYZE 会执行语句，应先在合适数据和环境验证。不要用单次暖缓存测量证明覆盖索引永远更快，也不要为每个查询建一个包含全部列的大索引。

## 反例与选型边界

查询命中大比例数据时，全表扫描可能比大量回表更划算。主键自增有局部性优势，但热点写入、跨地域发号、信息暴露也要评估；业务公开 ID 与数据库聚簇键可以分开。覆盖索引还受 MVCC 可见性等因素影响，不能承诺任何情况下都绝不访问聚簇记录。先描述典型路径，再说明例外，比背诵绝对结论可靠。

## 把机制放到一条完整路径中

```flow
二级索引查询
索引定位｜按条件找到相关索引记录
检查覆盖｜判断所需数据是否已在索引中
获取行数据｜必要时按主键访问聚簇页
缓冲判定｜页未缓存时才涉及相应物理读取
```
