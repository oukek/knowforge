## 容器的区别来自操作需求
列表保存有序元素并允许修改，元组表达固定位置组合，字典按键查找，集合表达不重复成员。选择时先问是否需要顺序、重复项、按键访问和频繁头部操作，而不是看到一组数据就全部放list。

字典保留插入顺序，但这不是按键排序；集合不承诺业务展示顺序。字典键与集合元素必须可哈希，列表不能直接作键。一个元组若包含不可哈希元素，也不能仅因外层是元组就当键。
## 先掌握每种容器的基本读写

列表下标从0开始，负下标从尾部计算，`values[-1]` 是最后一项。切片 `values[start:stop]` 不含 stop；越界单项访问会报错，切片边界则可以被截到有效范围。append 把一个对象作为单项加入，extend 逐项加入另一个可迭代对象。把 `[2, 3]` append 进去得到嵌套列表，而不是自动扁平化。

字典使用键而非位置索引。`record["title"]` 在缺键时抛 KeyError，`record.get("title")` 默认返回 None。若字段可能显式保存 None，就要用 `"title" in record` 或独立哨兵区分不存在与存在但为空。遍历字典默认得到键，需要键和值时使用 items()。

```python
values = [10, 20, 30]
values.append(40)
print(values[1:3])
record = {"title": "Python", "minutes": 30}
for key, value in record.items():
    print(key, value)
print("owner" in record, record.get("owner", "未指定"))
```

## 哈希结构为什么要求键稳定

字典和集合通过哈希值把候选范围缩小，再按相等规则确认对象。一个对象作为键后，如果影响哈希或相等性的内容随意改变，就可能无法按原路径找到它，因此可变列表不能直接用作字典键。不可变并非可哈希的唯一判据，实际取决于类型的哈希与相等实现；常见数据建模中选字符串、整数或全部成员可哈希的元组更容易保证稳定。

集合提供交集、并集和差集，适合表达标签、权限或已处理ID之间的关系。例如 `wanted - finished` 得到尚未完成的ID，`requested & allowed` 得到允许的请求子集。但权限结果仍需按可信身份生成 allowed，不能从客户端提交的字段推断。

排序也要区分是否修改原容器：`sorted(values)` 返回新列表，可以接受多种可迭代对象；`values.sort()` 在原列表排序并返回 None。按多字段排序可以给 key 返回元组。每次选择结构时，把操作频率与数据规模放在一起看：偶尔搜索十条记录不需要复杂索引，频繁扫描百万项则需要重新设计结构。

## 保序去重与真正的队列
```python
from collections import deque
values = ["b", "a", "b", "c"]
unique = list(dict.fromkeys(values))
queue = deque(unique)
print(unique)
print(queue.popleft())
print(list(queue))
```
dict.fromkeys 记录第一次出现顺序，适用于可哈希值。复杂记录通常应提取业务ID，而不是随意把整个对象转字符串。deque 的两端操作适合队列，list.pop(0) 则需要移动后续元素，规模增大时成本明显。
## 复杂度要连同条件一起理解
列表下标访问通常常数时间，搜索值需要遍历；字典与集合常见查找是平均常数时间，仍有哈希计算、冲突、扩容与内存成本。字符串键很长时计算哈希也不是无成本，最坏情况和均摊情况不能混写。
```flow
选择结构
需要保留全部顺序与重复项｜列表
固定字段组合且不希望替换位置｜元组或具名结构
按稳定业务键查记录｜字典
只关心成员存在或去重｜集合
频繁从两端加入和取出｜deque
```
## 容器共享和修改的边界
`[[]] * 3` 创建三个指向同一内部列表的引用，不是三份独立列表；需要 `[[] for _ in range(3)]`。遍历字典时改变大小可能失败，列表过滤通常生成新列表更清晰。

测试缺失键、值为None、空容器、重复业务ID和输入巨大时的内存。数据结构是业务规则的一部分，不能为了一个更短的表达式悄悄丢失顺序或重复记录。
