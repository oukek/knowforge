## 从具体问题认识按域限速、令牌桶与自适应退避

速率限制控制单位时间内发出多少请求，并发限制控制同时进行多少请求。两者不同：一个请求很慢时，并发可能很高但速率不高；请求很快时，即使并发只有几个，也可能每秒访问很多次。采集通常需要同时控制两者。

按域限速让不同站点有各自预算，避免一个目标因为另一个目标空闲而突然收到过量请求。

## 令牌桶与反馈调节

令牌桶以固定速率补充令牌，桶有容量上限，每发一个请求消耗一个令牌。补充速率控制长期平均，容量允许有限突发。计算补充量应基于实际经过时间，并使用适合测量间隔的时钟，避免系统时间调整导致异常放量。

多 worker 若各自拥有完整速率预算，总速率会乘上 worker 数量。需要统一协调，或把全局预算明确分配给各执行器。并发槽、连接池和令牌等待也要协调，避免任务占着稀缺连接却只是在等待令牌。

收到 429、Retry-After 或持续超时后，应降低该域速率并延后任务，而不是添加更多并发补吞吐。恢复采用逐步探测，防止全部任务同时醒来。自适应策略需要最小最大范围与可观察日志，避免系统在不同速率间剧烈振荡。

## 把机制放到一条完整路径中

```flow
按域发放请求
计算补充｜按经过时间恢复有限令牌
检查预算｜同时满足速率与并发限制
发出请求｜原子消耗令牌并占用槽位
反馈调整｜遇限流退避并缓慢恢复
```

## 配套代码：按域限速、令牌桶与自适应退避：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

def refill(tokens,elapsed,rate,capacity):
    return min(capacity,tokens+elapsed*rate)
show(refill(0,2,3,5))
show(refill(1,0.5,2,5))
```

模型只计算补充令牌，真实发放还要原子扣减、时钟单调性和多消费者同步。浏览器示例固定时间输入便于验证，不使用 sleep 模拟实际调度；生产系统应按实际吞吐和对端反馈调节。

## 从示例走向实际使用

先设保守的固定按域预算，再根据授权与目标反馈调整。用受控时钟测试令牌补充、桶满、长时间空闲与多执行器共享预算。

课内 refill 只演示令牌数量变化，真正发放还需原子扣减与并发保护。限速的目标是稳定和礼貌访问，不是寻找站点拒绝前的最大压力。
