## 内存不是只看 new 和指针
编译器通过逃逸分析等决定某些值是否可以放在栈上；返回地址并不自动等于危险，局部对象也不一定只在栈上。逃逸结果受调用关系、编译优化和接口使用等影响，应通过工具观察，而不是从源码关键字推断精确分配。

GC 回收不再可达的内存，不会替程序关闭文件、连接或 goroutine。一个大缓存仍然可达，即使业务已不需要，也不会被自动识别为垃圾。持续高分配会增加GC工作，内存占用和延迟要结合业务负载分析。
## 栈、堆和逃逸分析如何协作

局部变量不必永远留在栈上，使用new也不必简单等同于某种固定堆分配结果。编译器分析值的使用范围和生命周期，决定是否需要逃逸到更长寿命的存储区域；优化结果还受代码形态和版本影响。指针只是访问方式，不能仅凭是否带星号判断分配成本。

goroutine栈可以增长，堆上的可达对象由垃圾回收管理。减少无用分配、缩短大对象引用生命周期、控制缓存容量能降低内存压力。GC不是释放文件、连接或锁的替代品，这些外部资源仍需明确关闭。一个slice只取了大数组的小片段，也可能让整个底层数组继续可达。

## 发布二进制仍有环境边界

go build生成目标操作系统和架构适用的产物，GOOS与GOARCH控制目标。启用CGO或使用某些系统依赖时，还可能涉及原生库和交叉编译工具链，不能笼统保证任何Go程序都是一份文件复制到任意机器就能运行。证书、时区、配置文件和数据库仍属于交付环境。

服务入口应校验配置、初始化依赖、报告就绪，然后接流量。退出时停止接新请求，在预算内收束进行中工作并关闭资源。发布同一份构建产物、记录版本和保留回滚路径，比在服务器临时重新拉依赖构建更容易追踪。

诊断时将CPU、分配、goroutine阻塞与锁竞争分开。pprof帮助观察相应剖析，trace能展示调度与事件，但采集本身有成本，诊断端点也不能无保护地暴露公网。优化结论应来自代表性负载，而不是只看一次本机的空载内存数字。

## 用标准库观察基本运行环境
```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	values := make([]int, 0, 4)
	values = append(values, 1, 2)
	fmt.Println(len(values), cap(values))
	fmt.Println(runtime.NumCPU() > 0)
}
```
示例只输出稳定判断；真实 CPU 数与内存统计由环境决定，不适合写死答案。程序可用 pprof 分析CPU、堆、goroutine等不同维度，但采样结果需要对应具体版本、时间段与负载。
## 性能诊断先分类
CPU 高看热点调用栈；CPU 低但响应慢可能是在等待锁、连接池、网络或磁盘；内存高看存活对象与增长趋势；goroutine 数持续增长看阻塞位置与退出路径。堆快照展示的是某一时刻，不等于完整分配历史，需要对比与指标关联。
```flow
服务从启动到停止
读取与校验配置｜缺必需配置直接失败
建立依赖与健康状态｜连接、迁移策略、就绪检查
接收流量｜预算、限流、日志与指标
收到退出信号｜停止接新工作
等待与关闭｜在截止时间内收束请求、连接和后台任务
```
## 产物、配置与运维边界
Go 二进制能简化部署，但跨平台、CGO、证书、时区、配置文件与静态资源仍要考虑。配置从明确环境来源读取，密钥不编进仓库；日志不要打印完整凭据。pprof 调试端点可能泄露内部信息，应限制访问，而不是直接暴露公网。

发布前运行测试、竞态检查和合理集成验证，记录构建版本并准备回滚。优雅退出不是永远等所有任务完成，要有总期限；必须可靠完成的业务任务应持久化并可接续，不能依赖一个进程永不退出。
