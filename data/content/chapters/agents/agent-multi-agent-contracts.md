## 从具体问题认识多 Agent 协作

多 Agent 协作把任务分给多个执行者，但也增加通信、重复工作、冲突和失败成本。只有当分工能带来专业能力、并行收益或权限隔离，且超过协调成本时，才值得采用。

给几个 Agent 起“研究员、专家、审稿人”的名字不构成可靠分工。每个子任务需要明确输入、输出、证据和完成条件。

## 状态所有权与收敛条件

子任务契约限定范围、允许工具、预算、截止时间和产物 Schema。协调者保存任务身份与依赖，子 Agent 返回证据和未解决事项，而不是仅一段自信结论。重试同一子任务要保持可追踪身份，防止重复写入。

共享状态按字段或资源分配所有权，多个结果合并时检查版本和冲突。相同事实 ID 出现不同值不能简单最后覆盖，否则完成顺序决定业务事实。可使用明确优先级、证据核对或人工决策处理冲突。

系统需要收敛条件：全部必要子任务完成、证据满足要求，或预算耗尽后明确部分完成。互相评价不等于独立验证，多个相似模型可能重复同一错误。并行收益也会受串行汇总与慢分支限制。

## 先证明单 Agent 的瓶颈

把系统分成“规划者、研究员、审查员”不会自动提高质量。多 Agent 带来额外模型轮次、上下文复制、冲突和调试成本。只有任务可并行、专业上下文确实不同或权限需要隔离时，分工才可能有收益。先与单 Agent 加明确工具的基线对比。

单次汇总多个观点不等于事实已验证。相同模型、相同来源的多个回答可能高度相关，多数投票不能消除共同错误。关键结论仍需证据或程序校验。

## 子任务契约应比角色描述具体

每项子任务包含目标、输入快照、可用工具、资源范围、完成判据、输出 schema、预算和截止点。研究子任务返回事实与来源，不直接修改共享订单；执行子任务只接受已验证动作，不根据闲聊重新决定金额。

```js
const assignment = {
  id: 'research-policy', inputVersion: 7,
  output: ['claims', 'evidenceIds', 'unresolved'],
  canWrite: false, maxSteps: 4
};
```

LangGraph 子图可以提供组合边界；OpenAI Agents SDK 中 handoff 与把 Agent 当工具会影响控制权和结果回流方式。选用时明确谁掌握主任务，而不是只比较语法短不短。

## 共享状态需要所有权

把输入快照设为只读，各 worker 返回局部结果，协调者按规则合并。每个字段应定义单一写入者，或明确 reducer 的去重、交换律和冲突语义。两个 Agent 同时写 summary，最后写入者胜出会隐藏不一致。

| 状态 | 建议所有者 | 合并原则 |
|---|---|---|
| 用户目标 | 主任务协调者 | 用户变更触发新版本 |
| 检索事实 | worker 结果集 | 按稳定 ID 去重并保留来源 |
| 最终决定 | 明确决策节点 | 规则校验、冲突不静默覆盖 |
| 业务提交 | 受限执行服务 | 幂等和资源版本条件 |

不要让子任务通过共享全局变量绕过输入输出契约；跨租户或跨任务结果不得混入同一 reducer。

## 交接与恢复

交接应传目标、已确认事实、未决问题和授权边界，不是复制全部聊天历史。输入快照版本改变时，旧 worker 的结果可能已过期，协调者必须校验版本。handoff 只改变控制权，不自动转移真实用户授权。

失败时区分可独立重跑的只读子任务与已发生副作用的执行。回收所有子任务预算，避免协调者重试时又开启一组无人跟踪的 worker。终止条件包含成功、无进展、重复任务、成本与时间上限。

## 用收益和失败成本决定是否保留分工

固定任务集对比单 Agent、多个工具以及多 Agent 三种方案，记录业务成功、总轮次、关键路径、总成本、冲突与人工接管率。并行只缩短可并行部分，串行协调和重复检索可能抵消收益。

加入 worker 超时、重复结果、输入版本变化、互相交接循环和权限升级请求。只有分工在质量、隔离或交付上产生可测收益时才值得保留；更少的角色和更清楚的契约通常更容易维护。

## 把机制放到一条完整路径中

```flow
多 Agent 协作
拆任务契约｜范围产物权限预算与依赖
隔离执行｜各自负责明确状态和工具
核对合并｜检查证据身份版本与冲突
判断收敛｜达到成功条件或明确部分失败
```

## 配套代码：多 Agent 协作：任务契约、状态所有权与收敛

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。



```javascript
function mergeFacts(groups) {
  const merged = new Map();
  for (const facts of groups)
    for (const f of facts) {
      const old = merged.get(f.id);
      if (old && (old.value !== f.value || old.version !== f.version))
        throw Error("fact conflict: " + f.id);
      merged.set(f.id, { ...f });
    }
  return [...merged.values()];
}
const a = [{ id: "price", value: 10, version: 1 }];
console.log(mergeFacts([a, a]).length);
try {
  mergeFacts([a, [{ id: "price", value: 12, version: 2 }]]);
} catch (e) {
  console.log(e.message);
}
console.log(a[0].value);
```

相同事实重投递去重，不同版本或值冲突时拒绝静默覆盖，输入对象保持原样。实际事实还应带租户、来源和类型化比较规则。

## 从示例走向实际使用

先建立单 Agent 或固定工作流基线，再比较多 Agent 的成功率、时延、费用和故障恢复。若没有实际收益，减少分工是合理工程选择。

课内 mergeFacts 在同 ID 不同事实时抛出冲突，避免悄悄合并成一个看似完整但自相矛盾的结果。
