## 只记录最终答案无法排障
同一个“回答失败”可能来自检索空集、模型超时、工具权限不足、写入结果不明或渲染断流。需要把一次用户任务关联到各轮决策、模型请求、工具调用和业务操作。任务 ID、trace ID、调用 ID 与 operation_id 用途不同：调用 ID 关联一次尝试，operation_id 应跨重试保持同一业务意图。

OpenTelemetry 的 GenAI 语义约定提供可参考的规范化方向，相关约定有独立仓库且会演进。落地时固定采用的版本，业务仍应定义自己的成功、拒绝和副作用状态，不能把某个 span 结束就认定退款成功。
## Span 的父子关系与并行关系
根 span 表示任务，子 span 表示检索、模型或工具工作。并行兄弟 span 的耗时相加可能大于根耗时；把它们加起来显示“用户等待时间”会夸大延迟。端到端时长应看根区间或请求关键路径，累计活动耗时适合观察工作量但不等于等待时间。

| 字段 | 用途 | 不宜做什么 |
|---|---|---|
| task_id | 用户任务关联 | 放入所有指标标签形成高基数 |
| tool_call_id | 一次调用及返回关联 | 当作跨重试业务幂等键 |
| operation_id | 业务意图及查账 | 每次重试重新生成 |
| prompt/model version | 回归定位 | 只记一个 latest 字符串 |

异步队列与子进程需传播可序列化的关联信息，身份在新边界重新验证，不把 trace 标签当授权事实。
## 事件与指标分别承担什么
轨迹用于解释单次任务，指标用于看群体趋势。指标可以按工具类型、模型版本和受控错误类别聚合，避免用户 ID、完整问题等高基数或敏感字段。事件记录计划变更、审批、重试、取消与恢复，关键状态转移要有原因和版本。

费用按真实模型和工具使用汇总所有尝试，不能只记录成功 span。统计缺失时标记 unknown，而不是默认为零；部分费用可能稍后到账，需要允许对账更新。根任务失败仍可能已产生账单和副作用。
## 脱敏应发生在导出之前
完整提示和工具输出可能包含个人数据、内部文档和秘密。默认记录结构元数据、长度、来源 ID 与受控摘要；必要原文使用独立加密存储、访问审计和保留期。普通日志 redaction 不能保证语义改写的秘密都被清除，更不能补救已经发给外部导出器的数据。

```js
const safe = {tool: call.name, status: call.status, durationMs: elapsed};
// 不要默认附加 authorization、完整 args 或完整工具返回
```

调试录制需要可回放的最小事实快照，但生产写工具的回放应使用 fake 或只读模式，不能重放真实付款。
## 可运行实验：耗时与费用不要混算
实验设根任务 100ms，两个并行工具分别用时 60ms 和 50ms，累计子工作为 110ms，仍不代表用户等待 110ms。工具成本可以求和，等待时间不能按同样方式算。再过滤一个包含 authorization 的事件，只输出允许的元数据字段。

这里所有时间均为构造数据，不是对真实模型的性能测量。若要计算完整关键路径，还需图依赖和区间关系；用最大子耗时也不总等于根时间，因为还有串行前后处理。
## 诊断与验收
在开发数据上注入一个慢模型、一次工具重试、一次取消和一次已提交但响应丢失，确认能从任务追到业务事实。检查失败日志没有秘密，采样后仍能保留足够错误轨迹。可以用尾部采样偏向失败与高延迟，同时对正常任务保留统计代表性。

面试报告应分别给任务成功率、业务违规、延迟分布、每成功任务成本和未知费用比例。清楚说出采样和脱敏造成的观测盲区，不要把“有 tracing”当成系统已经可解释。
