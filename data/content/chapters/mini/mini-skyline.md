## 从具体问题认识Skyline 架构与迁移评估

Skyline 是微信小程序的一种渲染引擎。渲染引擎负责把界面结构和样式转换成布局、绘制和屏幕上的像素，它不负责让服务端接口自动变快，也不替代业务代码。学习 Skyline，首先要把“如何画页面”与“页面需要什么数据”分开。

传统方案中，视图依赖 WebView 的网页渲染能力；Skyline 使用不同的渲染实现来支持小程序场景。这可能改变启动资源、交互延迟和组件行为，所以迁移既是性能工作，也是兼容性工作。

## 把渲染替换拆成能力与收益两张表

渲染管线包含结构解析、样式处理、布局、绘制与合成。即使某个环节变快，总耗时仍由整条关键路径决定：页面等接口 800 毫秒，绘制从 100 毫秒降到 50 毫秒，用户并不会得到两倍快的首屏。先测瓶颈，才知道引擎变化能改善哪部分。

兼容性表按实际使用能力列出：布局规则、文本排版、滚动容器、原生组件、插件、手势和路由。不能因为属性名称与 CSS 相同就推断实现完全相同，也不能因为一个简单页面能打开就认定复杂页面已兼容。组件尺寸、输入焦点、键盘弹出和页面返回都应有具体用例。

试点应使用同样的数据、设备、网络和操作，分别比较启动、持续滚动、内存和错误率。灰度按可识别的版本与设备范围开展，服务端记录渲染模式，才能区分是新引擎问题还是同一时间发布的业务变化。支持范围和配置以目标基础库的官方文档为准，不把某个版本的限制当成永久规则。

## 把机制放到一条完整路径中

```flow
Skyline 迁移
确认瓶颈｜确定希望改善的渲染环节
能力盘点｜列出组件样式和交互依赖
真机对照｜固定条件比较收益与回归
灰度发布｜按版本观察并准备恢复
```

## 配套代码：用测量维度评估迁移

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

网络瓶颈和渲染瓶颈在总耗时中占比不同；模拟不代表 Skyline 基准。

```javascript
function total(network, logic, render) { return network + logic + render; }
console.log(total(800, 100, 100));
console.log(total(800, 100, 50));
console.log(total(100, 100, 400));
console.log(total(100, 100, 200));
```

相同渲染减半在不同瓶颈下总收益不同，不能从引擎能力推断固定首屏提升。这些数值是演示输入，迁移要测实际机型、兼容性和完整链路。

## 从示例走向实际使用

适合先选择依赖清晰、交互频繁且便于对照的页面，例如商品列表；不要一次迁移所有页面再寻找回退办法。为每项能力写下验证结果，尤其检查列表嵌套、弹层与原生输入组件。

本课的时间分解实验不是 Skyline 的真实基准测试。它用来解释局部优化如何影响总耗时，正式结论必须来自同一页面在目标设备上的对照数据。
