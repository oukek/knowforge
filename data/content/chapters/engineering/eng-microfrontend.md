## 从具体问题认识微前端、Module Federation 与选型成本

微前端把一个大型前端系统拆成可由不同团队独立演进的部分。它主要解决组织与发布边界问题，而不是天然提高页面速度。Module Federation 等机制可以在运行时组合不同构建产物，但组合后仍共享用户看到的同一个产品体验。

如果一个小团队维护单一应用，增加远程模块、版本协商和运行时故障路径，可能比普通模块化更昂贵。选型应从团队协作与独立发布的真实需求出发。

## 独立交付带来的运行时契约

应用壳负责导航、公共布局和跨应用体验，子应用负责自己的业务范围。两者需要稳定契约，包括挂载卸载、身份传递、路由、错误处理和共享状态。把大量业务对象放进全局共享状态，会让名义上独立的子应用重新变成强耦合系统。

运行时加载远程代码增加了网络与版本失败：远程入口不可用、依赖版本不兼容、共享库单例要求冲突，都可能在构建成功后才出现。应给子应用设置局部错误边界、加载超时与降级界面，避免一个功能模块拖垮整个壳。

样式隔离与安全隔离不是同义词。CSS 命名或 Shadow DOM 可以减少样式冲突，但不代表不可信脚本获得了安全沙箱。若确实需要隔离第三方不可信内容，应选择符合威胁模型的独立源与沙箱机制，并控制通信协议。

## 把机制放到一条完整路径中

```flow
运行时组合应用
应用壳｜提供导航身份与公共契约
远程加载｜获取匹配版本的子应用
局部运行｜按边界共享必要能力
故障隔离｜局部降级并清理卸载资源
```

## 配套代码：远程模块失败时保留应用壳

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

加载异常只降级局部区域，不替换整个导航与壳。

```javascript
async function remoteView(loader) {
  try { return await loader(); }
  catch { return '局部降级'; }
}
console.log('应用壳可用');
console.log(await remoteView(()=>Promise.reject(new Error('远程入口失败'))));
console.log(await remoteView(()=>Promise.resolve('远程内容')));
```

隔离失败让其他区域继续工作。真实微前端还需版本、路由、样式和共享依赖契约，这个异步函数不提供沙箱或权限隔离。

## 从示例走向实际使用

比较普通模块化、构建时共享包与运行时组合三种方案，写出独立发布收益与额外运维成本。只有收益足以覆盖版本治理和故障复杂度时，再引入微前端。

先做远程模块不可用的演练，确认导航、登录和其他模块仍可使用。再检查卸载后的监听与路由资源，避免多次进入导致重复副作用。
