## 从具体问题认识闭包、内存与生命周期

一个函数返回后，它创建的回调为什么还能读到函数里的变量？因为函数值不只有代码，还关联创建时可以访问的词法环境。闭包就是函数与这份环境关系共同形成的能力。它并不是“函数套函数”的语法名称：关键是函数离开创建位置后仍能使用外层绑定。

例如计数器工厂每调用一次创建一份count，返回的increment持续修改这份count；另一次工厂调用建立另一份环境，两个计数器互不影响。相反，同一次调用返回的多个函数可能共同读写同一绑定，因此私有状态也需要定义修改规则。

## 环境存活、共享绑定与生命周期

函数执行时会有调用栈帧，但闭包可访问的环境不应简单等同于“整块栈永远不释放”。引擎按可观察行为保存需要的信息，具体优化不由业务代码保证。垃圾回收关注可达性：若一个长期存在的事件监听器持有回调，回调又引用大数组，这些对象就可能继续可达。

回调晚执行时读取的是届时绑定的值。循环用var保存多个回调，通常共享已经推进到终值的变量；循环let或额外工厂调用可建立不同绑定。异步场景还要区分“共享的可变绑定”和“每次渲染创建的一组新局部值”，例如React事件闭包捕获的是那次组件调用中的状态快照。

闭包适合封装少量私有状态、延迟执行的参数和资源句柄。问题不在于使用闭包本身，而在于引用谁、谁持有回调、何时解除关系。移除监听器需要同一函数引用，取消计时器只阻止未来调用；已经发出的网络请求有自己的取消和结果有效性规则。

## 把机制放到一条完整路径中

```flow
回调如何保留外层状态
调用工厂函数｜建立本次局部绑定
创建内部函数｜关联外层词法环境
返回并保存函数｜后续仍可访问相关绑定
释放最后持有者｜不再可达的环境才有回收机会
```

## 配套代码：闭包是绑定而非快照

下面代码在课内JavaScript运行区执行；需要DOM、Node或平台SDK的真实集成，应按正文的运行边界另行验证。

比较每个工厂独立状态与同一闭包内部不断变化的计数。

```javascript
function createCounter() {
  let count = 0;
  return () => ++count;
}
const first = createCounter();
const second = createCounter();
console.log(first(), first(), second());
let current = 1;
const read = () => current;
current = 9;
console.log(read());
```

两次调用工厂产生独立词法环境；同一个环境中的闭包读取当前绑定，所以 current 改成 9 后 read 也读到 9，而不是创建时的数值。

## 从示例走向实际使用

把一个功能的资源拥有者写清：组件注册监听就负责卸载时移除，任务创建计时器就负责结束时取消。不要只把某个局部变量设为null，却保留其它回调或缓存对同一对象的引用。

排查泄漏时在重复进入退出功能后观察堆快照，沿保留路径找到长期根对象与回调之间的关系。教学计数器证明状态可保留，不能据此宣称任何闭包都会泄漏或一定常驻整份外层环境。
