## 从具体问题认识模型选择

模型选型是受约束的工程决策，不能只看排行榜或每百万 token 标价。某模型总分高，却不支持任务要求的工具协议或部署区域，就不是合格候选；便宜模型若经常重试，完整任务反而可能更贵。

先明确硬条件，再在同一任务集上比较质量、延迟与成本，才能得到对当前应用有意义的结论。

## 硬过滤、配对比较与升级策略

硬条件包括数据驻留、模态、上下文长度、输出契约、工具能力和服务可用性。条件不满足时直接排除，不用软分数补偿。例如隐私要求不能用“便宜很多”抵消。

合格候选使用相同输入、工具、检索证据和评分标准比较，记录首次成功率、总尝试、延迟分布和成功任务成本。模型输出有波动时做必要重复，样本按真实任务比例与关键风险切片组织。

分层路由可以让简单任务用低成本模型，复杂或验证失败任务升级。但升级条件必须可观察，升级也要受预算与权限约束。没有满足契约的候选时明确失败，不能为了返回答案静默换成能力不足的模型。

## 不先按排行榜排一个永久第一

模型适配的是任务分布与运行约束。知识问答、代码修改、结构化抽取、多模态识别、低延迟分类的需求不同；同一模型经不同端点可能有不同版本、限额与协议能力。选型表应写明供应商、准确模型版本、上下文与输出上限、工具/结构化支持、地区和数据政策，再谈价格。

## 先硬过滤，再比较软指标

不满足数据驻留、隐私、工具、语言或上下文要求的候选直接剔除。剩余候选用固定业务评估集比较质量、合规失败、TTFT/P95、吞吐、可用性、单位成功任务成本和人工返工。便宜 token 不一定任务便宜：长输出、重复尝试、工具耗时和人工接管都会放大总成本。

## 分层路由与升级

简单高置信任务可先用便宜模型，低置信或失败升级；高风险任务可能直接选更稳方案并增加人工复核。升级门由可执行校验、证据充分度与风险信号触发，不只看模型自我评价。备用需重新检查能力与权限，不能降级到不支持约束的模型后假装结果等价。

缓存和路由按租户、任务、模型/提示/知识版本分区。固定生产别名可能无提示漂移，因此记录响应真实版本，做 canary 与回归；模型更新、降价或限额变化都可能触发重新评估，而不是每次发布都追“最新”。

## 实验如何避免误导

同样输入、工具、上下文与总预算，配对运行并保存失败样本，评审尽量盲测。考虑 stochastic 波动、缓存冷热、跨区域网络与长任务尾延迟。不能把不同提示长度、不同证据集的成绩直接归因于模型，也不能拿公开榜单替代领域样本。

## 面试表达与持续治理

给出任务、硬约束、候选、实验、灰度和回退六步。价格、版本和限额随时间变化，不在资料中固定一个永远正确的厂商排名。对业务说明何时拒绝自动完成，往往比只说“复杂任务上大模型”更能体现工程判断。

## 实践任务与验收

用问答、抽取和工具执行三组各十条任务构成小评估，不要只挑你的提示最擅长的样本。先检查每个候选对 JSON schema、中文、数据区域和工具参数的支持，再固定相同证据与输出长度进行盲评。表格列出每个任务的正确性、违规、耗时、尝试次数与费用，错误单独分类，不只填一个平均分。

算两种流量分布：大部分为简单抽取、或复杂执行占多数，观察最优路由是否变化。模拟便宜模型出现格式错误并升级，加入第一次调用成本后再计算单位成功任务费用。若备用模型无法遵守必要结构化契约，应显示当前能力不可用，而非把自由文本硬转成已验证结果。此实验最终应能回答：选择依据是什么、什么变化会推翻选择、如何低风险地换掉它。

## 把机制放到一条完整路径中

```flow
模型选择
定义硬条件｜能力区域协议与资源要求
固定任务集｜按实际业务切片配对测试
比较结果｜质量尾延迟和成功任务成本
受控路由｜上线观察升级条件与回退
```

## 配套代码：模型选择：质量、延迟、成本与受约束路由

下面代码在课内JavaScript运行区执行；需要DOM、Node或平台SDK的真实集成，应按正文的运行边界另行验证。

使用本地 JavaScript 模型验证关键不变量；不调用真实数据库、模型或生产服务。实验简化之处与真实系统步骤见正文。

```javascript
const models=[{id:'cheap',region:'cn',schema:false,cost:1,success:0.7},{id:'fit',region:'cn',schema:true,cost:2,success:0.9},{id:'remote',region:'other',schema:true,cost:1,success:0.95}];
const eligible=models.filter(m=>m.region==='cn'&&m.schema);
eligible.sort((a,b)=>a.cost/a.success-b.cost/b.success);
console.log(eligible.map(m=>m.id));
console.log((eligible[0].cost/eligible[0].success).toFixed(2));
```

**一个模型 token 单价低一半，但失败后总要重试，如何比较？**

计算完成一个合格任务的总成本，包含全部尝试、工具、排队和人工返工，并比较尾延迟与失败风险。用固定预算与同一任务集配对，不用单 token 单价替代交付成本。

检查点：成功任务成本、全部尝试、尾延迟。

**自动升级到更强模型以后越权率上升，该怎样处理？**

升级模型可能更积极调用工具，但越权必须由宿主阻止。检查工具集合和授权契约，用同一对抗集回归；对高风险任务增加确认并可回退。质量提高不能抵消授权失败。

检查点：宿主授权、对抗回归、风险门。

**供应商同名模型静默升级，你怎么发现和回滚？**

记录可获得的真实模型版本、端点和响应元数据，持续跑冻结探针与关键回归，按成本/延迟/正确率告警。支持固定版本时优先固定；不能固定时保留经验证备用与任务级降级策略。

检查点：版本记录、行为探针、可用回退。

## 从示例走向实际使用

保存每次选型的数据与版本，业务分布变化后重新评估。一个阶段适用的模型组合不必永久固定，但变更要可追踪与回滚。

课内 cost/success 是简化期望成本指标，假设样本与费用可比较；真实报表应直接统计全任务实际费用及失败成本。
