## 从具体问题认识分布式采集、租约与至少一次处理

分布式采集让多个执行器共同处理任务，收益是扩大吞吐与容错，代价是任务可能重复领取、执行器可能失联、状态可能延迟。共享一个任务队列，并不自动提供“每个任务恰好执行一次”的保证。

执行器领取任务后崩溃，系统需要让别人接手；如果它只是网络暂停而没有真正停止，接手后就可能出现两个执行器同时处理同一任务。

## 租约、代次与至少一次语义

租约给执行器一段有限处理权，需要续租保持。过期后任务可重新领取，但旧执行器仍可能恢复并提交，因此结果写入应校验当前领取代次或 fencing token。只有仍持有有效代次的执行器可以确认当前任务完成。

消息系统常提供至少一次交付，意味着重复是正常恢复路径。下载本身通常可重复，但写入、计费或触发下游任务必须幂等。任务 ID、尝试 ID 与结果业务键分别表达不同身份，日志中应区分，避免把重试次数误当独立任务数量。

全局去重与按域限速也必须跨执行器协调。每台机器各自限制每秒十次，十台就可能合计一百次。分片策略还要避免热点站点集中压垮某个 worker，调度状态应支持重平衡、延迟执行与失败隔离。

## 把机制放到一条完整路径中

```flow
多执行器采集
共享调度｜统一任务身份与域预算
租约领取｜原子取得当前执行代次
执行续租｜记录尝试并响应失效
条件确认｜校验代次并幂等保存结果
```

## 配套代码：分布式采集、租约与至少一次处理：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

current_token=7
submissions=[('old',6),('new',7)]
show([name for name,token in submissions if token==current_token])
```

这里只模拟提交端检查当前令牌，未实现真正分布式原子操作。生产校验应在受保护资源的同一原子提交中完成，不能先在客户端比较后再无条件写入；模型用于理解旧执行者为何需要被拒绝。

## 从示例走向实际使用

演练执行器暂停后租约过期、旧执行器恢复提交、新执行器写入成功但确认丢失等情况。验证旧代次被拒绝，重复结果不会破坏数据。

课内 token 比较只展示提交资格，不包含真实租约时间与原子领取。生产方案需在数据库或队列协议中实现这些条件，并监控租约过期与重复率。
