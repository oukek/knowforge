## 从具体问题认识灰度、回滚、熔断与稳定性预算

灰度发布让新版本先影响一部分用户，以便在扩大范围前观察真实表现。回滚把系统恢复到已知可用状态；熔断则在依赖持续失败时暂时停止继续施压。这些机制都需要明确触发条件与恢复规则。

发布是否成功不能只看“构建完成”或“平均耗时下降”。某些低端设备可能变差，而新版本恰好拥有更多高端用户，整体平均数仍会显得更好。

## 比较相同人群并控制故障传播

灰度分组应稳定且可解释，例如按用户或设备散列固定分配，避免用户每次刷新随机切换版本导致状态混乱。记录版本、分组和关键环境后，再比较错误率、业务成功率与性能分布。小样本阶段要关注不确定性，不能用偶然的几个成功请求证明安全。

回滚要考虑代码、配置和数据三层。数据库结构或写入格式已经变化时，旧代码未必还能运行；因此迁移通常需要先兼容扩展，再逐步切换，最后清理旧结构。资源文件发布也要保留过渡，避免旧 HTML 引用已被删除的文件。

熔断器在失败达到条件后暂时拒绝或降级请求，等待一段时间再用有限探测判断恢复。它与限流不同：限流约束流量，熔断响应依赖健康状况。恢复时若所有实例同时放开，也可能再次冲击依赖，因此需要受控探测与逐步恢复。

## 把机制放到一条完整路径中

```flow
受控发布
小范围启用｜稳定分组并记录版本
观察证据｜比较同类人群的业务与性能
控制影响｜暂停扩大降级或回滚
逐步恢复｜验证兼容与依赖健康后推进
```

## 配套代码：分组指标能暴露总体均值隐藏的退化

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

演示固定分组下的变化方向，这些数值不是真实用户数据。

```javascript
const before={fast:[100,100],slow:[800,800]};
const after={fast:[50,50,50,50,50,50],slow:[1000,1000]};
const mean=values=>values.reduce((a,b)=>a+b,0)/values.length;
console.log(mean(Object.values(before).flat()));
console.log(mean(Object.values(after).flat()));
console.log(mean(after.slow)-mean(before.slow));
```

总体均值改善是因为样本结构和快设备收益，但慢设备退化 200。灰度应按设备网络和关键业务指标分层，不能只看一个总体均值。

## 从示例走向实际使用

发布前写清观察窗口、停止扩大条件和恢复动作，确保这些动作真正可执行。对学习平台可同时看登录、课程加载、提交答案与 AI 任务成功率，避免只关注首页。

课内例子展示人群比例变化如何掩盖慢设备退化。正式分析应按相同条件比较，并保留原始分布与样本量。
