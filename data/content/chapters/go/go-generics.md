## 泛型复用的是有类型关系的算法
如果两个函数只是元素类型不同而算法相同，可以用类型参数表达共性。约束规定参数类型允许哪些操作，编译器据此检查函数体。泛型不是把所有参数都改成any；any没有提供加法、比较大小等操作能力，函数仍只能使用约束保证的能力。

普通接口表达运行时行为契约，泛型表达编译时类型关系。存储接口和业务服务不一定因支持泛型就更适合重写；先判断差异是类型还是行为。
## 类型参数怎样保留输入输出关系

函数声明`func First[T any](items []T) (T, bool)`中的T是类型参数，表示同一次实例化里输入元素和返回元素使用同一种类型。调用时编译器常能从参数推断T，也可以显式指定。与把输入输出都写any相比，调用者不必再做类型断言，错误更早暴露。

约束any只保证可以保存和传递T等通用能力，不保证能使用加法或比较大小。算法需要把T放入map键时，用comparable等合适约束表达；需要特定方法时，约束可以列出方法。函数体必须对约束允许的类型都合法，而不是只对你今天测试的int合法。

## 类型集合与业务语义不完全相同

约束里的`~int`可以包含底层类型为int的自定义类型，而单独int的范围更窄。这使通用算法支持例如自定义计数类型，但不代表所有底层相同的业务类型都可以任意混合。用户ID与金额即使都用整数表示，也有完全不同的业务意义，应保持调用边界清晰。

去重算法的契约包括保序、相等规则和是否复制元素。comparable保证允许相关比较，但浮点NaN不等于自身，这会影响基于相等的去重语义；接口类型作键还需要关注动态值是否可比较。泛型提供类型关系，不替你选择业务上正确的“相同”。

不必为只有一处调用的短逻辑构造复杂约束层级。先识别稳定重复的算法，再用最小约束表达；若变化来自外部行为而非数据类型，小接口或函数参数往往更直接。

## 保序去重的完整程序
```go
package main

import "fmt"

func Unique[T comparable](values []T) []T {
	seen := make(map[T]struct{})
	result := make([]T, 0, len(values))
	for _, value := range values {
		if _, ok := seen[value]; ok {
			continue
		}
		seen[value] = struct{}{}
		result = append(result, value)
	}
	return result
}
func main() {
	fmt.Println(Unique([]int{2, 1, 2, 3}))
	fmt.Println(Unique([]string{"go", "py", "go"}))
}
```
comparable允许类型用于相等比较和map键，因此[]int不能直接作为T。该函数保持首次出现顺序，不会把输入排序，也不修改输入。复杂业务对象按ID去重时，可以改为接受提取键函数，并让键类型满足可比较约束。
## 约束与底层类型
类型集合可以描述允许的类型，波浪号可涉及具有某个底层类型的自定义类型。学习时先明确算法确实需要哪些运算，避免把所有数字类型随意放进同一约束；整数除法、浮点NaN和溢出有不同语义。
```flow
设计泛型函数
找到共同算法｜输入输出关系真的一致
确定需要的操作｜相等、排序、计算或方法
选择最小约束｜只允许能满足算法的类型
保留业务契约｜顺序、别名、错误与复杂度
用多种具体类型验证｜不要只测试一种实例化
```
## 不必泛型化的场景
函数只调用一个方法时，小接口常常更清楚；两种业务虽字段相似但规则不同，强行抽象会制造大量类型分支。反射、类型断言和泛型混用时，检查是否已经失去静态关系带来的收益。

测试空输入、重复项、自定义类型和是否修改原切片；性能比较要包含分配与代码复杂度。泛型的目的应是减少重复并保留类型安全，而不是让每个函数签名都带方括号。
