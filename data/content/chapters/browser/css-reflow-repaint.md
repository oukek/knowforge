## 回流和重排是不是两回事

在常见前端讨论里，回流（reflow）和重排通常都指重新执行布局计算，浏览器工具往往标为 Layout。它要回答元素的宽、高以及相对位置。重绘（repaint）则重新产生受影响区域的绘制内容，例如颜色、边框或阴影。不要把“重排”理解成必须把 DOM 节点顺序打乱。

想象一篇文章：把文字变红，通常不改变每行能放多少字；把字号从 14px 改为 24px，换行、段落高度、后面的按钮位置都可能改变。前者主要影响绘制，后者需要重新布局并更新绘制结果。实际引擎可以合并、跳过或局部执行工作，所以“每次设置样式都立即全页回流”是错误的。

## 哪些操作让浏览器需要重新计算

布局依赖变了才需要更新几何。例如宽度、高度、字体度量、display、内容或父容器约束变化，都可能让旧布局失效。颜色变化一般不影响几何；transform 改变视觉变换，通常不改变普通文档流占位，但也不能保证每次都仅发生合成。

设置 `element.style.width` 多半先把相关区域标为需要更新。浏览器可以等到后续时机统一计算。但如果紧接着读取 `offsetWidth` 或某些依赖几何的计算值，程序要求“现在的准确尺寸”，浏览器就可能必须提前补做布局。这叫强制同步布局：问题不是“读属性必定很慢”，而是先前的修改让布局过期了。

```flow
一次读写交错如何变贵
写入 width｜旧布局失效，等待统一更新
读取 offsetWidth｜程序立即要求新尺寸
同步执行布局｜主线程等待几何计算完成
再次写入 width｜刚完成的布局又失效
再次读取尺寸｜循环迫使多次布局
```

## 从错误写法改成批量读写

下面代码用于真实页面，HTML 中应有多个 `.row`。第一段对每个元素重复读父容器宽度，而每次写子元素都有可能影响后续布局依赖。不能仅靠代码行数判断一定触发多少次，需要用性能记录验证。

```javascript
// 在浏览器页面或 DevTools 中运行，Worker 中没有 document。
const rows = [...document.querySelectorAll('.row')];
const container = document.querySelector('.list');
// 改进：先读出本次统一使用的布局值，再集中写入。
const width = container.clientWidth;
for (const row of rows) {
  row.style.width = `${width}px`;
}
```

如果能用 CSS 表达，例如 `.row { width:100%; box-sizing:border-box; }`，通常不必让 JavaScript 读宽度。批量读写不是强制所有元素共享一个过期宽度；如果每步确实依赖上一步的新布局，先重新设计算法或限制影响范围，不能为了性能破坏正确性。

requestAnimationFrame 在绘制前提供回调机会，适合合并同一帧的视觉写入。但在回调里反复“写、读、写、读”仍可能强制布局。它不会自动把回调内部变成事务，也不能把重计算移出主线程。

## 如何判断优化是否有效

用固定页面规模、相同操作录制前后性能，观察 Layout 次数、总耗时和长任务，并检查视觉结果。可用不同数量的行放大差异，再在目标手机上测量。不要只用一次 `Date.now()` 报一个很小的时间：浏览器可能把真实绘制留到后面，测到的只是样式赋值时间。

定位布局问题时还要看失效来源：图片未预留空间、字体切换、展开动画按高度逐帧变化、长列表内容更新，都可能让布局成本变高。虚拟列表减少同时参与布局的内容；合理的 containment 缩小依赖；固定媒体比例降低布局偏移。它们解决的是不同原因，不应一概归结为“尽量不用 width”。
