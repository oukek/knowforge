## 从具体问题认识从注意力到 KV Cache

聊天越长，模型需要处理的历史通常越多。理解这种变化要先认识注意力：当前位置的 Query 与可见位置的 Key 比较，得到权重，再对 Value 加权汇总。它让当前位置从上下文中选择信息，但并不是在数据库里查一条固定记录。

生成式模型一次产生后续 token，旧位置的某些计算可以复用，KV Cache 就保存这些 Key 和 Value。缓存节省重复计算，同时占用随序列长度增长的显存。

## 用两个位置理解注意力计算

假设当前查询对两个位置的归一化权重为 0.25 和 0.75，对应 Value 简化为 2 与 10，加权结果就是 8。真实模型使用向量、多头与多层结构，本例只显示“按匹配程度汇总信息”的局部运算，不代表注意力权重就是人可直接理解的解释。

Prefill 一次处理输入上下文，decode 逐步生成新内容。decode 可以复用旧位置的 K、V，但新 token 仍要与可见历史交互，因此有缓存不代表长上下文没有额外工作。调度、带宽、计算与批处理都会影响实际延迟。

容量估算要用 KV 头数而非一律使用查询头数，并考虑层数、序列数、长度、维度和数据类型。公式给出张量主体量级，实际还包括分配、分页与运行时开销。不能把量化权重节省直接等同于 KV 缓存也同比缩小。

## 一次生成到底发生了什么

以 decoder-only Transformer 为例，分词器把文本变成 token ID，嵌入与位置相关变换进入多层网络，输出词表上下一 token 的 logits。选出一个 token 后把它接回序列，再预测后一个，因此输出长度直接影响串行生成时间。参数中编码的是统计规律，业务数据库和实时订单状态仍需外部查询，不能把模型记忆当成事实源。

一层注意力可简写为 `softmax(QKᵀ / sqrt(d) + mask)V`。Q 是当前位置的查询，K 用于计算匹配权重，V 是被加权汇总的信息。因果 mask 阻止位置看到未来 token。多头、归一化、残差和前馈网络都参与真实模型；注意力权重也不能直接当作因果解释或引用证据。

## Prefill 与 decode 的不同瓶颈

Prefill 对输入序列构建表示与缓存，decode 一次追加少量新 token。前者长输入可能带来明显首 token 等待，后者每步需要读权重及历史 KV，长输出又增加总时长。具体是计算、带宽、调度还是通信受限，应按模型、硬件和批次测量，不能用一句“GPU 利用率低”下结论。

| 指标 | 主要观察什么 | 常见误读 |
|---|---|---|
| TTFT | 排队、检索、prefill 到首次输出 | 把网关排队都算成模型慢 |
| TPOT | 输出阶段每 token 时间及抖动 | 用整段耗时除字数冒充 token 指标 |
| 端到端延迟 | 前后处理、工具调用、所有轮次 | 首 token 很快就认为任务很快 |

流式传输只让用户更早看见部分结果，不会消除后续 token 的计算。

## KV Cache 为什么能复用，也为什么耗内存

因果注意力中，旧位置的 K/V 在追加 token 时通常可复用，只为新位置计算 K/V，避免每一步重算所有前缀。缓存保留的是中间张量，不是自然语言摘要；改变前缀、模型或位置处理时不能随意复用旧缓存。

对每层相同布局的普通全长缓存，可用 `2 × 层数 × batch × 序列长度 × KV头数 × 每头维度 × 每元素字节` 粗估字节数。2 表示 K 和 V。GQA 的 KV 头数可少于查询头数，不能直接拿 attention heads 代入。滑窗、分页、量化、张量并行和分配碎片会改变实际占用，此公式不是 GPU 容量承诺。

## 优化要对准约束

如果是队列过长，先限制并发和输入预算；如果长输出主导，优化任务契约与停止条件；如果 KV 成为瓶颈，再实验缓存量化、offload 或更适合的模型结构。权重量化降低权重占用，不等于 KV 同时变小。缓存 offload 也可能用传输延迟换显存。

比较方案时固定请求长度分布、输出上限和质量集，记录吞吐、P50/P95、OOM、取消后释放时间。禁止用短提示单请求结果宣称长上下文并发容量。应用结果缓存还涉及权限和新鲜度，与模型 KV Cache 是不同层。

## 反例与验收

准备短入短出、长入短出、短入长出以及多会话混合四组请求，分别画排队时间、首 token 时间、decode 时间和峰值显存。对用户取消的长会话检查 KV 是否最终释放。再更新系统提示，验证跨请求前缀复用是否仍符合服务实现的规则。

面试时应能解释：长上下文上限代表可接受的输入范围，不代表该长度下仍有相同吞吐；增加批次也不保证单用户延迟降低。明确公式假设和测量边界，比背一个显存数字更有价值。

## 把机制放到一条完整路径中

```flow
带 KV 缓存的生成
处理上下文｜计算已有位置的 Key 与 Value
保存可复用状态｜按层与序列占用缓存空间
生成新位置｜新 Query 读取可见历史信息
继续或释放｜追加状态并在结束后回收资源
```

## 配套代码：从注意力到 KV Cache：推理为何越聊越慢

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。



```javascript
function kvBytes({ layers, batch, tokens, heads, dim, bytes }) {
  return 2 * layers * batch * tokens * heads * dim * bytes;
}
const config = {
  layers: 32,
  batch: 1,
  tokens: 4096,
  heads: 8,
  dim: 128,
  bytes: 2,
};
console.log(kvBytes(config) / 1024 ** 2);
console.log(kvBytes({ ...config, batch: 8 }) / 1024 ** 3);
function softmax(xs) {
  const m = Math.max(...xs),
    weights = xs.map((x) => Math.exp(x - m));
  const total = weights.reduce((a, b) => a + b, 0);
  return weights.map((x) => x / total);
}
const weights = softmax([0, Math.log(3)]);
console.log(weights.map((x) => Number(x.toFixed(2))));
console.log(Number((weights[0] * 2 + weights[1] * 10).toFixed(6)));
```

前两行只估算 KV，不包含模型权重；后两行是单 query 的注意力权重及加权值。改 batch 或 tokens，验证线性增长，不能据此预测真实 GPU 吞吐。 浮点加权和显示前保留六位小数，避免二进制浮点尾差干扰学习；并非使用精确实数运算。

## 从示例走向实际使用

排查慢请求时分开看输入处理、首 token 与后续生成速度，结合上下文长度和并发量判断瓶颈。只有某个阶段慢时，才有针对性地减少上下文或调整调度。

课内容量公式用于理解尺度变化；真实部署需要测量具体模型架构和推理服务，不能凭公式直接承诺每秒吞吐。
