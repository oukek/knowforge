## 从任务约束开始，而不是品牌开始
先定义输入模态、语言、长度、结构化输出、工具使用和错误代价，再列数据驻留、响应时间、并发和费用约束。某排行榜领先不能直接推断在自家工单抽取或代码检索任务最好。先有代表性样本与验收，才有可比选择。

不在课程中固定“当前最强型号”和价格，避免随版本失效。实际选型应核对具体模型卡、服务版本、许可和使用数据政策，并记录评估时点。
## 托管 API 与自部署的责任
托管服务减少权重部署与容量管理工作，但仍需考虑网络、限流、地域、版本和数据边界；自部署增加硬件、推理服务、扩缩容、更新和安全责任。开源权重不意味着零成本，也不意味着可忽略许可。

| 维度 | 托管服务要查 | 自部署要查 |
|---|---|---|
| 容量 | 配额、限流与排队 | 显存、批次与调度 |
| 质量 | 实际服务版本与配置 | 权重、模板及量化 |
| 数据 | 传输、保留和驻留 | 存储、网络与权限 |
| 运维 | 故障回退与依赖 | 升级、回滚与监控 |

本地浏览器运行课程 Python 不等于本地运行了大模型；Pyodide 是执行 Python 的环境，与模型权重推理是两类能力。
## 兼容接口不代表相同契约
某服务支持类似的路径和 JSON 字段，不保证消息角色、工具调用、schema、流式事件、拒绝和费用字段完全相同。用模型适配层将响应转为应用自己的联合类型，保留 request_id、模型版本和终态。

不要把失败统一兜成空字符串；区分传输失败、拒绝、不完整、格式不符与业务不满足。降级模型也要保持隐私和工具契约，不能为成功率展示而悄悄放宽安全。
## 可运行实验：先硬约束，再比较代价
实验按是否支持结构化输出和是否符合数据边界筛选，再按本题给定的综合成本排序。分数是构造数据，不是现实模型排行榜。修改硬约束，观察价格再低也不能使不满足要求的候选入选。

真实比较要固定提示、工具快照、数据集和输出预算，记录失败成本与人工审核。时延看分布和并发，不只测一次最快请求；质量看切片，不能以平均值掩盖高风险任务退化。
## 切换与验收
先使用 fake 建立接口测试，再对真实候选做质量实验；托管模型版本更新时跑同一套回归。把模型、提示、索引、工具 schema 作为兼容组合管理，回滚也需要兼容持久状态。

保留明确未知项：没测过的语言、长输入或高并发不能宣称支持。选型结论应附条件，说明为何满足当前任务，而不是宣称一个模型适合一切。
