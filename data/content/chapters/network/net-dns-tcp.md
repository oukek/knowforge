## 从具体问题认识DNS、TCP 握手与连接复用

域名是便于人记忆的名称，IP用于网络寻址，端口进一步标识主机上的服务入口。DNS把名字解析为相应记录，TCP则在两端之间建立可靠、有序的字节流。一个解决“去哪里”，另一个解决“怎样传”，它们不是同一层的协议。

DNS结果可能来自浏览器、系统或递归解析器缓存，也可能需要继续查询。TTL约束记录缓存时间，不意味着某个客户端一定立刻切到新地址；连接池里已有连接还可能继续使用旧目标。

## 握手、字节序列与两种窗口

TCP三次握手交换并确认双方初始序列号，建立收发状态。序列号和确认机制帮助识别已收到哪些字节，丢失时可以重传；它并不解释应用消息的边界。一次send可能分段到达，多次send也可能一起被read读出，所以业务协议要用长度、分隔符或已有消息协议分帧。

流量控制依据接收方能容纳的数据量，防止接收缓冲被压满；拥塞控制依据网络路径表现调节注入速率，避免中间链路拥塞。两者都会影响发送，但目的和信号不同。网络重传成功也只说明传输层数据交付，不能证明订单已提交或消息已持久保存。

连接复用可省去重复建立连接的成本，但受到源、协议、连接状态与浏览器策略影响。DNS缓存命中不等于TCP连接存在，TLS会话恢复也不等于完整连接复用。HTTP/3使用QUIC而非TCP，不能把所有浏览器通信都套进三次握手图。

## 把机制放到一条完整路径中

```flow
建立并使用连接
解析域名记录｜缓存或查询得到候选地址
协调传输状态｜TCP交换序列号，QUIC走另一协议路径
传输有序字节｜流量与拥塞控制共同约束速度
复用或关闭连接｜业务消息确认仍由上层定义
```

## 配套代码：连接复用与分段耗时模型

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

同一请求业务时间不变，连接复用仍能减少前置成本。

```javascript
function total({reuse, dns=15, tcp=30, tls=30, response=40}) {
  return (reuse ? 0 : dns + tcp + tls) + response;
}
console.log(total({reuse:false}));
console.log(total({reuse:true}));
```

第一次含 DNS/TCP/TLS 的模型成本为 115，复用时只剩响应成本 40。真实请求可能部分复用、使用会话恢复或走 QUIC，不应把这个固定数值当实测。

## 从示例走向实际使用

慢请求先拆DNS、连接、TLS、排队、首字节和下载时间，再检查是否实际复用了连接。连接关闭与TIME_WAIT等状态需要结合系统统计和协议上下文分析，不应看到数量多就随意修改内核参数。

本课耗时模型用于理解成本组成，真实数值来自测量。需要业务可靠交付时，在应用层定义确认、幂等和恢复游标，不把TCP可靠性当成数据库事务。
