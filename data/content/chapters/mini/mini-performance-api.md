## 从具体问题认识小程序启动与更新性能测量

性能测量是在一次用户操作中定义起点、终点和中间阶段，再把观察结果与设备、网络和版本关联。只记录接口耗时，无法知道用户究竟等了多久；只记录页面打开时间，也无法知道时间花在网络、脚本还是渲染。

例如“打开课程到正文可读”是用户能感知的目标。它可能包含启动、代码加载、登录检查、课程请求、内容解析和视图更新，必须把这些阶段放在同一条时间线上。

## 指标定义决定测量是否可比较

先明确冷启动与热启动、首次进入与返回页面、缓存命中与未命中的差别。把这些不同路径混成一个平均数，优化前后即使代码没有变化，也可能因用户构成不同而看起来变快。应按关键条件分组，并同时观察分位数、样本量和错误率。

平台性能接口提供一些宿主阶段的数据，自定义埋点补充业务阶段。二者的时钟、含义和可用范围需要核对，不能把任意时间戳直接相减。一次请求使用统一关联 ID，记录开始、完成、取消与失败，让缺失的终点也能被解释，而不是只统计成功样本。

埋点本身会消耗资源。高频手势逐帧上报完整对象，可能成为新的卡顿来源；应在本地聚合、采样并批量上传，限制单条大小和队列容量。性能数据通常只需要阶段与环境摘要，不需要包含用户输入的完整内容。

## 把机制放到一条完整路径中

```flow
一次可解释的性能记录
定义目标｜选择用户可感知的起止点
阶段采样｜关联启动请求处理与渲染
条件分组｜区分版本设备网络与缓存
定位验证｜用时间线验证改动影响
```

## 配套代码：排队、执行与总耗时分开

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

自定时间点计算不同阶段；这些是演示数据而非微信 Performance API 实测。

```javascript
const requests = [
  {enqueue:0, start:10, end:50},
  {enqueue:0, start:50, end:110}
];
const mean = values => values.reduce((a,b)=>a+b,0)/values.length;
console.log(mean(requests.map(x => x.start-x.enqueue)));
console.log(mean(requests.map(x => x.end-x.start)));
console.log(mean(requests.map(x => x.end-x.enqueue)));
```

三种口径分别是平均排队、平均执行和平均总耗时。把排队时间混进执行时间会误判接口；真实统计还要保留失败样本、设备网络分组和分位数。

## 从示例走向实际使用

为首屏定义可检查的完成条件，例如正文首段与主要操作可用，而不是把 onLoad 执行完当成用户已经看到页面。以相同定义比较版本，否则指标变化可能只是埋点位置变了。

先用一次真机操作的时间线验证事件顺序，再扩大采样。出现负耗时、阶段重叠或没有终点时，优先检查埋点协议与取消路径。
