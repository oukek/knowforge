## 从具体问题认识HMR、模块图与热更新边界

热模块替换允许开发时更新部分模块而不刷新整个页面。它希望保留与变化无关的状态，例如编辑表单里的输入，同时让修改的组件或样式生效。实现关键不只是把新代码下载下来，还要知道旧代码留下了什么。

模块图记录谁导入了谁。一个模块变化后，开发服务器沿引用关系寻找能够接受更新的边界；如果没有合适边界，就可能需要更大范围更新或整页刷新。

## 更新接受与旧资源处置

接受边界表示某一层知道如何把新的模块实现接入正在运行的应用。框架插件常负责组件更新与状态保留，但状态能否保留取决于变化类型，不能承诺任意修改都无损。改变模块导出或初始化方式可能破坏旧调用者的假设。

旧模块可能注册了事件、启动了定时器或建立连接。新模块再次执行初始化前，需要处置旧资源，否则每保存一次文件就增加一个监听器。dispose 一类生命周期入口负责清理或传递允许保留的数据，清理逻辑应与初始化逻辑对称。

开发热更新保留状态也会隐藏问题：某些初始化步骤只有首次加载执行，经过多次热更新后出现的状态未必是全新用户能得到的状态。因此调试完成后应刷新页面，并用生产构建验证。HMR 是开发反馈机制，不是生产线上自动修补运行中状态的部署方案。

## 把机制放到一条完整路径中

```flow
热更新传播
文件变化｜使相应模块转换缓存失效
依赖追踪｜沿导入关系寻找接受边界
处置旧版｜清理监听连接和临时资源
接入新版｜更新模块或回退整页刷新
```

## 配套代码：热替换前释放旧资源

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

重复加载模块时先调用 dispose，避免订阅累计。

```javascript
const listeners=new Set(); let dispose;
function replaceModule(version) {
  dispose?.();
  const listener=() => version;
  listeners.add(listener);
  dispose=() => listeners.delete(listener);
}
replaceModule(1); replaceModule(2); replaceModule(3);
console.log(listeners.size);
console.log([...listeners][0]());
```

每次替换释放上一份监听，最终只有当前版本。真实 HMR 还涉及模块图更新边界和整页回退，组件卸载也需要自己的清理。

## 从示例走向实际使用

遇到“保存几次后按钮触发多次”时，先检查模块顶层副作用和清理钩子。为监听、定时器与连接记录当前数量，热更新后应保持合理上界。

本课实验用重复替换与释放监听说明资源处置。实际项目还要验证组件状态、样式更新和依赖边界，不能仅测试文本是否变了。
