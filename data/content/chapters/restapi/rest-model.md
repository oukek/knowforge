## 从具体问题认识REST 约束、资源与 HTTP API 的边界

REST 是一种分布式系统架构风格，HTTP API 则是使用 HTTP 提供功能的接口。资源路径、JSON 与 GET/POST 很常见，但只满足这些外观并不等于完整遵循 REST。理解它的价值，是让客户端与服务端通过清晰、可演进的协议协作。

资源是可被识别和操作的概念，例如文章、学习计划或一次任务；表示是资源在某次响应中的具体形式，例如一份 JSON。数据库行、资源与 JSON 对象可以相关，但不是必须一一对应。

## 约束如何减少双方耦合

客户端与服务端分离界面和数据职责，无状态要求每次请求携带理解该请求所需的上下文，不依赖服务器记住隐含的前一步交互。无状态不等于服务器没有数据库，也不禁止保存账号或任务；关键是请求语义不能依赖不透明的会话步骤。

统一接口关注资源标识、通过表示操作资源、自描述消息与超媒体等约束。缓存约束让中间层知道什么可以复用，分层系统让客户端不必了解每个内部服务。许多实际 JSON API 只采用部分原则，应准确称为 HTTP API 或说明采用范围，而不是为了名称争论忽视契约质量。

接口设计应让方法、状态码、头与正文各自表达清楚信息。把所有操作都塞进一个 POST /do 并在正文用 action 区分，可能仍能工作，但会失去一些通用缓存、重试与观察工具能够利用的语义。复杂业务动作也不必为了路径全是名词而强行伪装成任意字段修改。

## 把机制放到一条完整路径中

```flow
资源与协议
业务概念｜确定可识别的资源与操作
表示设计｜选择客户端需要的字段
HTTP 契约｜用方法状态头和正文表达行为
演进边界｜保持客户端与内部实现解耦
```

## 配套代码：REST 约束、资源与 HTTP API 的边界：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

resources={'/articles/42':{'id':'42','title':'A'}}
representation=json.dumps(resources['/articles/42'],ensure_ascii=False)
show(json.loads(representation))
show('42' in resources['/articles/42'].values())
```

资源由 URI 标识，本次 JSON 是其中一种表示；这个字典不是完整 HTTP 或 REST 实现。理解业务实体与传输表示的区别，能避免把数据库列直接暴露给客户端，或让模型返回内部字段成为公共契约。

## 从示例走向实际使用

先以学习计划为例定义集合、单个资源与允许操作，再决定如何表示创建、更新与异步生成。写出一个完整请求响应，比先争论路径命名更能暴露契约缺口。

课内字典与 JSON 展示资源与表示的区别。真实服务还需要 HTTP 方法、缓存、授权和错误语义，不能把序列化成功当成 API 设计完成。
