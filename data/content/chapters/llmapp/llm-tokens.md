## 从具体问题认识Token、上下文窗口与预算分配

上下文预算决定一轮推理能放入多少指令、历史、检索资料和工具信息，并为输出留出空间。它不是简单截断用户输入长度。一个短问题可能附带很长历史和多个工具 Schema，实际请求远大于输入框里的文字。

预算分配需要优先级：任务规则与当前状态通常必须保留，重复历史和低相关资料可以减少；不能按消息先后顺序机械删到刚好不超限。

## 输入预算与输出预算共同设计

假设服务允许的相关窗口为 8000 token，计划为指令 800、历史 1800、检索 2400、输出 1500，则剩余 1500 用于协议与其他余量。这个计算只在具体模型计量规则允许时成立，不能把所有模型的输入上限、输出上限和推理 token 都当成同一字段。

精确计数使用目标 tokenizer 或服务提供的计数能力，字符比例只做粗估。发送前估算用于准入，返回 usage 用于核对实际消耗；缓存 token 是否包含在输入总量中、推理 token 如何统计，要按提供商语义处理，避免重复计费。

预算不足时先减少低价值上下文、检索冗余或历史细节，同时保留证据来源与工具配对。如果必要内容本身超过限制，应拆任务或明确失败，而不是静默删掉关键约束。输出上限太小可能导致结构化结果截断，太大也不代表一定会花满，但会影响资源规划。

## 把机制放到一条完整路径中

```flow
上下文预算
统计组成｜指令历史资料工具与媒体
预留输出｜按任务需要保留生成空间
按优先装配｜保证关键状态与证据完整
核对使用量｜记录实际消耗与截断原因
```

## 配套代码：Token、上下文窗口与预算分配：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

window=8000
allocations={'instructions':800,'history':1800,'retrieval':2400,'output':1500}
show(window-sum(allocations.values()))
show(sum(allocations.values())<=window)
```

数值是教学预算，不对应任何真实模型上下文规格，也没有执行 tokenization。实际计数必须使用目标模型工具，并为接口包装、工具定义和输出预留空间；裁剪策略还要通过任务质量评估。

## 从示例走向实际使用

记录各类输入占用与最终输出长度，按真实任务分布调整默认预算。用长答案、长代码与大量引用切片检查截断率，而不是只测试一个简短问答。

课内固定预算用于说明分配关系，不是推荐所有模型使用 8000 窗口。具体能力与计费字段以所接服务为准。
