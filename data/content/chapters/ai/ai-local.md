## 从具体问题认识WebGPU、WASM 与端侧推理

端侧推理把部分模型计算放在用户设备上，例如浏览器使用 WASM 或 WebGPU。它可能减少数据传出与持续网络等待，但需要下载模型、占用设备内存与计算资源。端侧不是天然更快，也不自动等于所有数据绝不外传。

第一次使用可能主要等待模型下载与初始化；后续重复任务才体现本地计算收益。因此要分别比较冷启动与热运行。

## 能力检测、资源预算与回退

WASM 提供可移植的低层执行能力，WebGPU 提供 GPU 计算与图形接口，模型运行时负责把算子映射到这些能力。浏览器、驱动、设备与算子支持会影响可用性，不能只检查一个全局对象存在就认定整个模型可以稳定运行。

内存包括模型权重、中间结果与缓存，移动设备还受到电量、温度和后台限制。大模型下载需要进度、缓存与版本管理，损坏或不完整缓存应能重新获取。多个标签页同时初始化也可能重复占用资源。

回退策略应明确何时改用云端、是否需要用户同意数据传出，以及离线时哪些能力不可用。端侧数据仍可能被日志、同步或其他请求发送，因此隐私承诺必须审查整个应用链路。结果质量也要用相同任务集比较，不能只展示本地运行成功。

## 把机制放到一条完整路径中

```flow
端侧推理
能力检测｜确认设备运行时与算子支持
下载初始化｜展示真实进度并管理缓存
受控运行｜限制内存并响应取消
必要回退｜说明能力与数据传输变化
```

## 配套代码：冷启动成本与复用次数

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

比较下载初始化后多次本地推理与逐次云请求的总时间模型。

```javascript
function localTotal(count){return 3000+count*20;}
function cloudTotal(count){return count*200;}
console.log(localTotal(1),cloudTotal(1));
console.log(localTotal(30),cloudTotal(30));
```

一次使用时冷启动主导，复用多次后本地模型可能摊薄成本。这里只比较虚构时间，真实选型还要模型大小、设备内存、功耗、隐私和准确率，不能只比热推理延迟。
