## 从具体问题认识wx.request 封装、取消与错误分类

wx.request 发起网络请求，但“请求完成”不等于“业务成功”。网络层可能收到 HTTP 响应，响应状态却是 401 或 500；HTTP 状态可能是 200，业务结果却表示库存不足。把这些层次混在一个成功回调里，会让错误提示与重试都变得不可靠。

请求还具有生命周期：发出、等待、收到结果、被取消或超时。用户切换筛选条件时，旧请求即使后来成功，也不应该覆盖新条件下的页面内容。

## 把请求封装为有边界的操作

封装层可以统一基础地址、认证信息、追踪 ID、超时和错误分类，但不要吞掉所有异常后只返回空数组。空数组可能表示确实没有数据，也可能表示服务不可用，调用者需要区分。响应解析后先检查传输与状态，再校验业务结构，最后交给页面。

请求任务提供的取消能力用来停止不再需要的工作。取消是用户意图的一种正常结束，不应和服务故障一起弹红色错误。由于取消可能与响应到达竞争，页面仍需用请求序号或参数版本判断结果是否有效；只调用 abort 并不能代替状态一致性设计。

重试适合明确的暂时故障，而且需要退避、次数或总时间预算。查询失败通常较容易重试，创建订单等写操作则必须先有幂等协议，否则一次网络超时后再次请求可能重复创建。认证失效的刷新流程应合并并发触发，避免十个请求同时刷新登录态。

## 把机制放到一条完整路径中

```flow
请求生命周期
建立上下文｜参数认证追踪与预算
发送等待｜保留取消句柄
分类校验｜区分网络HTTP与业务结果
有效提交｜确认仍是当前任务再更新页面
```

## 配套代码：调用成功不等于 HTTP 成功

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

模拟 wx.request 返回后对 statusCode 做业务层判定。

```javascript
function unwrap(response) {
  if (response.statusCode < 200 || response.statusCode >= 300) {
    throw new Error('HTTP ' + response.statusCode);
  }
  return response.data;
}
console.log(unwrap({statusCode:200, data:{ok:true}}));
try { unwrap({statusCode:503, data:{}}); } catch (error) { console.log(error.message); }
```

宿主 success 回调里的响应仍可能是 HTTP 503，需要独立判断状态和业务码。此处没有真实 RequestTask、取消或网络，只演示分层错误处理。

## 从示例走向实际使用

为封装定义成功数据、业务拒绝、认证失败、网络故障、超时和取消等结果类别。页面按类别决定重试按钮、重新登录或静默忽略，而不是检查错误字符串。

测试两个请求反序返回、页面退出后响应、HTTP 错误但网络成功，以及写请求响应丢失。真实服务器与小程序域名配置应在真机联调中验证。
