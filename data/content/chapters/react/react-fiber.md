## 渲染不是立即把页面画出来
React 的 render 阶段调用组件并计算下一份界面描述；commit 阶段把必要变化应用到宿主环境；之后浏览器才进行自己的布局与绘制。因此函数组件执行不等于 DOM 必定改变，DOM 改变也不等于立即显示一帧。

把渲染保持为纯计算很重要。React 可以重试、放弃或重新开始某次渲染，如果你在函数体里发购买请求、改外部数组或注册监听器，未被提交的计算也会产生真实副作用。应将动作放在事件处理或正确的同步生命周期中。
## 协调过程先确定哪些状态仍属于同一组件

React根据新旧元素的类型、位置与key等判断哪些部分可以复用。保持同一身份通常保留对应组件状态；类型或key改变可能导致旧子树卸载并建立新状态。这个过程称为协调的一部分，它不是逐字符比较HTML字符串，也不是保证永远找到数学意义上最少DOM操作的通用算法。

Fiber把组件关系、待处理更新和相关状态组织成可调度的工作结构。它使渲染工作不必总以一次不可分割的递归遍历推进，但组件自己执行的一段巨大同步计算仍会占用线程。需要真正隔离CPU工作时，可能要拆算法、分块或用Worker，不能只靠框架调度名称。

## 可中断渲染为什么要求纯净

React准备下一界面时可能因更紧急更新而暂停、重新计算或放弃部分结果。如果组件函数体直接扣费、修改外部集合或注册订阅，未提交的渲染也会造成现实副作用，而且重复计算可能重复执行。纯渲染只根据输入产生描述，外部动作放在明确事件或提交后的同步边界。

commit阶段把选定结果应用到宿主DOM，浏览器随后还要处理样式、布局和绘制。组件函数执行次数、commit次数和浏览器帧数并不相等。开发模式额外调用帮助检测问题，也不应直接被当成生产性能数字。

Profiler适合观察某次提交由哪些组件产生工作，浏览器Performance适合观察主线程、布局和绘制。两个工具解释不同层次，结合输入规模、状态传播范围与实际用户延迟，才能知道应该优化组件结构还是DOM和CSS。

## Fiber 表示可组织的工作单元
可以将 Fiber 理解为 React 管理组件树工作与状态关联的数据结构。它保存组件类型、关系、状态与待处理工作等信息，使框架能把计算拆成可以调度的单元。不要把 Fiber 说成浏览器线程：它并不让多个组件函数自动在多个线程同时执行。

优先级调度让紧急输入与非紧急视图更新有不同处理机会。可中断主要针对计算阶段；已经对外提交的 DOM 变更不能随意当作未发生。理解机制时先区分“准备下一界面”和“对外提交”，再研究具体版本的 lane 等实现。
```flow
一份更新的去向
交互或外部数据提交更新｜记录工作与优先级
Render 阶段｜调用组件、处理状态、比较描述
可能暂停或重算｜更紧急更新可改变工作安排
Commit 阶段｜应用 DOM 变更与相关生命周期操作
浏览器绘制｜用户看到最终提交结果
```
## key 与状态位置为什么相关
```jsx
// 用户切换时，有意清空草稿：
<Editor key={user.id} initialText={user.draft} />
```
稳定 key 表示同一业务实体；改变 key 则可有意获得新实例与初始状态。如果每次用 Math.random 作 key，输入框、焦点与状态可能反复丢失，性能也变差。列表索引只在不会重排、插入或删除等限制明确时才可能符合身份需求。
## 如何分析一次重复渲染
先检查是谁提交更新、父组件是否重新渲染、Context 是否变化，以及开发模式是否在做额外检查。用 Profiler 观察提交和耗时，不要仅凭 console 打印次数判断线上一定执行了同样次数的 DOM 操作。

大型计算即使在可调度架构下也可能长时间占用一次函数调用；拆分组件和使用 transition 不能自动把任意同步算法搬到 Worker。性能修复应针对实际工作量、状态范围和浏览器成本，而不是把“Fiber”当万能性能解释。
