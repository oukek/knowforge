## 先澄清词义与拼写
这里的 AgentScope 是 AgentScope 框架，不是某个“agent 的 scope”。Harness 指围绕模型的工具执行、上下文、状态、权限、资源、恢复与观测等运行环境，不完全等同于一个 SDK。选框架前先列你需要的运行时能力，避免拿不同层次的产品硬比功能数量。
## 两种组织任务的重心
AgentScope 以 Agent、消息、模型/格式适配、工具与协作流程组织应用，可从 ReAct Agent、消息交换与多 Agent 协作入手；并非只能做自由对话，也有工作流与会话状态能力。LangGraph 以状态图、节点、边与 reducer 描述执行，适合把分支、循环、中断恢复和状态更新显式表示；并非不能多 Agent，图节点也可以封装 Agent。

| 维度 | AgentScope 的常见切入 | LangGraph 的常见切入 |
| --- | --- | --- |
| 建模视角 | Agent 与消息协作、模型和工具组合 | State、节点、边与更新合并 |
| 适合验证 | 多角色交互、可替换 Agent 组件 | 分支、状态演进、审批与恢复 |
| 必须额外确认 | 当前版本的持久化、部署、错误语义 | checkpointer、并发 reducer、外部幂等 |
两者都不能自动替业务做认证、租户隔离、密钥管理和账务，也不能因为有 checkpoint 就宣称所有副作用 exactly-once。
## 用同一任务做 POC
例如售后流程：识别问题、检索政策、查询订单、待人工确认、执行退款、生成报告。用相同模型、工具和样本分别实现，注入进程崩溃、工具成功响应丢失、审批重复提交和状态冲突。比较实现可理解性、恢复正确性、可测性、观测与团队维护成本，而非只比 hello world 行数。
## 什么时候选显式图
审批、长任务恢复、阶段验收、条件分支和并发状态冲突是核心时，图式状态更容易解释执行走到哪一步。但图节点粒度过细也会增加状态/调试成本。若业务主要是 Agent 消息协作、原型验证与组件组合，先从相应 Agent 抽象实现可能更直接。实际边界随版本变化，应核对目标版本文档与实验，不给绝对功能禁令。
## 可运行状态机与限制
下方是无 SDK 的最小任务状态机，展示等待审批与完成状态不可被任意跳过。真实框架的异步、并发、持久化与恢复要用各自机制实现；这个模型不能作为某个框架的完整 API 示例。学习者可以添加拒绝、超时、重复恢复，检验状态不变量。
## 面试中的选择结论
先给约束，再给候选和证据，最后说明迁移与锁定成本。如果项目只需要固定三步处理，普通服务代码也可能比两种框架都更合适。应能解释自己选择了哪层抽象，并指出它没有替你完成的宿主责任。

## 朋友原题与口述参考
**原题记录：** 不同的harness如何选择？agent scope vs langgraph的区别和应用场景，怎么做选择？

先澄清 AgentScope 是框架名，Harness 是模型外的执行、状态、上下文、权限和观测运行环境。AgentScope 常从 Agent/消息、模型适配、工具和协作流程入手；LangGraph 常从状态图、节点、边、reducer、检查点与中断恢复入手。两者都能组织工作流/多 Agent，不能简单说一个只会聊天另一个只会流程。

对同一含审批与副作用的任务做 POC，在相同模型/工具下比较恢复、调试、并发状态、部署与维护。图式控制强、恢复要求明确时优先评估 LangGraph；Agent 组件和协作体验优先时评估 AgentScope。所有方案仍需宿主授权和外部幂等，简单固定流程可直接写服务代码。

## 延伸追问与分析
**你的任务只有检索、抽取、校验三步，是否一定要用 Agent 框架？**

不一定。固定且可预测流程用普通函数/队列也容易测试和恢复；根据分支动态性、长任务、审批和团队维护决定。引入框架应能减少实际复杂度，不能只因为面试提到 Agent。

检查点：问题复杂度、必要能力、维护成本。

**LangGraph 并发两个节点写同一状态字段，为什么要讨论 reducer？**

并发更新的合并语义必须明确，是追加、去重、覆盖还是冲突；不能靠执行顺序碰运气。按目标版本定义 reducer，并测试重复重放与乱序。涉及外部写操作仍由业务幂等承担，不由状态合并自动解决。

检查点：并发合并、重放语义、业务幂等。

**从 AgentScope 迁到另一种运行时，怎样避免业务逻辑全部重写？**

把工具业务 API、任务契约、权限和评估集与框架消息格式解耦，adapter 负责状态和事件映射。先迁无副作用任务，再双跑对照，保留旧任务版本与恢复路径；不能直接搬检查点就假定兼容。

检查点：业务边界、事件适配、版本迁移。
