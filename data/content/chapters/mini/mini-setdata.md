## 从具体问题认识setData 语义、路径更新与批量合并

setData 是小程序把逻辑层状态变化交给视图层的入口。可以把它理解为提交一份“哪些可见字段改变了”的更新单，而不是普通的对象赋值。this.data 负责保存页面数据，模板通过绑定读取相应字段，两者之间需要框架完成同步。

例如购物车中第二件商品数量从 1 变成 2，更新单只需表达这一项数量和受影响的合计。把所有商品、接口原始响应和调试信息都重新发送，是把业务对象的大小误当成界面需要的数据量。

## 路径更新、合并与可见完成

setData 接收键值映射，键可以是字段路径，例如 items[1].count。路径更新能够表达局部变化，但路径必须对应当前数据结构；排序或分页以后，旧索引可能已经指向别的商品，所以异步更新前还要用业务 ID 确定目标。对象身份稳定和数组位置稳定是两件事。

一次业务动作中多个互相关联的字段可以合并提交，例如数量和合计一起更新，避免界面在两次更新之间暂时显示不一致。反过来，把持续产生的更新一直延迟到一个超长批次，虽然减少了调用数，却会增加交互延迟。合并策略需要时间窗口、最大等待和卸载时的处理规则。

setData 调用后逻辑侧字段的变化与视图渲染完成不是同一个时刻。需要读取更新后的布局时，应使用相应完成回调和查询机制，而不是认为下一行代码就能得到最终尺寸。不可见的请求句柄、定时器和大型缓存不应塞进 data；只有模板依赖的数据才需要承担跨层同步成本。

## 将通信成本量化到字节与频率

逻辑层一次更新要经历序列化、通信与渲染消费，调用函数返回不代表视图已完成。既要减少频率，也要限制载荷与更新范围；只把 60 次全量更新改成 30 次，若每次仍携带巨大对象，瓶颈可能依然存在。优先局部路径、可见范围和批量合并，避免高频发送不会参与展示的数据。

## 真机实验与渲染器边界

用相同输入分别记录计算、通信回调、渲染/帧与用户交互；按设备和基础库分层。切换 Skyline 不能自动消除业务算法、图片解码与状态设计成本，Worklet 也不是任意 JS 的替代运行时。测试弱网、前后台切换和页面销毁，确保旧任务和监听器被停止。

## 把机制放到一条完整路径中

```flow
局部数据更新
定位对象｜先用业务 ID 找到当前记录
计算变化｜得到数量与合计的同一版本
提交差异｜只发送模板需要的字段
完成观察｜在更新完成后读取布局
```

## 配套代码：同步 data 与异步视图的教学模型

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

模拟一次局部 patch；不调用真实微信 API，也不覆盖数据路径或宿主调度。

```javascript
const data = {count:0};
const view = {count:0};
function setData(patch, callback) {
  Object.assign(data, patch);
  queueMicrotask(() => { Object.assign(view, patch); callback?.(); });
}
setData({count:1}, () => console.log('回调', view.count));
console.log('立即读取', data.count, view.count);
```

data 同步变化，而视图提交在另一个调度点。真实 setData 不一定用微任务，视图完成要依据宿主回调；不要把这个模型的任务顺序当作微信实现。

## 从示例走向实际使用

先把商品的完整业务记录放在逻辑状态中，再投影出模板确实用到的名称、价格、数量和图片地址。提交前统计字段数量与序列化大小，检查是否有重复提交相同值的情况。

实际页面可写 this.setData({"items[1].count": 2, total: 39.8})，但金额计算应使用合适的整数最小单位或十进制方案。局部更新解决的是通信问题，并不会顺便修复价格精度或异步结果覆盖问题。
