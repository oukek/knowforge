## 从具体问题认识资源建模、URI 与状态迁移

资源建模决定 API 向调用者暴露哪些业务对象，以及它们允许怎样变化。URI 是资源的标识，不应简单复制数据库表结构。一个学习计划可能聚合多张表，但客户端仍可以把它当成一个有明确状态的资源。

例如草稿文章可以发布，已归档文章是否允许恢复则由业务规则决定。修改 status 字段不是普通字符串赋值，而是触发受权限和当前状态约束的迁移。

## 资源身份、集合与动作

集合路径表示一组资源，单个路径用稳定 ID 定位资源。嵌套路径适合表达明确归属，但过深嵌套会让 URI 与内部关系过度绑定。即使路径包含 tenantId 或 userId，服务端仍必须验证调用者有权访问该范围。

更新接口应定义可写字段与状态迁移规则。把请求 JSON 直接覆盖数据库对象，可能让用户修改 ownerId、role 或内部计费字段。复杂动作如发布、取消与退款，可以设计明确的操作或子资源，关键是输入、授权、幂等与结果清楚，而不是形式上强求所有操作都一样。

资源 ID 应稳定，不依赖展示名称或数组位置。删除需要说明是立即不可见、软删除还是异步清理，以及后续查询返回什么。关联对象的存在与生命周期可以由业务层校验，涉及多个写入的不变量使用事务维护。

## 配套代码：资源建模、URI 与状态迁移：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

allowed={'draft':{'published','deleted'},'published':{'archived'},'archived':set()}
def can_move(old,new): return new in allowed.get(old,set())
show(can_move('draft','published'))
show(can_move('archived','published'))
```

状态机验证迁移是否合法，但真实 API 还需验证身份、资源归属和版本。把允许迁移写出来，能让接口、测试和文档共享同一个业务边界，避免把任何字符串都接受为新状态。

## 从示例走向实际使用

先画状态迁移图，标出每条边的权限、前置条件和副作用，再设计路由。这样能发现“已完成任务再次运行”“已发布内容直接改成草稿”等未定义情况。

课内 allowed 表演示迁移白名单。生产接口还要用条件更新或事务防止两个并发请求基于同一旧状态同时成功。
