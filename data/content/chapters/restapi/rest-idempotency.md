## 从具体问题认识幂等键、请求摘要与结果重放

幂等键标识一次业务意图的多次提交。它解决的是客户端无法确定上次结果时的安全重试，例如服务器已创建订单但响应丢失。重试应返回同一结果，而不是再次创建。

键并不等于用户账号，也不应每次网络重试都重新生成。一个新的业务操作使用新键，同一个操作的重复尝试沿用原键。

## 请求身份与持久结果

服务端记录作用域、幂等键、请求摘要、执行状态与最终结果。作用域可以包含用户、租户与操作类型，避免不同调用者碰撞。相同键与相同参数可重放结果，相同键但参数不同应明确冲突，否则调用者可能误以为新参数已生效。

并发请求必须通过唯一索引、事务或等价原子协议决定赢家。先查不存在再写入，在没有约束时仍会被两个请求同时通过。执行中状态也要有明确处理：等待、返回处理中或要求稍后查询，而不是重复执行业务。

记录保留期决定多久内提供去重保证，应与客户端重试窗口相符。跨系统副作用还需要下游幂等或 Outbox 等机制；只把结果放进本机内存，进程重启后就会失去保证。请求摘要应基于稳定规范化规则，不应因无关 JSON 字段顺序产生不同身份。

## 作用域、摘要与并发赢家

稳定键应绑定租户和业务意图，规范化请求摘要用于拒绝同键异体。两个实例同时检查都不存在时，必须由数据库唯一约束决定赢家；进程 Map 或锁租约不能替代业务持久事实。重试需要返回首次完成的结果，并明确 processing 状态的恢复策略与过期保留期。

## 跨系统副作用的重放

数据库提交和外部消息是两个提交域。事务 Outbox 让业务记录与待发布事件一起提交，发布后标记前宕机仍可能重复，因此接收方也要按稳定 event_id 去重。测试提交前、提交后响应前、发送后标记前三个窗口，区分请求幂等、消息至少一次与业务效果恰好一次的边界。

## 把机制放到一条完整路径中

```flow
幂等请求
生成业务键｜同一意图的重试沿用身份
原子登记｜保存作用域摘要与执行状态
完成操作｜事务维护业务结果与记录
重放结果｜重复请求返回已有事实或冲突
```

## 配套代码：幂等键、请求摘要与结果重放：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

cache={}
def create(key,payload):
    if key in cache:
        if cache[key]['payload']!=payload: return 'conflict'
        return cache[key]['result']
    cache[key]={'payload':payload,'result':'order-1'}
    return 'order-1'
show([create('k',{'n':1}),create('k',{'n':1}),create('k',{'n':2})])
```

字典模型验证同键参数一致性，没有提供多进程原子性、持久化和过期管理。生产实现必须依赖数据库约束与事务等机制，并且避免缓存响应里的敏感数据超出保留期；客户端超时不代表服务端没有成功。

## 从示例走向实际使用

测试同键同参、同键异参、两个并发首次请求、提交后断连与重启恢复。检查业务对象数量和副作用次数，而不只看响应是否相同。

课内 cache 是教学模型，真实实现需要持久化与竞争保护。客户端按钮禁用只改善体验，无法代替服务端幂等。
