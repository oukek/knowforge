## 上下文是一次受约束的信息装配
模型调用输入包含任务规则、用户目标、历史行动、工具定义和外部证据。它们有不同信任级别、有效期和删除规则。上下文工程先决定本轮需要什么、哪些必须保留、哪些应重新查询，再决定如何排列和压缩。扩大窗口只能提高容量，不能保证模型注意到关键约束或证据没有过期。

退款任务最小状态可以包含：用户意图、已确认订单、政策版本、已执行操作 ID、待用户确认的问题、未完成步骤和已知错误。把“聊了 80 轮”压成一段流畅故事，若丢掉“用户尚未同意提交”，仍是不合格压缩。
## 预算应在装配前分配
建立输入上限，并为预期输出、工具定义、协议开销与安全余量预留空间。字符数只能用于粗估，准确计数需采用匹配模型及消息格式的计数方式；中文、代码、图片和工具 schema 的代价不能靠统一四字符规则处理。

| 信息 | 默认策略 | 失效条件 |
|---|---|---|
| 当前目标与禁止动作 | 必须保留，独立字段 | 用户明确改变目标 |
| 已提交操作凭据 | 保留稳定引用，按需查账 | 到期归档，不应凭摘要抹除 |
| 外部搜索全文 | 选择片段、去重、附来源 | 文档变更或权限收回 |
| 调试中间日志 | 保留结论和必要反例 | 阶段结束后压缩 |

必要项本身已超预算时应显式失败或拆分任务，不能静默删除规则后继续。
## 裁剪必须保留可核验性
工具结果可以先结构化，只回传当前问题需要的字段、单位、时间、版本和来源 ID。对列表采取确定性排序和分页，并标明 `truncated`、总数与继续查询方式。不能把“只取到 20 条”改写成“只有 20 条”，也不能把未查询区域当作不存在。

```js
const result = {
  items: rows.slice(0, limit),
  total: rows.length,
  truncated: rows.length > limit,
  sourceVersion: 'inventory-v7'
};
```

敏感数据的裁剪还应在进入模型前完成。权限不够时不要先把全文发给模型，再依赖提示要求它不泄漏。
## 压缩的状态契约
应用自己生成的摘要应有明确字段、来源指针和版本，保留未决事项与相互矛盾的事实，避免用新推测覆盖用户原话。对工具调用链，调用与结果要保持关联，不得留下一个失去对应调用的结果。

OpenAI 官方 compaction 还包含不透明的压缩状态项；它不是让应用自由编辑的人类摘要。使用对应服务时按其状态续接约定保留返回内容，不应猜测其内部文本或手工重写。具体阈值与 API 配置取决于使用接口；本课浏览器实验只演示应用层预算选择。
## 可运行实验与反例
实验先预留输出预算，再保留所有 required 项，对 optional 项按优先级选择；必要项超出可用预算抛错。把一条低价值日志设为高优先级，观察关键证据是否被挤出，说明“贪心排序”只是明确策略，不一定是全局最优的信息选择算法。

进一步把订单状态设为已退款、摘要设为未退款，要求下一步先查权威系统。检查压缩前后是否同样拒绝重复退款、同样等待审批、同样说明证据冲突。摘要只能协助推理，不能代替提交时的业务校验。
## 如何验收压缩质量
建立固定的“下一步问题集”：当前目标是什么、哪些动作已完成、还缺什么授权、关键证据从哪来、哪些事实尚未确定。对完整上下文和压缩上下文分别运行同一套检查，同时评估 token、延迟和任务成功率。不能只用字数缩短率评价质量。

当任务阶段改变时重新装配，旧候选方案可以丢弃，已接受的约束和提交凭据必须继续可查。上线后记录上下文版本、选择原因和来源引用，排障时才能区分检索未找到、裁剪丢失和生成误用。
