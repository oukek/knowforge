## 从具体问题认识AI 服务上线、Trace、灰度与故障回退

LLM 应用上线的是一组协同版本：模型、提示、工具、检索索引、输出 Schema 和应用代码。只记录模型名称，无法解释为什么同一问题昨天正确、今天失败。部署需要让这组版本可追踪、可灰度和可回退。

同时，上游限额、长响应和不稳定网络会影响服务。成功调用一条简单提示只是连通性验证，还不构成生产可用。

## 从版本发布到运行治理

发布前固定验收集，检查任务质量、权限边界、超时与计费。部署后先让少量流量进入新版本，比较成功率、首事件时间、总延迟和成本分布。平均值可能掩盖长尾，因此同时观察分位数与异常切片。

服务端维护有限并发与队列，给每个任务总时间和资源预算。重试只针对允许重试的错误，并受剩余预算约束；多个供应商同时故障时要降级或明确失败，不能无限换模型导致费用和延迟失控。

追踪 ID 贯穿前端任务、应用尝试、检索与工具。用户断线与任务失败分开处理，持久状态支持重连查询。日志脱敏且有保留策略；关键账本和状态转移需要可靠持久化，不能仅存在进程内存里。

## 把机制放到一条完整路径中

```flow
LLM 应用发布
固定版本组｜模型提示索引工具与输出契约
离线验收｜验证质量边界与失败结算
小流量观察｜比较延迟成本和异常切片
治理回退｜限流降级追踪与兼容回滚
```

## 配套代码：AI 服务上线、Trace、灰度与故障回退：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

release={'model':'configured-model','prompt':'p3','index':'docs-v7','tools':'t2'}
trace={'release':release,'retrieval_ms':40,'model_ms':500,'validated':True}
show(trace['release'])
show(trace['retrieval_ms']+trace['model_ms'])
```

版本清单是示意值，不是模型推荐或真实测量。阶段求和只适用于本例顺序执行；实际 trace 要区分并行与关键路径，日志只保存需要的脱敏信息，并支持按同版本回放评估。

## 从示例走向实际使用

上线演练包括上游超时、限流、流中断、服务重启和版本回滚。每种故障都检查用户是否得到明确终态，以及预留额度是否正确结算。

课内 release 元组展示版本组合；真实发布还需构建产物、配置和数据库兼容性管理。回滚提示不一定能撤销已经执行的业务副作用。
