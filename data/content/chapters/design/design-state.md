## 从具体问题认识系统设计

跨页面状态共享与跨应用身份传递是两个不同问题。同一应用中，多个页面可以通过统一状态层读取当前用户或草稿；不同小程序、不同域或不同应用之间，不能假设内存和存储天然共享。

跨应用跳转时，目标应用需要确认“谁发起、允许做什么、凭证给谁用、何时失效”。直接把长期登录令牌放在 URL 中，会扩大泄露与误用范围。

## 状态所有权与一次性票据

先区分服务端事实、客户端缓存、页面局部状态和可分享的路由参数。用户权限属于服务端事实，组件展开状态通常属于页面局部状态。把所有内容都放进全局 store，会造成生命周期混乱；把所有内容都放进 URL，又可能泄露敏感信息或产生无法恢复的复杂参数。

跨应用身份衔接可使用服务端签发的短期、限定受众与用途的票据，由目标后端验证并兑换自己的会话。票据应有一次性或防重放机制，不能仅检查过期时间。签名或服务端随机记录保证票据不是客户端随意伪造，受众限制防止在错误应用中使用。

共享业务数据则通过经过授权的 API 获取，目标应用根据自己的权限显示。退出登录、账号切换与票据兑换失败需要明确行为，不能把上一个账号的缓存继续展示。数据同步使用版本或事件协议，身份跳转本身并不会自动合并所有状态。

## 把机制放到一条完整路径中

```flow
跨应用状态衔接
识别范围｜区分局部共享与跨应用数据
签发票据｜限定身份受众用途与有效期
服务兑换｜验证防重放并建立目标会话
授权取数｜按业务权限读取与同步状态
```

## 配套代码：票据用途、受众与时效一起校验

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

用确定性条件模拟跨应用票据校验，不提供签名或真实身份认证。

```javascript
function verify(ticket, audience, now) {
  return ticket.audience===audience&&ticket.expires>now&&ticket.purpose==='login';
}
const ticket={audience:'B',expires:200,purpose:'login'};
console.log(verify(ticket,'B',100));
console.log(verify(ticket,'A',100));
console.log(verify(ticket,'B',200));
```

票据不能随意跨受众重用，到期也应拒绝。真实服务端需验证签名/存储状态、防重放和用户授权；纯前端布尔判断不能建立可信登录态。

## 从示例走向实际使用

设计跨页编辑流程时先决定谁拥有草稿，再决定页面返回如何同步。设计跨应用入口时先定义票据契约与兑换接口，再实现跳转按钮。

课内对象校验只展示受众、用途与时间条件，不包含真实签名与单次消费；生产环境必须把可信验证放在服务端。
