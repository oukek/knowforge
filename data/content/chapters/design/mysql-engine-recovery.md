## 从具体问题认识InnoDB 与其他引擎

MySQL 由 SQL 处理层和存储引擎等部分协作完成查询。存储引擎负责数据与索引的组织、并发访问和相关恢复能力，因此选择引擎是在选择一组行为保证，而不只是比较查询速度。InnoDB 面向需要事务与并发控制的常见业务。

转账要求扣款与入账一起成功或一起失败，进程崩溃后也要恢复到符合规则的状态。这个例子能帮助理解事务、日志与恢复为什么需要配合。

## 事务能力背后的不同记录

事务把一组操作组织为一个提交单位，原子性要求不能只留下其中一半。并发控制协调多个事务的读写，隔离级别定义可观察行为；持久性则取决于提交后的恢复保证与实际配置。不能把事务简单理解为“给几条 SQL 加 BEGIN”。

redo 记录用于恢复数据页的修改，undo 支持回滚并参与历史版本读取，binlog 位于服务层并用于复制与时间点恢复等场景。三者目的与内容不同，不能用“都是日志”互相替代。脏页可以晚于事务提交落盘，但相关日志与刷盘策略必须满足所要求的恢复保证。

比较 InnoDB、MyISAM 或 MEMORY 时，应看事务、锁粒度、崩溃恢复、数据是否持久和适合的访问模式。MEMORY 中的数据不是普通磁盘表那样在重启后继续存在；MyISAM 不提供与 InnoDB 相同的事务能力。某个只读小实验更快，不足以替代生产对一致性和恢复的要求。

## 从职责分层而非背表格开始

MySQL 服务层负责连接、解析、优化和 binlog 等公共能力，存储引擎负责记录、索引、并发控制和相应恢复。InnoDB 常用于事务型业务；MyISAM、MEMORY 不是“更老所以没有意义”，而是在事务、锁粒度、持久性和特定工作负载上取舍不同。不同版本、引擎插件应分别确认能力。

## 常见引擎如何比较

| 维度 | InnoDB | MyISAM | MEMORY |
| --- | --- | --- | --- |
| 用户事务与回滚 | 支持 | 不支持 | 不支持 |
| 典型并发机制 | 行级索引锁、MVCC，也有表级锁 | 表级锁 | 表级锁 |
| 记录组织 | 聚簇组织，二级键定位主键 | 数据与索引分离 | 内存数据，常见 HASH/B-tree |
| 重启后数据 | 结合日志恢复持久数据 | 需关注崩溃与修复边界 | 表定义可保留，数据丢失 |
| 典型选择 | 订单、账户、通用 OLTP | 受约束的历史或专用负载 | 可重建、容量有界的临时数据 |
“用了行锁”不表示只锁一条业务记录。没有合适索引可能扫描并锁住更多范围；元数据锁、DDL 和表级意向锁仍会出现。

## 三种日志为什么不能互相替代

undo 保留回滚与一致性读需要的旧版本信息；redo 支持已记录变更的崩溃恢复；binlog 位于服务层，支持复制和时间点恢复等用途。提交耐久性还取决于刷盘参数、操作系统和存储保障，不能只说“有 redo 就绝不丢数据”。长事务会推迟旧版本清理，造成历史链与空间压力。

账户转账必须把扣款、入账和相关状态放在合适事务中，且所有参与表都要具备需要的事务能力。外部消息和支付接口不能随数据库回滚自动撤销，可用 outbox 与幂等消费衔接，不能把网络调用包进 BEGIN 就称为分布式事务。

## 验证环境与恢复演练

```sql
SHOW ENGINES;
SHOW CREATE TABLE orders;
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'sync_binlog';
```
确认表实际引擎、版本、数据量与事务边界。恢复能力通过备份还原、binlog 回放、复制延迟与故障演练验证。不要在生产上故意强杀数据库来证明机制，也不要将表引擎转换当作无成本操作：需考虑重建、锁、空间和回滚时间。

## 可运行模型与限制

JS 模型把事务的待提交操作与已提交日志分开，崩溃恢复只重放已确认的操作。它解释提交记录和未提交状态的区别，不能代表 InnoDB 页刷写、两阶段提交和真实 fsync 时序。尝试在提交前抛异常，观察原始余额是否变化，再说明真实数据库需要哪些日志与原子性保证。

## 如何组织面试答案

先给业务要求：并发更新、事务一致性、恢复目标、数据容量；再比较引擎，而不是以 SELECT COUNT(*) 的一个特例决定选型。追问 MyISAM 是否更快时，应要求具体读写比例、索引、数据热度与并发；性能是工作负载测量结果，不是引擎名称的固定属性。

## 把机制放到一条完整路径中

```flow
事务与恢复
业务写入｜形成需要保持一致的一组变化
并发控制｜协调可见性与冲突访问
日志提交｜按配置记录恢复所需信息
崩溃恢复｜重建有效状态并处理未完成事务
```

## 配套代码：InnoDB 与其他引擎：事务、锁与崩溃恢复

下面代码在课内JavaScript运行区执行；需要DOM、Node或平台SDK的真实集成，应按正文的运行边界另行验证。

使用本地 JavaScript 模型验证关键不变量；不调用真实数据库、模型或生产服务。实验简化之处与真实系统步骤见正文。

```javascript
const balances = new Map([['A',100],['B',0]]);
const committed = [];
function transfer(from,to,amount,commit) {
  const changes = [[from,balances.get(from)-amount],[to,balances.get(to)+amount]];
  if (!commit) return;
  committed.push(changes);
  for (const [id,value] of changes) balances.set(id,value);
}
transfer('A','B',30,false);
console.log([...balances.values()]);
transfer('A','B',30,true);
const recovered = new Map([['A',100],['B',0]]);
for (const tx of committed) for (const [id,value] of tx) recovered.set(id,value);
console.log([...recovered.values()]);
```

本段程序用于把状态、条件和数据之间的关系写清；真实实现仍需上文介绍的资源、权限与失败协议。

## 从示例走向实际使用

在测试环境演练异常终止与恢复，确认应用层如何识别提交结果不确定的请求。备份也要验证恢复过程，不能只确认备份文件存在。

下面的余额模型只表达“提交的变更可以重建结果”，不是 redo、undo 的真实实现。真实引擎涉及页、日志序号、检查点与崩溃恢复流程，应结合官方文档和数据库实验阅读。
