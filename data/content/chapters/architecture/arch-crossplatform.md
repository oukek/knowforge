## 从具体问题认识Web、小程序、RN 与 Flutter

跨平台开发希望在多个终端复用一部分代码，但“复用”可以发生在不同层：业务计算、接口契约、组件描述或整个渲染实现。Web、小程序、React Native 与 Flutter 的宿主能力和渲染路径不同，不能只按语法是否相似判断迁移成本。

一个订单状态计算函数可能在多端共享，而输入法、导航返回、文件权限和原生支付通常需要各自适配。明确哪些共享、哪些保留平台差异，比追求一个笼统复用率更有意义。

## 逻辑复用与体验一致如何分层

Web 依赖浏览器能力，适合链接访问与网页生态；小程序依赖宿主接口和发布规则；React Native 将组件体系与原生平台协作；Flutter 具有自己的界面框架与渲染组织。具体架构会随版本发展，选型应查看项目所用版本与目标平台支持，而不是沿用旧桥接模型解释全部现状。

可以把系统拆成领域逻辑、数据访问、界面与宿主适配。领域逻辑尽量不直接读取 window 或 wx，数据层通过接口处理网络和存储，平台层负责权限、导航和设备能力。共享层过厚会把平台差异变成大量条件分支，共享层过薄又造成业务规则重复。

体验一致不等于像素完全相同。各平台的返回手势、键盘、安全区和无障碍习惯不同，强行统一可能降低可用性。测试应围绕同一业务目标在各端是否完成，同时接受合理的平台交互差异。

## 把机制放到一条完整路径中

```flow
跨平台分层
盘点能力｜识别业务共性与宿主差异
提取核心｜共享规则数据契约和纯计算
平台适配｜实现导航权限存储与原生能力
目标验证｜按真实设备完成业务路径
```

## 配套代码：共享领域规则，平台能力显式注入

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

同一业务规则运行在不同适配器上；不假装所有端都有同样能力。

```javascript
function checkout(platform,amount) {
  if(amount<=0)throw new Error('金额错误');
  return platform.pay(amount);
}
console.log(checkout({pay:amount=>'Web 支付 '+amount},10));
console.log(checkout({pay:amount=>'小程序支付 '+amount},10));
```

共享业务校验而将支付能力留给平台适配器。真实支付仍需服务端订单、鉴权、签名和平台 SDK；这里只输出演示文本，不创建支付。

## 从示例走向实际使用

先做最难能力的验证原型，例如长列表、富文本输入或复杂手势，而不是只做一个静态首页。评估原生依赖、升级成本、团队调试能力和发布流程。

复用率应区分共享业务规则与共享界面代码，并结合缺陷与维护成本判断。一个高复用数字不能证明用户体验或交付效率更好。
