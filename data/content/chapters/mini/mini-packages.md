## 从具体问题认识主包、分包、独立分包与预下载

小程序代码包是用户打开页面前需要获取并加载的代码与资源集合。主包承载启动所需的公共部分；分包把某些页面及其依赖组织为单独的加载单元。分包的目的，是减少首次进入不相关功能时必须付出的成本。

例如商城首页不必立即下载售后处理界面的所有代码。把售后页面放入分包后，用户进入售后功能时再加载相关内容，但它依赖的公共代码、资源位置和跳转路径都要设计清楚。

## 分包的收益来自依赖边界

普通分包通常仍与主包构成一个应用：进入分包页面时，需要满足主包与该分包的加载条件。独立分包强调能够在相应入口下不依赖主包先行运行，因此不能随意引用主包中的初始化状态和资源。它适合明确的独立入口，不是给所有页面加速的通用标签。

代码按目录移动不保证包体变小。如果构建工具把大型公共依赖重新打进主包，或者多个分包各自重复携带同一资源，首包或总下载量仍可能很大。应查看构建后的依赖与体积，而不是只看源码文件夹。资源是否能共享、异步加载如何工作，需要按当前平台规则核对。

预下载是在用户可能需要某功能之前提前获取分包。它以额外网络和缓存占用换取进入速度，命中率低时反而浪费资源。可以在用户进入相关业务路径后触发，并考虑弱网与移动流量，避免一打开首页就把所有分包预下载回来。

## 把机制放到一条完整路径中

```flow
按访问路径拆包
分析入口｜找出首次必须显示的页面
划分依赖｜区分公共与功能专属代码
构建检查｜观察实际包体与重复依赖
按需加载｜结合访问概率安排预下载
```

## 配套代码：主包和总包预算校验模型

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

用 KB 为自定统一单位检查演示预算，不对官方 M/KB 单位做隐含换算。

```javascript
function check(mainKB, subKB, mainBudgetKB, totalBudgetKB) {
  return {mainOK:mainKB <= mainBudgetKB, totalOK:mainKB + subKB.reduce((a,b)=>a+b,0) <= totalBudgetKB};
}
console.log(check(1800, [1500, 1600], 2000, 6000));
console.log(check(2300, [1000], 2000, 6000));
```

总预算通过不代表主包预算通过；包拆分也需检查单包与引用。此处预算由参数输入，不替代官方当前限制和 miniprogram-ci 的实际包体检查。

## 从示例走向实际使用

建立三个预算：首次进入主包的大小、典型路径累计下载量、分包进入的等待时间。将低频管理页面、富编辑器等大依赖与高频首页分开，公共模块只放真正共享且启动必要的内容。

检查冷启动、分享直达分包、主包进入分包和独立入口四种路径。仅测试从首页点击进入，容易漏掉全局初始化尚未执行时的空状态问题。
