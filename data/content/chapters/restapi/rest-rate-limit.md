## 从具体问题认识限流、配额、重试预算与过载保护

限流约束请求到达速度，并发限制约束同时执行数量，配额约束一段周期内可消耗的总资源。对 AI API，这些资源还可能是 token、图片数量或内部额度。三个维度共同决定服务能否在高负载下保持可用。

用户余额足够，不代表系统当前有空闲并发；当前并发很低，也不代表这个用户今天还有可用配额。接口应区分这些拒绝原因。

## 准入、预留与结算

请求进入时先做低成本身份与参数检查，再判断速率、并发和资源预算。高成本任务可以预留估算额度，完成后按实际消耗结算并释放差额；并发请求的预留必须原子，否则多个任务可能同时看到相同余额并超支。

过载保护还包括有界队列、排队超时和公平调度。无限排队会让用户等待超过可接受时间，同时占用内存。重试需要全局预算，避免网关、客户端和 SDK 各自重试三次，最终把一次请求放大成许多上游调用。

429 可表达调用者受到限流，服务整体不可用可能使用相应服务错误；具体状态与 Retry-After 应在契约中说明。取消、失败和部分完成如何计费也要清楚，不能只在成功路径释放预留。所有结算以持久任务事实为依据，避免重复回调重复扣费。

## 把机制放到一条完整路径中

```flow
资源准入与结算
入口判断｜检查速率并发和配额
原子预留｜为任务锁定必要预算
受控执行｜有限排队与重试时间
最终结算｜按事实扣费释放并防重复
```

## 配套代码：限流、配额、重试预算与过载保护：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

budget=1000; spent=750; estimated=300
show(spent+estimated<=budget)
show(max(0,budget-spent))
```

预算模型把预估消耗与剩余额度比较，实际系统需要并发预留与结算，避免多个请求同时通过检查后超额。这里的数值是教学预算单位，不代表模型价格或任何平台真实计费方式。

## 从示例走向实际使用

测试多个任务同时接近余额上限、排队中取消、上游失败和结算重放。检查总预留与实际扣费守恒，而不是只看单次请求返回值。

课内预算比较展示准入条件，真实系统还需原子写入与账本。限制的目的应清楚可解释，不能让用户只看到模糊“服务异常”。
