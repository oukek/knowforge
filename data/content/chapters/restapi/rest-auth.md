## 从具体问题认识认证、授权、OAuth、JWT 与资源归属

认证确认调用者身份，授权判断这个身份能否执行某个操作。登录成功只解决第一步，不能说明用户可以读取所有订单或修改任何学习计划。资源归属检查必须在服务端每条相关路径中执行。

OAuth 是授权框架，JWT 是一种令牌表示格式，两者不是互斥登录方案。系统可以使用不透明会话令牌，也可以使用经过验证的 JWT，关键是生命周期与权限契约清楚。

## 令牌验证之后仍要检查资源

不透明令牌通常由服务端查会话记录判断有效性；JWT 可以携带签名保护的声明，但签名不等于加密，正文通常可被读取。验证 JWT 应限定算法、验证签名、发行者、受众与时间等条件，不能只做 Base64 解码就信任用户 ID。

令牌证明的身份还需与数据库中的当前状态结合，例如账号禁用、租户成员变化与资源所有权。角色权限适合表达一类操作能力，资源级授权则决定是否能操作具体对象。只在前端隐藏按钮无法阻止直接调用 API。

凭证存储与传输影响攻击面。Cookie 自动携带时要考虑 CSRF，前端可读取的令牌要考虑 XSS 与泄露；HTTPS、过期、轮换与注销都属于会话设计。OAuth 授权流程应使用适合客户端类型的标准方案，不自己拼一个看似相同的重定向协议。

## 把机制放到一条完整路径中

```flow
认证与授权
验证凭证｜确认来源有效期与身份
建立上下文｜加载账号租户及当前权限
检查资源｜判断归属和允许操作
执行审计｜仅在通过后处理并记录必要事实
```

## 配套代码：认证、授权、OAuth、JWT 与资源归属：最小可验证示例

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

使用 Python 标准库和固定样本验证关键机制。show() 把结果序列化成 JSON；可修改输入再运行。

```python
import json

def show(value):
    """按 JSON 打印结果，便于逐行预测和验证。"""
    print(json.dumps(value, ensure_ascii=False, separators=(',', ':')))

def can_read(actor,article):
    return actor['tenant']==article['tenant'] and article['owner']==actor['id']
show(can_read({'id':'a','tenant':'t1'},{'owner':'a','tenant':'t1'}))
show(can_read({'id':'a','tenant':'t1'},{'owner':'b','tenant':'t1'}))
```

纯函数演示归属与租户条件，不负责解析令牌，也不是完整角色权限系统。真实查询要在返回数据前加范围过滤，并处理共享、管理员等明确规则；客户端传入 owner 字段不能作为可信事实。

## 从示例走向实际使用

测试匿名、本人、同租户其他用户、跨租户用户与管理员对同一资源的操作矩阵。权限判断应覆盖查询、导出、下载与后台任务，而不只是更新接口。

课内 can_read 表达租户与所有者的组合条件，真实角色与共享规则可能更复杂，应把规则集中在可测试的业务授权层。
