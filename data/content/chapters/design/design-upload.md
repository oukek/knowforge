## 从具体问题认识系统设计

分片上传把大文件拆成多个较小片段分别传输。断点续传则在中断后只补传服务器尚未确认的片段，避免重新发送整个文件。两者需要共同的上传会话和分片身份，否则服务器无法知道哪些片段属于同一文件。

例如文件被分成五片，服务器已确认 0、2、4，恢复时应上传 1、3。进度应基于已确认的字节，而不是仅按已经开始发送的片数计算。

## 上传会话、完整性与合并提交

客户端先申请上传会话，服务端校验身份、文件大小、类型与配额，并返回受限的上传参数。每片包含会话 ID、片号和必要校验信息。并发数量应有上限，避免浏览器内存、连接与服务器写入被同时耗尽。

恢复时从服务器查询已完成片段，因为本地记录可能落后或误以为发送成功。重复上传同一片需要幂等处理，并确认内容一致；分片 hash 可检测损坏，但文件 hash 不应作为绕过访问权限的凭据。知道某个文件 hash 不代表有权读取该文件。

所有片段到齐后，服务端验证数量、顺序、总大小和完整性，再执行合并或对象存储完成操作。完成状态必须原子切换，避免用户读到半成品。过期未完成会话要清理，上传目录与最终对象路径不能直接信任用户输入。

## 把机制放到一条完整路径中

```flow
可恢复上传
创建会话｜校验权限大小并定义分片
受控传输｜并发上传并记录服务确认
恢复补片｜以服务端状态计算缺失部分
验证完成｜校验合并后发布最终对象
```

## 配套代码：断点恢复只上传缺失片

下面复用本课的确定性机制实验，只表达所讨论的局部关系，不等于真实宿主、数据库或模型服务。

按 uploadId 对应的已确认分片集合计算缺片，不真正读文件或上传。

```javascript
const total=5;
const confirmed=new Set([0,2,4]);
const missing=Array.from({length:total},(_,index)=>index).filter(index=>!confirmed.has(index));
console.log(missing);
console.log(confirmed.size/total*100);
```

缺片为 1 和 3；进度基于确认片计数仅适用于各片等大，实际末片和字节进度需按确认字节计算。服务端还要校验内容、所有权和幂等合并。

## 从示例走向实际使用

测试最后一片成功但确认丢失、合并重复请求、同片不同内容、文件中途被替换与权限撤销。界面同时显示上传中、校验中和已完成，避免字节传完就误报业务成功。

若使用对象存储直传，临时凭据只允许特定对象和操作，并有有效期。后端仍负责授权、完成验证和业务关联。
