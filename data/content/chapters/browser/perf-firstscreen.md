## 性能优化先回答“用户在等什么”

页面慢可能是收到 HTML 慢，可能是大图迟到，也可能是内容已经显示却点不动。它们的瓶颈不同。首屏不能只用一个 onload 时间概括：页面加载完成时未必已经展示关键业务内容，反过来用户能开始阅读时也可能还有不重要资源没加载完。

将体验拆成网络等待、资源处理、JavaScript 执行、浏览器渲染和交互反馈。LCP 关注主要可见内容的出现，INP 关注交互到下一次画面更新的延迟，CLS 关注非预期布局移动。实验室测试便于复现，真实用户测量才反映设备与网络分布；两者应共同使用，不能拿开发电脑的一次刷新当用户结论。

## 找关键路径，而不是给所有资源同时加优先级

请求依赖可能形成串行链：HTML 到达后才发现 JavaScript，脚本执行后才请求接口，接口返回后才知道首屏图 URL。即使每个资源不算大，串联等待也会很长。应在 Network 的 initiator 与瀑布图里找出真正阻碍关键内容的依赖，再决定将资源提前暴露、服务端输出数据还是调整加载顺序。

```flow
一张首屏图为何迟到
请求 HTML｜服务器处理和网络往返
发现并下载入口脚本｜下载、解析、执行都需要时间
执行页面数据请求｜可能再次等待服务端和网络
发现图片 URL｜图片下载、解码
完成布局与绘制｜关键内容才显示
```

关键图片不要无差别 lazy-load；懒加载更适合暂时不可见的内容。preload 应用于确实关键且属性匹配的资源，否则可能抢占其它请求带宽或导致重复请求。代码拆分减少初始加载，但拆得过碎又可能制造瀑布。是否优化要看依赖和目标环境，不是检查“用了多少优化名词”。

## 资源体积如何变成实际时间

图片需要合适尺寸、格式与压缩，不能把原始大图按 CSS 缩小就当作优化完成。响应式图片通过 srcset/sizes 告诉浏览器可选资源与显示需求；width/height 或 aspect-ratio 提前提供比例，避免图片到达后把内容挤开。

```html
<img src="cover-640.webp"
     srcset="cover-320.webp 320w, cover-640.webp 640w"
     sizes="(max-width: 600px) 90vw, 320px"
     width="640" height="360" alt="课程封面">
```

这段示例需要服务端实际提供两张图。sizes 描述布局中的预计显示宽度，不能随意写一个值，否则浏览器可能选到过大的资源。对脚本还要分析依赖、未使用代码、压缩与缓存；gzip/Brotli 降低传输量，但解压后的代码仍要解析和执行。

## 让主线程及时响应

一个任务中大量排序、解析或组件更新会延后输入与绘制。首先减少工作量，再考虑分批或 Worker。Worker 适合不依赖 DOM 的计算，但复制大数据、启动和消息处理也有开销。框架的异步更新并不意味着复杂计算自动离开主线程。

```javascript
async function processInBatches(items, consume) {
  for (let start = 0; start < items.length; start += 100) {
    for (const item of items.slice(start, start + 100)) consume(item);
    if (start + 100 < items.length) {
      await new Promise(resolve => setTimeout(resolve, 0));
    }
  }
}
```

这只是主动让出任务的简单示范，100项并不是通用最佳批量。如果单项就很重仍会卡顿；如果需要按帧预算调度，还应测量耗时和交互。纯 `await Promise.resolve()` 只切到微任务，不一定让浏览器有机会处理下一次交互。

## 渲染成本与资源生命周期

长列表同时挂载几千个复杂节点会增加布局、样式和内存成本。虚拟列表只渲染可见区域附近的项，但需要处理动态高度、键盘导航、滚动定位和可访问性。反复读写布局造成的抖动应改成合理的批量阶段，而不是只加缓存或换网络协议。

图片解码、大阴影、过多图层、字体变化都可能影响渲染。离开页面后仍保留监听器、定时器和闭包，也会逐渐积累资源。优化不是一次性删字节，还包括在组件生命周期结束时正确清理工作。

## 用对照测量完成一次优化

先记录目标用户群、设备、网络、页面版本与基线，选择真正代表体验的指标。每次改变尽量对应明确假设，例如“首屏图片被脚本串行发现”。修改后观察相关时间段是否缩短，同时检查错误率、缓存命中、视觉结果和其它指标是否恶化。

线上比较应使用合理样本和分位数，避免只展示最好的一次。监控按版本、设备和网络分组，保留回滚能力；若改善仅发生在热缓存桌面环境，就不要宣称移动端整体提升。最终能解释的是哪段工作被消除或提前，而不是一句“我做了懒加载和 CDN”。
